7.3 Forward, deferred and clustered

Every lit pixel needs its material and every light that reaches it. Forward, deferred and clustered rendering are three ways of organising that work, and the choice decides how many lights a game can afford, how much memory traffic each frame costs, and whether transparency and MSAA come easily.

1 The picture

2 In plain words

A shading model (7.2) says how one light lights one point. A frame has about two million points on screen at 1080p and often dozens of lights. The rendering path is how a renderer organises that multiplication: which light meets which pixel, in which pass, and what gets written to memory in between.

There are two classic answers. Forward rendering lights each object as it is drawn. Deferred rendering first draws every object into a set of screen-sized images that record each pixel's surface, and adds the light afterwards. Modern renderers add a third ingredient to either: they cut the screen into small regions and work out in advance which lights reach each one.

Everyday comparison

A town runs leaflet campaigns, each covering one neighbourhood. In the forward way, every street checks every campaign that touches any part of it, so a long high street hears about nearly all of them. In the deferred way, the town first maps every house, and each campaign team then walks only its own neighbourhood on the map.

In the clustered way, each postcode keeps a short list of the campaigns covering it, and every house just reads its own postcode's list.

The problem it solves

Lighting costs surfaces times lights. Most of those pairs are wasted: lights that do not reach a pixel, pixels shaded and then hidden behind something nearer, materials worked out again for every light.

Each rendering path removes some of that waste, at a price in memory, bandwidth or flexibility.

Why a lead cares

The rendering path is one of the earliest technical decisions in a project and one of the hardest to reverse. It sets the dynamic light budget, decides whether MSAA is available, changes how transparent objects are lit, and governs how much memory bandwidth every frame spends, which matters most on phones, standalone VR and at 4K. Engines pick a default; switching later changes which features work, so the decision belongs in pre-production with the art direction in mind.

3 How it works

Start with forward rendering, then deferred and its G-buffer, then the light culling that both use today, and finish with the problems deferred rendering has to work around.

1 Forward: light each object as it is drawn

Forward rendering is the obvious way. For each object, the CPU works out which lights touch it and hands the shader that list. The pixel shader reads the material's textures and loops over the lights. Everything about the pixel is decided in one go.

Two kinds of waste creep in. Lights are matched to whole objects, so a large floor gets every light that touches any part of it, and its pixels loop over lights far away from them. And a pixel may be fully shaded and then covered by something nearer, which is overdraw; a depth pre-pass removes most of that at the cost of drawing the scene twice.

Forward renderers cap the lights per object to keep shaders short. Unity's URP Forward path allows the main light plus eight additional lights per object, and Godot's Mobile renderer eight omni and eight spot lights per mesh. Past the cap, lights are dropped, which is why 7.1 lists flickering lights as a forward symptom.

2 Deferred: write the surfaces down, light them later

Deferred rendering splits the frame in two. The geometry pass draws every opaque object once and runs only the material: it reads the textures and writes the results, base colour, normal, roughness and so on, into the G-buffer, a set of screen-sized render targets plus the depth buffer. GPUs can write several targets from one pixel shader at once, called multiple render targets, so this takes one pass.

The lighting pass then works on the screen instead of on objects. For each pixel it reads the G-buffer, rebuilds the surface, and adds the light of every light that reaches it. Material cost no longer multiplies with light count, and lights only touch the pixels they cover. Olsson and colleagues trace the idea to a 1988 hardware design and the full-screen G-buffer to 1990, and in 2012 described it as mainstream only in recent years, once GPUs had the memory to spare.

3 A G-buffer you can look at

The Lantern Courtyard is a small deferred renderer. Its G-buffer pass writes three colour targets and depth, and every view below except Final is one of them, shown as a picture. Nothing in these buffers is lit yet: that happens in the lighting pass, which reads all of them for every pixel.

4 G-buffer layout and bandwidth

The G-buffer layout is the list of what is stored, in which target and in what format. Every byte per pixel is multiplied by every pixel on screen and paid for twice a frame: once when the geometry pass writes it, once when the lighting pass reads it. Burns and Hunt, writing in 2013, put typical optimised layouts at 16 to 32 bytes per pixel.

Layouts are a constant negotiation. Normals squeezed into 24 bits band on smooth surfaces, so URP offers a slower, more accurate encoding as an option. A deferred renderer also needs to know which shading model (7.2) each pixel uses; URP keeps it in the top four bits of the stencil buffer. Materials that do not fit the layout at all, such as URP's Complex Lit or HDRP's Fabric and Hair shaders, are drawn with a forward pass alongside the deferred ones.

5 Lighting the G-buffer, light by light

The classic way to run the lighting pass is to draw a light volume for each light: a sphere for a point light, a cone for a spot, sized to its range. Only pixels inside the shape run that light's shader, using the stencil buffer to reject pixels in front of or behind the light's range. URP's Deferred path works this way.

The catch is bandwidth. Every light volume reads the G-buffer again for every pixel it covers and adds its result into a light buffer, which means reading and writing that too. With eight lights over the average pixel, a 1080p frame reads and writes several hundred megabytes in the lighting pass alone. Tiled and clustered shading were invented to fix exactly that.

6 Tiles and clusters

Light culling works out ahead of time which lights can reach which part of the screen. Tiled shading cuts the screen into tiles, such as the 32 × 32 pixel tiles in Olsson and colleagues' tests, and a compute shader builds a list of the lights that reach each tile. Each pixel then reads the G-buffer once and loops over its tile's short list, which turns the lighting pass from bandwidth-bound into arithmetic-bound.

Tiles have a blind spot. A tile is a column reaching from the camera into the distance, and if it contains both a near post and a far wall, every light floating in the empty space between them counts too. Clustered shading, published by Olsson, Billeter and Assarsson in 2012, also slices each column in depth, with slices that grow with distance, and keeps only the lights that reach a slice where there is something to light. In their tests a scene with about 2,400 lights took 17 ms with clusters against 26 ms with tiles.

The same light lists work for forward rendering. Forward+, presented by Harada, McKee and Yang at Eurographics 2012, adds a depth pre-pass and per-tile light lists to forward rendering, so each pixel loops only over nearby lights with no G-buffer at all. Godot's Forward+ renderer and Unreal's forward renderer use grids of this kind, and Unity's URP offers Forward+ and Deferred+, the tiled and clustered versions of its two paths.

7 How cost grows with the number of lights

The plot below is a small illustrative cost model. Each path is a straight line: a fixed cost for the frame plus a cost for every extra light. Forward with per-object lists has the steepest line, because objects meet far more lights than their pixels need. Classic deferred pays a fixed price for its G-buffer and then re-reads it for every light. Clustered pays a small fixed price for its lists and has the shallowest line.

Maths The model behind the plot

P is the pixel count, N the number of lights, a the share of the screen each light's range covers. The GPU is assumed to achieve 5 trillion operations a second and 400 GB/s of memory bandwidth. One light at one pixel costs 150 operations; building one pixel's surface from its textures costs 100. All three paths start with a depth pre-pass.

forward = pre-pass + P × (material + N × min(1, 8a) × light) + colour write

deferred = pre-pass + P × material + G-buffer write + N × a × P × (light + read 20 B + read and write 16 B) + N × 2 µs

clustered = pre-pass + light lists + P × (material + N × a × 1.5 × light) + colour write

The 8 says an object meets eight times as many lights as an average pixel; the 1.5 says a cluster's list holds half as many lights again as really touch the pixel. Change either and the lines move, but their order rarely does.

8 Why transparent objects fall back to forward

A G-buffer stores one surface per pixel. A window in front of a wall needs two, the glass and the wall behind it, and blending them needs both lit. So deferred renderers draw the opaque world into the G-buffer and light it, then draw transparent objects afterwards with an ordinary forward pass, sorted back to front and blended on top, as in 5.5 Depth and blending.

That second path has its own limits. URP's Deferred path lights transparent objects with at most nine lights each, like its Forward path. HDRP always renders transparent Lit materials forward. Unreal's forward renderer cannot do dynamically shadowed translucency, one of several features its documentation lists as unsupported there.

9 MSAA and deferred

Multisample anti-aliasing, MSAA, smooths edges by keeping several samples per pixel along triangle edges (9.2 Anti-aliasing). In a deferred renderer every sample needs its own G-buffer data, so 4× MSAA multiplies the G-buffer by four: URP's 20 bytes become 80 bytes per pixel, 633 MB for one 4K G-buffer. Engines do not offer it. Unreal supports MSAA only with its forward renderer, URP only on its Forward and Forward+ paths, and HDRP only in Forward Only or Both modes.

Deferred engines use temporal anti-aliasing and upscalers instead. Forward rendering keeps MSAA available, which is one reason it is common in VR: Epic's documentation notes that the constant small head movements in VR make temporal techniques look blurry, "making MSAA a better choice".

10 Visibility buffers and deferred decals

A visibility buffer pushes the deferred idea further. Instead of the material's results, the geometry pass stores only which triangle covers each pixel, in as few as four bytes, as Burns and Hunt described in 2013. A later pass looks the triangle up, rebuilds its position, UVs and normal at that pixel, and runs the material only for pixels that are really visible. Unreal's Nanite rasterises into a 64-bit visibility buffer, depth plus cluster and triangle index, then writes an ordinary G-buffer so it fits the rest of Unreal's deferred renderer.

Deferred rendering also makes decals cheap. A deferred decal is a box projected onto whatever the G-buffer already holds inside it: it rewrites the albedo, normals or roughness there, before any light is added, so a bullet hole or a puddle stain is lit exactly like the wall under it.

4 What it costs

The main costs are memory, bandwidth and the time spent on lights that do not matter. Take a 1080p frame (2,073,600 pixels) with URP's 20-byte G-buffer and eight lights over the average pixel.

A desktop GPU can absorb a few gigabytes a second; tens of gigabytes a second is a real share of its bandwidth, and on phones and standalone headsets, where memory traffic also costs battery and heat, it is often the deciding factor. Tile-based mobile GPUs (tile-based GPU) can keep a G-buffer in on-chip memory if the geometry and lighting passes share one render pass; otherwise Unity warns that Deferred has a high performance impact on mobile because of the extra passes.

What makes the bill grow

  • ResolutionG-buffer memory and traffic scale with pixel count: 4K is four times 1080p.
  • Bytes per pixelEach extra G-buffer target or wider format adds to every write and every read.
  • Overlapping lightsClassic light volumes re-read the G-buffer per light; forward with per-object lists pays for distant lights.
  • Light rangeBigger ranges put lights in more tiles and clusters and over more pixels.
  • TransparencyA deferred renderer still needs a complete forward path, with its own shaders and light lists, for everything transparent.
  • MSAAMultiplies the G-buffer by the sample count, which is why deferred engines do not offer it.

In proportion

No path is fastest everywhere. With a handful of lights, forward costs least and keeps MSAA. With many lights, clustered light lists win on either path. Deferred buys cheap decals, screen-space effects and one material evaluation per pixel at the price of bandwidth. Measure on the target hardware with the real content, and look at the light complexity view before blaming the path.

5 How it breaks

Most rendering-path problems show up as lights misbehaving, transparent objects looking out of place, or a frame that slows down far more than expected when the resolution goes up.

Lights pop in and out

Cause
A limit is reached: lights per object in a forward path, or the maximum lights or clustered elements per view, so the engine drops different lights as the camera moves.
Ask for
The engine's light complexity or cluster view at that spot, the limit that applies to the path in use, and the cheapest fix: smaller ranges, fewer lights, split meshes or a clustered path.

Glass lit differently from the wall behind it

Cause
Transparent objects go through the forward fallback, which has its own light limits, shadow support and features, so they miss lights the deferred world receives.
Ask for
The light list and limits for transparent materials on this path, and a side-by-side of the same light on an opaque and a transparent surface.

Jagged edges and no MSAA option

Cause
The project uses a deferred path, where MSAA is not available, and temporal anti-aliasing is off or unsuitable, as often in VR.
Ask for
A comparison of the engine's temporal options against switching to a forward path with MSAA, with the features each choice gives up.

Stepped rings in smooth highlights

Cause
Normals are packed into too few bits in the G-buffer, so smooth, glossy surfaces show steps in their highlights that forward rendering does not.
Ask for
The G-buffer normal format and any accurate-normals option, such as URP's, with its cost measured on the target hardware.

4K or mobile frames slow down far more than expected

Cause
The G-buffer and lighting passes are limited by memory bandwidth, which grows with pixels and bytes per pixel, and on mobile by extra passes that leave tile memory.
Ask for
A GPU capture with the time and memory traffic of the G-buffer and lighting passes at both resolutions, and options: fewer G-buffer bytes, a lower internal resolution with an upscaler, or a forward path.

Each engine can draw where lights pile up: Unreal's Light Complexity view mode, URP's Lighting Complexity debug mode for Forward+ tiles, HDRP's Tile/Cluster Debug in the Rendering Debugger's Lighting panel, and Godot's Cluster Omni Lights and Cluster Spot Lights debug draw modes.

Switching paths late

Unity's documentation notes that Deferred and Deferred+ need shader model 4.5 and do not support OpenGL or OpenGL ES, and that Unity falls back to Forward when a device or a shader cannot use the selected path. Unreal's forward renderer drops several screen-space features. Check every effect the art direction relies on before switching, not after.

Rendering-path briefs need the engine, the platforms and their frame budgets, the light counts as numbers, and the features that must keep working. Adapt these.

Questions to ask when reviewing rendering-path work

  1. Which path does each platform use, and what is the light limit there?Limits differ per path and per platform, and exceeding them drops lights silently.
  2. How many bytes per pixel is our G-buffer, and how many times is it read per frame?That is the bandwidth bill at every resolution.
  3. Which materials and effects fall back to forward?Transparents and special materials get different lights and features.
  4. How do we anti-alias, given the path?MSAA needs forward; deferred depends on temporal methods.
  5. What does the light complexity view look like in our busiest view?It shows where lights pile up before anyone changes the path.
  6. What would switching path later break?Features differ between paths; knowing now avoids a costly surprise.

8 Check yourself

  1. A level has 40 small lights scattered over one large floor mesh. Why does forward rendering with per-object light lists struggle here, and what fixes it without going deferred?

    Show answer

    Lights are matched to whole objects, so every pixel of the floor loops over every light that touches any part of it, and a per-object cap such as URP Forward's nine will drop most of them. Forward+ fixes it: per-tile or per-cluster light lists give each pixel only the lights near it.

  2. Why can a deferred renderer not simply draw a glass window into the G-buffer like a wall?

    Show answer

    The G-buffer stores one surface per pixel. A window pixel needs two, the glass and what is behind it, both lit, then blended. So transparent objects are drawn after the lighting pass with a forward pass, sorted back to front.

  3. A 20-byte G-buffer is written and read once per frame at 60 fps. Roughly how much memory traffic is that at 1080p, and at 4K?

    Show answer

    At 1080p: 2,073,600 × 20 B × 2 ≈ 83 million bytes a frame, about 5 GB/s at 60 fps. At 4K, four times the pixels: about 20 GB/s. Every extra read of the G-buffer adds more.
