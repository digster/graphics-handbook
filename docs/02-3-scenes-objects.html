2.3 Scenes, objects and components

Every engine has to record where each thing in a game world is, what it is made of and what it does. They do it in one of two shapes: a tree of objects that carry components, or tables of components that code sweeps through in bulk.

1 The picture

2 In plain words

Open any game editor and you see the same three panels. A list of everything in the level, a 3D view of it, and, when you click one thing, a column of settings for that thing. The list is the scene. The things in it are objects. The blocks of settings are components.

A scene is one saved world or piece of a world: a level, a main menu, a test room. Unreal Engine calls it a level or a map. Every object placed in it has a transform, its position, rotation and scale. The object itself does almost nothing. Its components do the work: one holds the mesh to draw, one the collision shape, one a light, one a script that makes the light flicker.

Objects can hang under other objects, so a lantern moves when its post moves. And when the same arrangement is needed fifty times, it is saved once as a reusable template and placed fifty times. The last section of How it works covers the second shape from the picture, where components live in tables instead of inside objects.

Everyday comparison

A new phone does very little. The apps you install decide whether it is a camera, a map or a music player. Two phones with the same apps behave the same way, wherever they are.

The object is the phone, its transform is where the phone is, and the components are the apps. A reusable template is a backup you restore onto fifty phones, and changing one phone's wallpaper afterwards is a local change that the backup does not overwrite.

The problem it solves

Without components, programmers would write a new type of object for every combination: lantern on a post, crate with a light, crate that floats. Each new idea would wait for code.

With components, a designer makes a floating crate by adding a physics component and a hover script to an ordinary crate. With templates, they make it once and reuse it everywhere.

Why a lead cares

This structure decides how your team builds levels, how many things the game can afford to simulate, and what good code looks like in your engine. It comes with the engine: Unreal's Actors, Unity's GameObjects and Godot's nodes work differently, and each engine's option for huge numbers of things is a separate way of working that needs its own skills. Building 30 doors with an entity component system wastes weeks. Giving 50,000 bullets a scripted object each can eat the CPU's share of every frame.

3 How it works

Follow the courtyard from its file on disk to the code that moves it each frame. There are seven steps.

1 Scenes: the saved world

A game is a set of scenes. Each one is a file that lists every object in it with its components and settings: .umap in Unreal Engine, .unity in Unity, .tscn in Godot. Loading a scene creates those objects in memory, and from then on the engine updates them every frame.

Small games load one scene at a time: the menu, then the courtyard, then the crypt. Open worlds are too big for that. Unreal's World Partition keeps one persistent level split into grid cells and loads the cells near the player, unloading them as the player moves away.

2 Transforms: where, which way, how big

Every placed object has a transform. Position says where it is, usually in metres. Rotation says which way it faces. Scale says how big it is compared with the model as it was made. Rendering reads the transform to know where to draw the mesh, physics reads it to know where the collider is, and gameplay code changes it to move things.

Engines differ in where the transform lives. In Unity every GameObject has a Transform component and cannot exist without one. In Unreal an Actor has no transform of its own: it borrows the transform of its root component. In Godot the transform is built into every 3D node.

3 Parents and children: local and world

Objects form a tree. The scene graph is that tree: the scene at the root, objects below it, and objects hanging under other objects. Unity shows it in the Hierarchy window, Unreal in the Outliner, Godot in the Scene dock.

The links in the tree make a transform hierarchy: whatever happens to a parent happens to its children. So a child stores a local transform, measured from its parent, and the engine works out its world transform, measured from the world's origin, by combining the local one with every parent above it. Move the post and the lantern's local transform does not change at all. Its world transform does.

Simplified

The figure only adds positions. Real engines combine position, rotation and scale as a matrix, so turning the post would also swing the lantern around it, and scaling the post would push the lantern further out. 3.4 Spaces and transforms shows how.

Every engine gives code both views, and mixing them up is one of the commonest bugs in AI-written gameplay code. In Unity, transform.position is the world position and transform.localPosition the local one. In Godot, position is local and global_position is world. Unreal splits it by call: SetActorLocation places an Actor in the world, while SetRelativeLocation moves a component relative to its parent.

4 Objects and components in each engine

The three big engines agree that objects are built from parts. They disagree about what an object is.

In Unreal Engine an Actor is anything that can be placed in a level. Its components come in three kinds. Actor Components add behaviour and have no position. Scene Components have a transform and can attach to each other, and one of them is the root that gives the Actor its place in the world. Primitive Components are Scene Components that can be drawn or collided with, such as a static mesh.

In Unity a GameObject is a container that always has a Transform, and every other part is a component added to it: a mesh renderer, a collider, a light, and scripts, which are components too. Parts that need their own position become child GameObjects.

Godot has no separate idea of a component. A node does one job, such as drawing a mesh, holding a collision shape or casting light, and an object is a small branch of nodes. Each node can carry one script.

Simplified

These are reasonable setups, not the only ones. An Unreal team might make the lantern a separate Actor attached to the post; a Unity team might put the light on its own child. The parts and the rules stay the same.

5 Prefabs, instances and overrides

A courtyard needs many crates. Nobody builds each one by hand. A prefab is a saved object, with its components and children, that can be placed again and again. Each placed copy is a prefab instance, still linked to the prefab, so a change to the prefab reaches every copy.

A level designer can still change one copy. That change is an override, and it always wins: if Crate B's scale is overridden, later edits to the prefab's scale skip Crate B. Unity marks overrides in the Inspector with a blue line and bold text and offers Apply and Revert. Godot shows a revert icon beside each overridden property. When many copies share the same changes, a prefab variant is cleaner: a mossy crate made from the plain one, inheriting everything it does not change.

The names differ. Unity calls them prefabs, with variants and prefabs nested inside prefabs. In Godot any saved scene can be placed inside another as an instance, so scenes double as prefabs. In Unreal the usual template is a Blueprint class: an asset made with Unreal's visual scripting system that bundles an Actor's components, settings and logic, placed in levels as instances whose properties can be changed one by one.

6 ECS: components in tables

The object model is easy to understand and edit, but it scatters data. Each object is created on its own, somewhere in memory, and its components are separate pieces reached through pointers. Code that updates 10,000 crates jumps from place to place.

That matters because the CPU never reads one value from main memory. It copies a whole block, usually 64 bytes, into its cache, a small, fast memory next to each core. Reading a value already in the cache takes around half a nanosecond. Missing the cache and going to main memory takes around 100 nanoseconds, about 200 times longer.

An entity component system (ECS) turns the data inside out. An entity is only an ID number. Components are plain data with no code, stored in tightly packed arrays, one array per component type. A system is code that runs over every entity with the components it needs, in order, one array at a time. Entities with exactly the same set of component types form an archetype, and each archetype is stored in fixed-size blocks called chunks; in Unity's Entities each chunk is 16 KiB.

Simplified

The top strip is the worst case. Real CPUs keep several cache misses in flight at once, and engines already pack some object data: Unity, for example, has optimised the memory layout of its transforms. Measure with a profiler before redesigning anything for the cache.

ECS has costs too. The data is harder to see and edit than an object with a list of components, debugging means reading tables rather than clicking on a thing, and adding or removing a component moves an entity to a different archetype, which Unity's documentation warns is expensive when done often.

7 How the engines combine both

No major engine asks designers to edit tables. Each keeps objects for editing and puts bulk data underneath.

Unity's DOTS, its data-oriented toolset, is built around the Entities package. Designers place ordinary GameObjects in a subscene, and a step called baking converts them to entities, in the editor only, never during play. Unity's ECS packages now ship as core packages of the editor, and Unity is aligning the IDs of GameObjects and entities so the two can work together more closely.

Unreal's Mass Entity framework is an ECS for large numbers of similar things. Its components are called fragments and its systems processors. Epic's City Sample uses it for the crowds and the traffic, with spawner Actors placed in the level creating the entities. Hand-placed gameplay objects stay Actors.

Godot has no ECS. Its developers explained in 2021 that nodes are the interface designers work with, while the heavy data for rendering, physics and audio lives in servers that process it in bulk.

Moving target

This area is changing. Unity is bringing GameObjects and entities closer in each Unity 6 release. Epic's Unreal Editor for Fortnite uses a newer entity-and-component model called Scene Graph, still in beta, and Epic has said Unreal Engine 6 will eventually move gameplay to a framework built on it, keeping Actors and Blueprints in early versions. Check the current state before committing a project to either.

4 What it costs

Take a system that moves 10,000 crates each frame. Each crate's position is three 4-byte numbers, 12 bytes. The work per crate is tiny; fetching the data is what costs.

The scattered case cannot be predicted that way. Neither row includes the cost of calling a separate update function on each of 10,000 objects, which per-object scripts add on top.

The hierarchy has a cost as well

Every child's world transform depends on its parents, so moving a parent means recomputing everything under it. Unity's own performance team described a game that moved ability objects out from under its moving characters and spawned characters at the root of the scene, and gained about 10 frames per second on its target hardware.

  • Object countEach object that updates every frame adds a call and scattered reads. Thousands add up to milliseconds.
  • Moving parents with many childrenEvery frame the parent moves, every child's world transform is recomputed.
  • Spawning and destroying during playCreating objects allocates memory and runs setup code; reusing a pool of objects avoids most of it.
  • Structural changes in an ECSAdding or removing a component moves the entity's data to another archetype's chunk.
  • Many archetypesEach archetype gets its own chunks, so thousands of nearly empty ones waste memory and break up the arrays.
  • People-timeECS code needs programmers who think in data layouts and tools that show tables. Budget for that before choosing it.

5 How it breaks

Most scene bugs are one of a few shapes. The first four you can usually see in the editor; the last two show up in a profiler.

A part stays behind

Cause
The lantern sits at the root of the scene, or code detached it, so it is not a child of the post and does not follow it.
Ask for
The parent of every moving part in the hierarchy, and a check that the code spawning it also attaches it.

Jumps when attached

Cause
Code set a world position where it meant a local one, or attached with a rule that kept the old world position. Unreal's attachment rules and Unity's worldPositionStays flag decide this.
Ask for
Which space each transform write uses and which attachment rule is used, plus a test that attaches at a known offset.

A child looks sheared

Cause
A parent with different scale on each axis and a rotated child. Combined, they shear the child into a shape no position, rotation and scale can describe, and colliders stop matching.
Ask for
Uniform scale on parents. Scale the mesh itself or a child at the end of the chain instead.

A prefab change does not arrive

Cause
That instance has an override on the property, and an override always wins over the prefab.
Ask for
The instance's list of overrides (Unity's Overrides dropdown, Godot's revert icons) and a team rule on which properties level designers may override.

Frame time climbs with object count

Cause
Every object runs its own update each frame and reads scattered memory. Hundreds are fine; tens of thousands are not.
Ask for
A profile of per-object update cost, then fewer updates (only nearby or visible things), pooling, or moving the hot set to Entities or Mass.

ECS memory balloons

Cause
Too many archetypes, often from giving entities many different shared component values, so each chunk holds only a few entities. Unity's documentation shows 100,000 one-entity archetypes taking more than 1.5 GB.
Ask for
The archetype count and how full the chunks are, and a review of how shared components are used.

To confirm the last two, record a CPU profile: Unreal Insights, the Unity Profiler or Godot's profiler. Look for one function called thousands of times per frame, or for time spent in transform updates.

7 Say it to your AI

Good briefs about scene structure say how many of each thing exist, what runs on them every frame, and who edits them. Without that, an AI will pick a structure that suits a tutorial rather than your game. Adapt these.

BriefUse when deciding how to build large numbers of things
Engine: Unity 6.6, URP. Targets: PC and PlayStation 5 at 60 fps.
Our market square needs 3,000 walking townsfolk. Today each one is a GameObject with an Animator, a NavMeshAgent and our Townsperson script. Level designers place market stalls by hand; townsfolk are spawned at runtime.

1. Profile the current setup and tell us where the CPU time per frame goes.
2. Compare three options: keep GameObjects but update less often, move townsfolk to Entities, or a hybrid where only nearby townsfolk are GameObjects. For each, estimate CPU time, list what designers lose in the editor, and name the risks.
3. For the option you recommend, list the components or fragments each townsperson would have.
4. Tell us how we will measure before and after, on PlayStation 5.
  • Counts, frame rate and platform tell the AI whether ECS is worth its cost.
  • Saying who edits what keeps the answer from removing tools designers rely on.
  • Asking for options and a measurement plan avoids a rewrite on faith.
Bug reportUse when objects jump or drift when parented
Unreal Engine 5.8. When the player picks up a lantern we attach it to the hand socket. Since yesterday's merge the lantern appears about 3 m in front of the hand instead of in it. Lanterns placed in the level and then picked up are wrong; lanterns spawned straight into the hand are fine.

Find the cause. Check every place the lantern's transform is written: whether it sets a world or a relative location, and which attachment rule each attach call uses. Show me the line that is wrong, the fix, and an automated test that attaches a lantern at a known offset and checks its world position.
  • The pattern (placed lanterns wrong, spawned ones fine) points at a kept world position.
  • Naming local, world and attachment rules keeps the search on transforms.
  • A test with a known offset stops the bug coming back.

Questions to ask when reviewing scene and object code

  1. Which objects are children of which, and why?Deep chains under moving parents cost CPU every frame and cause parts to be left behind when they are wrong.
  2. Does each transform write mean local or world, and does the code say so?Mixing the two is the commonest cause of objects that jump.
  3. How many of these will exist at once, and what runs on each one per frame?Per-object cost times object count is the bill.
  4. Are these created and destroyed during play, or pooled?Spawning in bulk during play causes hitches.
  5. Does this change edit the prefab, or override one instance?Overrides silently block later prefab edits.
  6. In ECS code, does anything add or remove components every frame?Each one moves an entity's data to another archetype.

8 Check yourself

  1. A post stands at world x = 3 m. Its child lantern has local position (0.5, 2). You move the post to x = 10 m. What are the lantern's local and world positions now?

    Show answer

    Local is unchanged at (0.5, 2). World is (10.5, 2), because the engine combines the post's new position with the lantern's local one.

  2. A designer changes the crate prefab's material. Every crate in the level updates except one. What is the likely cause?

    Show answer

    That crate has an override on its material. Overrides always win over the prefab, so the edit skips it. Revert the override, or apply it to the prefab if it was intended.

  3. Why does an ECS system that moves 10,000 entities usually beat 10,000 objects that each move themselves?

    Show answer

    The positions sit side by side in one array, so the CPU loads only the bytes it needs, in an order it can fetch ahead, and runs one loop instead of 10,000 separate update calls. Scattered objects load a whole cache line from a new place for each one.
