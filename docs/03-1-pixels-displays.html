3.1 Pixels and displays

A game draws each frame into a grid of pixels in memory, and the screen reads that grid out row by row, many times a second. The game and the screen run on separate clocks, and how they hand frames to each other decides whether motion looks smooth, torn or jerky.

1 The picture

2 In plain words

A screen is a grid of tiny lights. Each one is a pixel, and the game decides its colour every frame. The finished picture sits in a block of memory called a framebuffer, one colour value per pixel, before the screen shows it.

The screen does not take the whole picture at once. It reads it out from top to bottom, row after row, and starts again at the top many times a second. The game, meanwhile, produces frames at whatever speed the work allows: sometimes faster than the screen, sometimes slower, rarely in step. Everything about smoothness comes down to how a finished frame is handed to a screen that is already busy reading the previous one.

Everyday comparison

A station departures board that updates row by row, top to bottom, once a minute. A clerk prepares the next timetable on a clipboard and hands it over when it is ready.

If the clerk hands over a new sheet while the board is halfway through updating, the top rows show the old times and the bottom rows the new ones. The board can wait for the clerk, or the clerk can wait for the board to finish. Those are the choices a game has.

The problem it solves

Without rules for the handover you get a picture split between two moments in time, a tear. Strict rules remove the tear but make finished frames wait, and uneven waits show as stutter.

Modern screens can also do the waiting themselves: they hold off refreshing until the next frame arrives. That removes both problems inside a range of speeds.

Why a lead cares

Resolution is the biggest single lever on GPU cost: 4K has four times the pixels of 1080p, and most of a frame's GPU time is spent per pixel. The handover settings (vsync, frame caps, variable refresh) decide how a given frame rate feels, and they are among the first options players look for in a settings menu. "It stutters" and "it tears" are two different bugs with two different fixes, and you need to tell them apart in a playtest report.

3 How it works

Follow one frame from the GPU's memory to the glass. There are seven steps.

1 Pixels and the framebuffer

Look closely at a screen and each pixel is three small lights, red, green and blue, each set to a brightness. Mixing the three makes every colour the screen can show. 3.2 Colour done right covers what those numbers mean; here they are just bytes.

The GPU writes a frame into a framebuffer in its own memory, VRAM. The most common layout stores each pixel in 4 bytes: one each for red, green and blue, and one spare channel called alpha. Pixels follow each other along a row, and rows follow each other down the image, so the framebuffer is simply the picture as a long list.

2 Resolution: how many pixels

A picture's resolution is its size in pixels, written width × height. The everyday names count rows: 720p is 1280 × 720, 1080p is 1920 × 1080, 1440p is 2560 × 1440, and 4K (in games and TVs) is 3840 × 2160. The "p" comes from television and means every row is drawn in every refresh.

The names hide how fast the numbers grow. Doubling the width and the height quadruples the pixels, so 4K is exactly four times 1080p, not twice. Each of those pixels is coloured by a small program on the GPU, the pixel shader, often several times per frame.

The resolution the game renders at does not have to match the screen. Many games render at a lower internal resolution and scale the result up, which 9.3 Upscaling and frame generation covers. The screen's own pixel count, its native resolution, is fixed: anything else is stretched to fit, and stretching softens the picture.

3 How a screen draws: scan-out and refresh rate

A screen's refresh rate is how many times per second it redraws, in hertz (Hz). A 60 Hz screen starts a new picture every 16.7 ms; 120 Hz every 8.3 ms; 144 Hz every 6.9 ms. This is the display's clock, and on most screens it never changes while the game runs.

Each refresh is a scan-out: the display hardware reads the framebuffer one row at a time, top to bottom, and updates the matching row of the panel. After the bottom row comes a short pause before the top row starts again, the vertical blank. That pause is the only moment when no row is being read.

Simplified

The figures draw the vertical blank much wider than it is so you can see it, and treat scan-out as a steady sweep. Real panels differ in detail (some light rows in groups, OLEDs and LCDs respond at different speeds), but every common display still takes its picture out of the framebuffer in order, during the refresh.

4 Front buffer, back buffer, present

The GPU cannot draw into the framebuffer the display is reading, or players would watch every frame being painted. So there are at least two. With double buffering the display reads the front buffer while the GPU draws the next frame into the back buffer. When the frame is finished, the game calls present, and the two buffers swap roles.

The graphics API manages these buffers as a swap chain: a small ring of framebuffers, usually two or three, plus the rules for when a presented frame may become the front buffer. Direct3D calls the step Present; Vulkan calls it vkQueuePresentKHR and names the rules "present modes".

5 Tearing: swapping mid-picture

The simplest rule is "swap the moment the frame is done". If that moment falls while the display is reading rows, every row above the scan point came from the old frame and every row below comes from the new one. Anything moving sideways is drawn in two places, offset at a horizontal line: screen tearing. Because the game's clock drifts against the display's, the tear line jumps to a new height every refresh.

Try it below. The simulator slows a 60 Hz display down so you can watch each refresh. It opens with vsync off and a game at 45 fps: watch for rose tear lines in the picture and split blocks in the timeline. Then switch the present mode, and come back to it after the next two steps.

6 Vsync: wait for the blank

Vsync (vertical sync) changes the rule to "swap only during the vertical blank". No row is being read then, so there is never a tear. The cost is waiting: a finished frame sits until the next blank. In Vulkan this is the FIFO present mode, the only one every device must support; in Direct3D it is a sync interval of 1.

When the game keeps up with the display, vsync is ideal: one new frame per refresh, evenly spaced. Trouble starts when frames take longer than a refresh. With double buffering, a frame that misses a blank waits for the next one, and the GPU cannot start another frame meanwhile because both buffers are taken. A game that could run at 45 fps is held to 30, and a game that could run at 29 is held to 20.

Triple buffering adds a third buffer so the GPU can keep drawing while a finished frame waits. The frame rate stays near 45, but the display can only change pictures on its 16.7 ms beat, so some frames stay up for one refresh and some for two. Objects that move at a steady speed appear to lurch: stutter. The extra queued frame also adds up to one frame of delay between input and screen.

This is why fixed-refresh games aim for a frame rate that divides the refresh rate exactly: 60 or 30 on a 60 Hz screen, 120, 60 or 40 on a 120 Hz screen. A steady 30 fps feels smoother than a frame rate wandering between 40 and 59.

7 Variable refresh rate: the screen waits instead

With variable refresh rate (VRR), the display stops keeping its own beat. It holds the vertical blank open until the next frame is presented, then scans that frame out at once. Every frame is shown as soon as it is ready and stays up until the next one arrives, so there is no tearing and no uneven holding. NVIDIA sells this as G-SYNC, AMD as FreeSync, and HDMI 2.1 added its own version, HDMI VRR.

VRR works inside a range set by the panel, such as 48 to 144 Hz. Above the top of the range the screen cannot refresh any faster, so the game either tears or falls back to vsync. Below the bottom, the panel cannot hold a picture long enough, so the driver shows each frame two or more times, evenly spaced. AMD calls this low framerate compensation (LFC): a 35 fps game on a 48 to 144 Hz monitor is shown at 70 refreshes a second, each frame twice.

On Windows

Microsoft's documentation states that variable refresh rate displays need tearing to be allowed in the swap chain: the game presents with a sync interval of 0 and the DXGI_PRESENT_ALLOW_TEARING flag, on a flip-model swap chain. Engines handle this, but custom renderers and ports often miss it, and VRR then silently does nothing in windowed and borderless modes.

Maths The numbers behind every timing figure in this chapter

Time per refresh and time per frame:

refresh period (ms) = 1000 / refresh rate (Hz)   frame time (ms) = 1000 / frame rate (fps)

Under vsync with double buffering, a frame that takes longer than one refresh is held for whole refreshes:

shown frame rate = refresh rate / ceil(frame time / refresh period)

A 22.2 ms frame on a 16.7 ms refresh needs ceil(1.33) = 2 refreshes, so 60 / 2 = 30 fps. With triple buffering the average stays at the game's own rate, but each frame is held for either floor or ceil of that ratio: 1 or 2 refreshes at 45 fps.

Pixel throughput, a rough guide to GPU load:

pixels per second = width × height × frame rate

4 What it costs

Two bills come out of this chapter: GPU time, which grows with pixels and frame rate, and delay, which grows with waiting and buffering.

A competitive player at 1440p and 144 fps asks the GPU for more pixels per second than a 4K player at 60, in well under half the time per frame. The framebuffers themselves are small next to the textures and the intermediate images a modern frame uses, many of which are also screen-sized and so scale the same way.

What makes the cost grow

  • PixelsPer-pixel work scales with width × height. 4K costs four times 1080p for every full-screen effect.
  • Frame rate targetThe frame budget shrinks from 16.7 ms at 60 fps to 8.3 ms at 120 and 6.9 ms at 144.
  • Full-screen passesEvery screen-sized render pass (lighting, effects, post) is paid again at the higher pixel count.
  • Waiting under vsyncA finished frame can wait up to one refresh for the blank: up to 16.7 ms at 60 Hz.
  • Queued framesEach extra frame allowed in the queue (triple buffering, a deeper driver queue) can add one more frame of delay between a button press and the screen.

In proportion

A swap chain of three 4K framebuffers is about 100 MB, a small share of a modern GPU's memory. Resolution's real cost is time, not memory. That is why upscaling, which draws fewer pixels and reconstructs the rest, became standard on every platform.

5 How it breaks

Display problems are easy to describe badly. "It feels choppy" can mean any of the five below. Ask for a video, or a frame-time graph, and match it to a picture.

Torn picture

Cause
Vsync is off, or VRR is not active, so frames swap while the display is reading rows. Worst on fast sideways camera pans.
Ask for
Vsync and VRR options in the settings menu, a check that VRR actually engages in borderless mode, and a frame cap just under the refresh rate for VRR players.

Stutter at a decent frame rate

Cause
Vsync on a fixed-refresh screen with a frame rate that does not divide the refresh rate, such as 45 to 55 fps at 60 Hz. Frames stay up for one or two refreshes unevenly. Uneven frame times from the game itself look the same.
Ask for
A frame-time graph, not an average fps number. Then a cap at 30 or 60, a lighter preset, dynamic resolution, or VRR support.

Stuck at exactly 30 (or 20)

Cause
Double-buffered vsync. The GPU could manage 45 fps but has to wait for every swap, so a frame that misses one refresh waits for the next.
Ask for
The swap chain's buffer count and present mode, GPU time per frame from a profiler, and whether a third buffer or VRR is acceptable for this platform.

Sluggish, floaty controls

Cause
Too many frames between input and screen: vsync waits plus a deep queue of finished frames, often from triple buffering with a GPU faster than the refresh rate.
Ask for
A latency measurement, the queue depth (for example Unity's maxQueuedFrames or Godot's frame_queue_size), and a frame cap slightly below the refresh rate.

Soft or blocky image

Cause
The game outputs a resolution other than the screen's native one and the screen stretches it, or the render scale is below 100% without a good upscaler.
Ask for
The output resolution against the panel's native resolution, the render scale, and whether the interface is drawn at native resolution.

A tear, a stutter and a 30 fps lock can all coexist in one complaint. Ask for the present mode, the refresh rate of the player's screen and a frame-time graph before anyone changes code.

Every engine manages the swap chain for you. What you set are the rules: vsync, frame caps, buffer counts and resolutions, usually from a settings menu backed by these calls.

A cap for VRR players

Godot's documentation recommends, with vsync on and a VRR monitor, capping the frame rate slightly below the refresh rate, using r − r² / 3600: about 138 fps on a 144 Hz monitor. The cap keeps the game inside the VRR range, where it neither tears nor waits for vsync. The same reasoning applies in any engine.

7 Say it to your AI

Good briefs about display behaviour name the engine, the platforms and the screens players use, and describe what is seen in time, not just "it feels bad". Adapt these.

Bug reportUse when motion stutters at a good frame rate
Unreal Engine 5, Windows, DirectX 12. Players on 60 Hz monitors report stutter when panning the camera, even though the fps counter shows 48 to 55. Players on 144 Hz VRR monitors do not report it. Vsync is on.

Explain the likely cause in terms of refresh rate, frame time and how long each frame stays on screen. Propose two fixes with their trade-offs (for example a 30 fps cap option, dynamic resolution to hold 60), and say what we should capture (frame-time graph, present timing) to confirm the cause before and after.
  • The 60 Hz against VRR pattern points straight at vsync judder, not a game bug.
  • Asking for trade-offs stops a single "turn vsync off" answer that brings tearing back.
  • Capturing before and after turns a feeling into evidence.

Questions to ask when reviewing display code

  1. What happens when the game cannot hold the target frame rate on a 60 Hz screen?The answer should name the present mode and buffer count, and whether players see 30 fps, stutter or tearing.
  2. How many frames can be queued between input and screen?Each one can add a frame of delay; the setting is easy to raise and easy to forget.
  3. Does VRR actually engage in borderless windowed mode?On Windows it needs the tearing flag; without it VRR quietly does nothing.
  4. Which settings are only read at startup?Players expect a settings menu to apply changes, or to say that a restart is needed.
  5. Is the interface drawn at native resolution when the 3D render scale is lowered?Blurry text is the first thing players notice about a low render scale.

8 Check yourself

  1. How many times more pixels does a 2560 × 1440 frame have than a 1920 × 1080 frame? And 3840 × 2160?

    Show answer

    2560 × 1440 = 3,686,400 pixels, about 1.78 times 2,073,600. 3840 × 2160 = 8,294,400, exactly 4 times: both dimensions double, so the area quadruples.

  2. A game's GPU work takes 20 ms per frame. On a 60 Hz screen with vsync and double buffering, what frame rate do players get, and what changes with triple buffering?

    Show answer

    20 ms misses the 16.7 ms refresh, so each frame waits for the second blank: 30 fps, evenly held. With triple buffering the GPU keeps drawing at 50 fps, but frames are held for one or two refreshes unevenly, so it stutters, and the extra queued frame adds delay.

  3. A tester reports a horizontal line across the screen that jumps to a different height every frame during fast turns. What is it, and what are the two standard fixes?

    Show answer

    Screen tearing: frames are being swapped during scan-out. Turn on vsync, which swaps only in the vertical blank, or use VRR, where the screen refreshes when each frame arrives. With VRR, cap the frame rate just below the screen's maximum so it stays in range.
