10.2 A mobile frame

A phone's GPU draws the same passes as a console's, but it pays for every byte that leaves the chip in battery and heat. This chapter follows a frame through a tile-based GPU: what stays on the chip, what has to go out to memory, what each choice costs, and how engines arrange their passes so the frame stays small for a whole session.

1 The picture

2 In plain words

Phone GPUs, most standalone headsets and Apple's own GPUs draw the screen in small squares. They first work out which triangles touch which square, then finish each square completely inside a little memory on the chip and write the result out once. 3.5 CPU, GPU and graphics APIs introduced the idea; this chapter is about what it does to a whole frame.

The rule that follows is simple. Anything a frame can do inside one square is cheap. Anything that forces a finished image out to main memory and back again costs memory bandwidth, and on a phone bandwidth turns into battery drain and heat. Heat matters because a phone can shed very little of it, and after some minutes of running hot it slows itself down.

An everyday comparison

A cook in a small kitchen with the pantry down a flight of stairs. Fetching each ingredient as the recipe calls for it means hundreds of trips. A good cook brings up one tray with everything one dish needs, finishes the dish on the counter, plates it and only then goes back down. The counter is small, so the work is planned dish by dish.

The problem it solves

Main memory is far from the shader cores and expensive to reach, in time and in energy. Working tile by tile in on-chip memory lets a phone draw console-style frames on a phone's small power budget, as long as the frame is arranged so the tiles do not have to keep going back to the pantry.

Why a lead cares

Mobile performance problems are often about bytes and heat, not shader maths. A feature that costs 0.3 ms on a console can cost a phone several milliseconds and a warm hand if it breaks the tile. A game can hold 60 fps in a five-minute test and drop to 40 twenty minutes in. Ask how each pass loads and stores its images, which effects force a round trip, and what the frame looks like after 30 minutes on the slowest target device.

3 How it works

The steps follow one render pass from its triangles to the image it leaves behind, then widen out to the whole frame, the engines' choices and a whole play session. Bandwidth numbers are worked for 1920 × 1080 at 60 fps, where one 4-byte-per-pixel image is 8.3 MB.

1 Binning: sorting triangles into tiles

A tile-based GPU runs each render pass in two phases. The first, binning, runs the vertex shaders for every draw in the pass and adds each triangle to a list for every tile it touches. Arm's Mali GPUs use 16 × 16 pixel tiles, so a 1080p screen is 120 × 68 = 8,160 tiles. The lists go out to main memory, a cost an immediate-mode GPU does not have. Arm calls this the main overhead of tile-based rendering, and notes that tessellation in particular is disproportionately expensive on a tile-based GPU.

The second phase draws one tile at a time from start to finish: set up the tile, shade only the pixels of the triangles in its list, then write the finished tile out. Qualcomm's Adreno GPUs call tiles bins and size them to fit their tile memory, and their driver can also choose to render a pass directly to memory instead.

2 Tile memory: small, fast and close

Tile memory is the store inside the GPU that holds the current tile's colour, depth, stencil and MSAA samples. Depth tests and blending happen there, without touching main memory. Apple's documentation lists its advantages: bandwidth and latency many times better than device memory, and much lower energy per access. Qualcomm calls it GMEM.

It is small, so formats matter. Arm's guide says older Mali GPUs have 128 bits of colour storage per pixel for 16 × 16 tiles, Mali-G72 and later up to 256 bits, and recent GPUs up to 1,024. A frame that needs more still works, but the GPU switches to smaller tiles, which Arm warns can reduce performance.

3 Load and store actions

Every render pass has to say what happens to each of its images at the start and at the end, because on a tile-based GPU those are the only moments main memory is touched. The load action sets the start: Load reads the old image from memory into each tile, Clear fills the tile with a value, and Don't care starts with whatever is there. Clear and Don't care read nothing. Arm's engineers describe a clear load action as free and a separate clear command as very expensive.

The store action sets the end: Store writes the finished tile to memory, Don't care lets the GPU throw it away. A depth buffer that nothing reads after the pass should never be stored. Vulkan also has a NONE option for images a pass uses without changing, core for stores since Vulkan 1.3 and for loads since 1.4. Metal's names are MTLLoadAction and MTLStoreAction.

Simplified

OpenGL ES has no explicit load and store actions. The driver guesses them from the calls the game makes, which is why mobile guides ask for glClear at the start of a frame and glInvalidateFramebuffer on images that are no longer needed. Mali and Adreno GPUs also compress the tiles they write, and Mali can skip writing a tile that did not change, so real transfers can be smaller than the arithmetic here.

4 Bandwidth is battery and heat

On a console, wasted bandwidth costs time. On a phone it costs energy as well, and energy becomes heat in a sealed case. In 2013 Arm estimated that moving one byte to or from main memory took about 150 picojoules, which makes every GB/s of traffic about 0.15 W, against a whole GPU power budget it put at about one watt. The figure is from 2013, so treat it as an order of magnitude; the point is the ratio between moving bytes and the whole budget, which is why mobile guides are written around bytes.

At that rate the careless pass above burns about 0.22 W more than the careful one, all of it heat. The Khronos Vulkan guide makes the same point in general terms. On tile-based GPUs, it says, memory bandwidth is often the most significant performance factor, and keeping data in tile memory makes an application both faster and less power-hungry.

5 Subpasses, framebuffer fetch and memoryless images

A frame has more than one pass, and the in-between images are where bandwidth goes. Deferred lighting writes a G-buffer and then reads it back, so on a tile-based GPU the goal is to do both inside one render pass, tile by tile, and never store the G-buffer at all. Every API has a way to say so.

Vulkan splits a render pass into subpasses. A later subpass reads an earlier one's output as an input attachment, at the same pixel only, and the driver can merge them into one hardware pass so the in-between images stay in tile memory. Merging is up to the driver, and VK_EXT_subpass_merge_feedback reports whether it happened. Engines that use dynamic rendering instead of render pass objects get the same effect from local reads, core in Vulkan 1.4. OpenGL ES extensions and Unity's documentation call the same ability framebuffer fetch, and Apple calls it programmable blending. A pixel shader reads the value already in the render target at its own pixel.

Images that live only inside one render pass need no main memory at all. A memoryless attachment is Metal's name for a texture that exists only in tile memory; Vulkan gets the same with transient attachments backed by lazily allocated memory. Apple's deferred lighting sample declares its whole G-buffer this way.

6 MSAA resolved on the tile

MSAA is a natural fit for tile-based GPUs. The samples of one tile fit in tile memory, so the GPU can test and blend four samples per pixel on the chip and average them as it writes the tile out. That on-tile resolve means the samples never reach main memory. In Vulkan the pass names a resolve attachment and stores the multisampled image with Don't care; in Metal the store action is multisampleResolve. A separate resolve command or a blit after the pass throws the saving away.

7 Why G-buffers and screen effects cost more

A desktop G-buffer is written in one pass and read in several. On a phone, each of those reads is a round trip unless it happens at the same pixel inside the same render pass. By Arm's numbers, a 1080p G-buffer of four 32-bit images, stored and read back, costs about 4 GB/s at 60 fps that a merged pass would not spend.

The effects that break the chain are the ones that read neighbouring pixels: SSAO, SSR, bloom, depth of field, blurs, and anything that samples the depth or colour image as a texture. When the GPU draws one tile, its neighbours are either not drawn yet or already written out, so the image has to be stored and read back for the effect. Godot's documentation names glow and depth of field as effects its Mobile renderer cannot do efficiently for this reason, and Unity's untethered guide warns that SSAO needs several passes with a high cost on tile-based GPUs.

8 Forward, Forward+ and deferred on a phone

All three rendering paths from 7.3 Forward, deferred and clustered exist on mobile, with different trade-offs. Forward rendering keeps MSAA and transparency simple and has one pass per object, so it is the default in most mobile renderers. Forward+ adds light lists for scenes with many lights. Deferred works on mobile only when the G-buffer stays on the tile, which is how Unreal's Mobile Deferred path is built.

9 Heat and the length of a session

A phone can run its chips faster than it can cool them. Android's documentation says devices can maintain high performance only for a limited time before thermal throttling lowers their clocks. What matters for a game is sustained performance: the frame it can hold for a 30-minute session, not the frame it reaches in the first five minutes.

Both mobile systems tell the game how close it is. Android's thermal headroom API returns a forecast from 0.0, no throttling, to 1.0, severe throttling, and its heuristics treat 0.85 as possible light throttling and 0.95 as moderate. It should be called no more than once every 10 seconds. iOS reports a thermal state of nominal, fair, serious or critical. A game reads these and steps quality down before the device does it for them.

10 A mobile settings checklist

Everything above reduces to a short list that a lead can hand to a team or an AI agent and check in a capture. Engines expose each item differently; section 6 lists where to find them.

4 What it costs

Worked example. Frame A draws its opaque pass into an RGBA16F colour image and a depth image, loading and storing both (49.8 MB), then runs colour grading, vignette and tone mapping as three separate full-screen passes, the last one writing the 8-bit output (91.3 MB). That is 141 MB a frame, 8.5 GB/s at 60 fps. Frame B draws the same picture as one render pass: the scene colour stays on the tile in B10G11R11, depth is cleared and discarded, the three same-pixel effects run as a last subpass, and only the 8.3 MB output is stored, 0.5 GB/s. At Arm's 2013 rate of 0.15 W per GB/s, the 8 GB/s difference is about 1.2 W of heat, more than the whole GPU budget Arm quoted then.

  • ResolutionEvery stored image grows with pixels: 1440p moves 1.8 times the bytes of 1080p. Render scale is the strongest single lever.
  • Bytes per pixelRGBA16F doubles every load and store of RGBA8; extra G-buffer layers can also force smaller tiles.
  • Passes that leave the tileEvery effect that reads neighbours, every depth or colour copy and every unmerged pass adds a full-screen write and read.
  • Frame rateBytes per frame times frames per second: the same frame at 60 fps moves twice what it moves at 30.
  • GeometryTriangle lists and vertex outputs go to memory during binning, so dense meshes, many attributes and tessellation cost more than on a console.
  • Session lengthPower turns into heat over minutes; the cost of a wasteful frame shows up as throttling a quarter of an hour later.

The usual trade

Teams set a mobile budget in two currencies: milliseconds on the slowest target phone, and a sustained frame rate after 30 minutes. A feature has to pass both. Cheap-looking full-screen effects often fail the second, and that only shows in long device tests.

5 How it breaks

Mobile frames fail in ways a desktop test never shows: they slow down with time, cost more on one GPU vendor than another, or show garbage where an image was discarded too early.

Smooth for five minutes, then slow

Cause
The frame uses more power than the phone can shed, usually from bandwidth: high resolution, HDR formats, full-screen effects. The device throttles once it heats up.
Ask for
A 30-minute run on the slowest target with frame times and thermal headroom logged, and quality steps tied to the headroom readings.

A cheap-looking effect costs milliseconds

Cause
An effect that reads neighbouring pixels, or samples the depth or colour image as a texture, splits the render pass, so the whole image is stored and reloaded.
Ask for
A capture showing the physical passes before and after, the load and store action of every image, and a same-pixel or lower-resolution version of the effect.

Garbage tiles on some phones

Cause
An image marked Don't care on store, or memoryless, that a later pass reads after all; or a pass that loads with Don't care and does not cover every pixel. The contents are undefined, so it works on one GPU and fails on another.
Ask for
A list of every image's load and store action and its readers, Vulkan validation layers on, and tests on Mali, Adreno and Apple GPUs.

MSAA is slow and memory-hungry

Cause
The multisampled image is stored and resolved by a separate command, a blit or a later pass, so four samples per pixel go out to memory and back.
Ask for
A resolve attachment or multisampleResolve in the same pass, the multisampled image memoryless or transient, and a capture that shows no resolve pass.

Slow with dense meshes

Cause
Binning writes every triangle into tile lists and every vertex output to memory. Very dense meshes, many vertex attributes, tessellation or geometry shaders make that phase the bottleneck.
Ask for
Triangle counts per frame against the mobile budget, LODs, positions in their own vertex stream, and no tessellation or geometry shaders on mobile.

Banding and flat highlights

Cause
Fewer bits per pixel for HDR: Godot's Mobile renderer uses RGB10A2 by default, and B10G11R11 has no alpha and less precision than RGBA16F, so skies band and very bright values clip.
Ask for
Dithering before output, exposure that keeps the brightest values in range, and RGBA16F only where the capture shows the bandwidth can be afforded.

7 Say it to your AI

Mobile briefs go well when they name the GPUs, the API and the session length, and ask about bytes and passes as well as milliseconds.

ReviewUse when a mobile build gets slow or hot after a few minutes
Unity 6.6, URP Forward+, Vulkan on Android. Targets: a Mali-G715 phone and an Adreno 740 phone, 60 fps, render scale 0.8, 4× MSAA.
After 12 minutes the game drops to 42 fps and the phone is hot. Attached: Render Graph Viewer export and a Snapdragon Profiler capture.

1. List every render pass with its load and store action per attachment, and mark each one that loads or stores without a later reader.
2. Mark every point where the render graph could not merge passes, with the reason it gives.
3. Estimate the bytes per frame that leave the chip at 1080p and at our render scale.
4. Propose changes ranked by bandwidth saved, and say which break MSAA, HDR or any visual feature.
5. Suggest how to use thermal headroom readings to step quality down, with thresholds.
  • Load and store actions per attachment are where most mobile bandwidth is won or lost.
  • The render graph's own merge reasons stop the AI guessing about passes.
  • Bytes per frame turns a vague heat problem into a number that changes can be measured against.
BriefUse when adding a post effect to a mobile game
Unreal Engine 5.8, mobile renderer, Android Vulkan and iOS Metal. We want a stylised colour wash and a soft edge vignette on the final image.

1. Say whether each part reads only its own pixel or its neighbours, and so whether it can stay on the tile.
2. Propose where it runs so it adds no extra store and reload of the scene colour.
3. List the formats of every image it touches and the bytes per frame at 1080p and 60 fps.
4. Explain how we confirm in a capture that no extra physical pass was added.
  • The same-pixel question decides almost the entire cost of a post effect on mobile.
  • Asking for formats and bytes makes the AI do the bandwidth arithmetic up front.
  • A capture check turns the claim into something a reviewer can verify.

Questions to ask when reviewing mobile rendering work

  1. What are the load and store actions of every image in this pass?A Load or Store with no reader is a full-screen transfer for nothing.
  2. Does anything read a neighbouring pixel, or sample depth or colour as a texture?That splits the render pass and sends the image out and back.
  3. Is MSAA resolved in the same pass, and are the samples memoryless?A separate resolve moves nine times the bytes.
  4. Was it tested for 30 minutes on the slowest phone of each GPU vendor?Heat problems only show over time, and vendors differ.
  5. What happens when thermal headroom rises?A game that does not step down is stepped down by the phone, unevenly.

8 Check yourself

  1. A pass draws the whole screen with opaque geometry. Its colour image is set to Load and its depth to Store, and nothing reads the depth later. What should they be, and what does the change save at 1080p and 60 fps?

    Show answer

    Colour should load with Clear or Don't care, since every pixel is overwritten; depth should clear and store with Don't care. That removes one colour load and one depth store, two 8.3 MB transfers: about 1.0 GB/s at 60 fps.

  2. Adding a small bloom effect to a phone game costs 3 ms and makes the phone noticeably warmer, while tone mapping cost almost nothing. Why?

    Show answer

    Bloom blurs, so it reads neighbouring pixels. The scene colour has to be stored to memory and read back, and the bloom images themselves are written and read too. Tone mapping reads only its own pixel and can run on the tile in the same pass.

  3. A game holds 60 fps in a five-minute QA test but players report 40 fps after twenty minutes. What do you ask for?

    Show answer

    A long session test on the target phones with frame times and thermal headroom or thermal state logged, the bandwidth per frame from a capture, and quality steps tied to the headroom readings so the game reduces its load before the device throttles.
