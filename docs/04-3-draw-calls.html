4.3 Draw calls, batching and instancing

Everything the GPU draws starts as a request from the CPU, and every request costs CPU time to prepare. A scene made of thousands of small objects can use up the CPU's whole frame on requests while the GPU waits. Batching and instancing get the same picture drawn with fewer, cheaper requests.

1 The picture

2 In plain words

The GPU never goes looking for work. The CPU tells it what to draw, one object at a time: this mesh, with this material, at this position. Each of those requests is a draw call. Before each one, the CPU sets up everything the draw needs, and the engine, the graphics API and the driver each spend a little time checking and recording it.

A few hundred draw calls cost almost nothing. Tens of thousands do. A forest, a city or a crowd built from separate objects can spend the CPU's whole frame on this paperwork while the GPU has little to do. Engines answer with two families of fixes. Batching groups or merges objects so there are fewer requests and less set-up between them. Instancing draws many copies of one mesh with a single request.

Everyday comparison

A print shop charges a set-up fee for every job and a small fee for every copy. Ordering 1,000 business cards as 1,000 separate jobs means 1,000 set-up fees, even though the printing is the same. Changing paper stock between jobs costs extra, because the printer has to unload one paper and load another.

Batching is grouping your orders by paper stock. Instancing is one job that says "print this card 1,000 times, with these 1,000 names".

The problem it solves

Without batching and instancing, a scene's object count would set the frame rate far more than its detail does. Artists would have to choose between dressing a scene with props and keeping the game smooth.

With them, a thousand trees can cost little more CPU time than one.

Why a lead cares

Draw calls are the most common CPU bottleneck in rendering, and content decisions set them: how many objects a level has, how many unique materials, how scenes are built. They show up as CPU time on the render thread, so a game can run slowly on a powerful graphics card. A draw call budget per platform belongs in the art and level-design guidelines, next to the triangle and texture budgets.

3 How it works

Follow the CPU as it turns a scene into commands for the GPU, then the tricks that make those commands fewer and cheaper. There are seven steps.

1 What one draw call carries

The draw itself is tiny: draw this many indices from this index buffer, starting here. Everything else is set-up the GPU needs in place first. The render state covers which shaders run, how vertices are laid out, how colours blend, whether depth is tested and which faces are skipped. Around it sit the buffers, the textures and the constants: small blocks of numbers such as the object's model matrix and the material's tint.

The CPU records all of this as commands in a command buffer. If the next object uses the same material and mesh, only its matrix needs to change. If it uses a different material, most of the set-up starts again. Modern APIs bundle most of the render state into one pre-built object, a pipeline state object, which 5.6 Shaders in practice covers.

2 Where the cost lands: CPU, then GPU

Recording a draw costs CPU time on the render thread: the engine gathers the object's data, the graphics API checks it, the driver turns it into the GPU's own commands. Explicit APIs such as DirectX 12 and Vulkan cut the driver's share and let several threads record at once, but the engine's own work per object remains. Triangles and pixels, the GPU's real work, barely affect this cost. A 12-triangle crate costs the CPU about as much to submit as a 50,000-triangle statue.

The GPU has a small cost per draw too: switching state can leave parts of it idle for a moment, and a draw of a few dozen triangles cannot keep thousands of cores busy. But the usual failure is on the CPU side. When the CPU takes longer to record the frame than the GPU takes to draw it, the GPU sits idle between commands and the frame rate is set by the CPU.

Simplified

Real engines overlap frames: while the GPU draws frame N, the CPU records frame N + 1, as 2.2 The game loop and threads describes. The picture still holds. Whichever side takes longer per frame sets the frame rate, and an idle GPU is the sign that the CPU side is the limit.

3 Sorting draws by state

The cheapest fix changes nothing about the content: draw things in a better order. Changing shader is the most expensive switch, then changing material, then changing mesh, and changing only the matrix is cheapest. So engines sort each pass's draws so that objects sharing a shader sit together, and within those, objects sharing a material. This is material sorting, also called state sorting.

A common way to do it is a sort key: one 64-bit number per draw, with the most important state in the highest bits. Sorting the numbers sorts the draws. Opaque objects are also roughly sorted front to back, so nearer surfaces hide farther ones early; transparent objects must be drawn back to front, which can force more state changes. 5.5 Depth, stencil and blending explains why.

Unity's URP and HDRP push this idea further with the SRP Batcher. It keeps every material's settings in GPU memory, uploads them only when they change, and keeps per-object data in one large buffer. Draws that use the same shader variant then need almost no set-up between them, even if their materials differ. Unity's documentation puts it plainly: the SRP Batcher reduces render-state changes between draw calls. The number of draws stays the same; each one gets cheaper.

4 Merging meshes: static and dynamic batching

Batching is the umbrella name for turning many draw requests into fewer or cheaper ones. The oldest form merges geometry. Take every object that never moves and shares a material, transform its vertices into world space, and copy them all into one big vertex buffer. That is static batching: a hundred rocks become one buffer and as little as one draw.

The price is memory and culling. A rock used a hundred times is now stored a hundred times, because each copy sits at its own place in world space. And the batch is one object as far as the renderer knows, so it cannot skip the rocks that are out of view without splitting the draw into pieces. Unity's static batching does split it, at the cost of more draws.

Dynamic batching does the same merge for moving objects, every frame, on the CPU: transform each small mesh's vertices and write them into a shared dynamic buffer. The transform work grows with vertex count, so it only pays for tiny meshes. Unity's documentation limits it to meshes under 300 vertices and notes that it often gains nothing on consoles or with modern APIs.

Teams also merge by hand. A merged mesh is several objects joined into one asset, in the modelling tool or with an engine tool, so a market stall of twenty props becomes one object with one draw per material. It suits clusters that always appear together. It goes wrong when the merged area is large: Godot's documentation warns that an entire city that is off screen will still be rendered if it is joined to a single blade of grass that is on screen.

5 Instancing: one mesh, many copies

Merging copies geometry. GPU instancing avoids the copies. The mesh stays in memory once, and one draw call asks for it to be drawn many times. Alongside it goes a buffer of per-instance data: one row per copy, usually a transform and perhaps a tint or a few custom numbers. The vertex shader runs for every vertex of every instance and uses the instance's number to read its row.

Instancing has one strict rule. Every instance uses the same mesh and the same material, so everything that differs between copies must move into the per-instance data. Four tree materials that differ only in colour can become one material with a per-instance tint. Four materials with different shaders cannot.

Try all four approaches on one forest below. Start with one draw per tree, then sort, merge and instance, and watch where the CPU time goes. Then switch on culling: separate draws and instances can skip trees outside the view, a merged mesh cannot.

6 Letting the GPU decide: indirect and GPU-driven drawing

Even instanced, the CPU still decides what to draw: it culls the scene, counts the visible instances and writes their data. In indirect drawing, the draw call's own numbers, how many indices and how many instances, are read from a buffer in GPU memory instead of being supplied by the CPU. Microsoft's Direct3D 12 documentation describes it as moving some scene traversal and culling from the CPU to the GPU.

That opens the door to GPU-driven rendering. The whole scene's object data lives in GPU memory. Each frame a compute shader tests every instance against the view, using the techniques of 4.4 Culling, and writes the survivors and the draw arguments itself. A handful of indirect draws then consume them. The CPU's work no longer grows with the number of objects. Ubisoft's renderer for Assassin's Creed Unity used this approach and reported one to two orders of magnitude fewer draw calls with about ten times the objects of the previous game.

Code What a draw's arguments look like when the GPU writes them

In Direct3D 12, an ordinary instanced draw takes five numbers from the CPU. An indirect draw reads the same five numbers from a buffer, one record per draw, which a compute shader can fill. Vulkan and Metal have equivalents.

// A direct draw: the CPU supplies the numbers.
cmdList->DrawIndexedInstanced(6000, 1000, 0, 0, 0);
//                  indices per instance, instances, first index, base vertex, first instance

// An indirect draw: the same five numbers live in GPU memory,
// one record per draw (D3D12_DRAW_INDEXED_ARGUMENTS).
struct DrawArgs { UINT IndexCountPerInstance, InstanceCount,
                   StartIndexLocation; INT BaseVertexLocation;
                   UINT StartInstanceLocation; };

// A culling compute shader writes DrawArgs records and a count;
// the GPU then runs as many draws as it wrote.
cmdList->ExecuteIndirect(signature, maxDraws, argsBuffer, 0, countBuffer, 0);

When reviewing code like this, check who writes the count buffer, what happens when the GPU writes more draws than the maximum, and whether the argument buffer is cleared or rewritten every frame.

4 What it costs

Take this chapter's illustrative model: 5 µs of CPU time to record a draw and 15 µs more to change material. A level with 1,000 draws, sorted so that material changes are rare, spends about 5 ms on the render thread just recording them. That is 30% of a 16.7 ms frame at 60 fps, 36% of a 13.9 ms frame on a 72 Hz headset and 60% of an 8.3 ms frame at 120 fps. The render thread has other work too, so the real ceiling is lower.

Draws multiply with passes. An object drawn into a depth pre-pass, four shadow cascades and the main pass costs six draws. Adrian Courrèges's breakdown of one GTA V frame on PC shows how the total builds up.

Draw call budgets by platform

A draw call budget is the number of draw calls per frame a project allows on each platform, set from what that platform's CPU can record within the frame. Published figures are rare and always come with conditions, because the real limit depends on the engine, the graphics API, the state changes and what else the CPU is doing.   • Passes per objectEvery pass that draws an object adds its draws again: depth pre-pass, each shadow cascade, the main pass, reflection captures.
  • Unique materialsEach one splits batches and adds state changes. A material copied per object, often by a script, can multiply draws overnight.
  • Shader variantsA different variant of the same shader still breaks a batch. Unity notes that SRP batches with few draws in each often mean too many shader variants.
  • Extra viewsSplit screen, the second eye in VR, reflection probes and security-camera screens each draw the scene again.
  • Small propsEvery separate object counts, however few triangles it has. A pebble costs the CPU as much as a statue.

In proportion

Draw calls cost CPU time, and only matter when the CPU is the limit. If the GPU is the slower side, halving draws changes nothing on screen. Check which side overruns the frame budget before spending artist time on merging and instancing; 11.1 Frame budgets shows how.

5 How it breaks

Draw call problems look like performance problems first, and occasionally like visual ones. These are the usual patterns.

Slow even on a fast graphics card

Cause
Too many draw calls or state changes. The render thread takes longer than the GPU, which waits between commands. Frame rate barely changes with resolution.
Ask for
Render thread and GPU times side by side, the draw count per pass, and the top meshes and materials by draws, before any fix is chosen.

Draw calls jump after a small change

Cause
Objects that shared a material now each have their own copy, so they no longer batch or instance. In Unity, reading Renderer.material in a script clones a shared material for that object.
Ask for
A before-and-after frame capture with the reasons batches break, and a search for per-object material copies, material property overrides and new shader variants in the change.

Every copy in the same place

Cause
The shader ignores the per-instance data, so every instance uses the same transform or the same tint. It happens when a custom shader lacks instancing support or the instance buffer is not bound.
Ask for
A frame capture showing the draw's instance count and the instance buffer's contents, and a check that the shader reads its row by instance number.

Memory jumps after batching

Cause
Static batching or merging stored a world-space copy of a mesh for every placement. Repeated props, rocks and foliage are the worst cases.
Ask for
Instancing for meshes that repeat, batching only for unique static geometry, and the memory before and after in a build on the target platform.

Fast in one direction, slow in another

Cause
A merged mesh or an instanced group spans a large area, so it is drawn whole whenever any corner is in view. Wrong bounds on a group can also make all of it vanish or pop at once.
Ask for
Merges and instance groups split by area, sized so each is mostly in or out of view, and the bounds checked in the engine's culling debug view.

To see draw calls directly, step through a frame with the engine's frame debugger or a frame capture tool such as RenderDoc or PIX. Each lists every draw, its state and its instance count.

Unity caveat

In URP and HDRP, a MaterialPropertyBlock on a renderer makes it incompatible with the SRP Batcher and keeps it out of the GPU Resident Drawer. Unity's guidance is to avoid the API in those pipelines and use Material Variants for objects that need different settings.

7 Say it to your AI

Good briefs about draw calls state the platform's budget, the current count per pass and which thread is over budget, and ask for the memory and culling cost of every fix. Adapt these.

Questions to ask when reviewing work on draw calls

  1. How many draw calls does this add per frame, in which passes, on our weakest platform?One visible object is often several draws: depth, each shadow cascade, the main pass.
  2. Does this create a unique material or material instance per object?Unique materials split batches and multiply state changes.
  3. If meshes are merged, what does it cost in memory, and how is the result culled and streamed?A merged mesh is drawn, culled and loaded as one piece.
  4. If instancing is used, where do the differences between copies live, and what bounds are used for culling?Wrong bounds make whole groups pop, vanish or never cull.
  5. Was the gain measured on the target device, with render thread and GPU time both reported?Fewer draws only help a CPU-bound frame, and the editor adds overhead of its own.

8 Check yourself

  1. A level has 2,000 copies of one rock mesh with one material. Static batching and instancing would both cut it to one or two draws. Why is instancing usually the better choice?

    Show answer

    Static batching stores a world-space copy of the rock for every placement, so roughly 2,000 times the mesh memory, and the batch culls coarsely. Instancing stores the mesh once plus a small row of data per rock, and can skip rocks outside the view.

  2. An optimisation cut draw calls from 3,000 to 300, and the frame rate did not change. What does that tell you?

    Show answer

    The frame was limited by the GPU, or became limited by it. Draw calls cost CPU time, so cutting them only speeds up a frame whose render thread is the slower side. Check render thread and GPU times before and after.

  3. A thousand trees share one mesh but use four materials that differ only in colour. Why can't they be one instanced draw as they are, and what would make it possible?

    Show answer

    One instanced draw uses one mesh and one material. Replace the four materials with one that reads a tint from per-instance data, and give each tree its colour there.
