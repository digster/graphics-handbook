5.2 Vertex shaders

The vertex shader is the program the GPU runs once for every corner of every mesh it draws. Its one required job is to say where that corner lands on screen. Along the way it can bend, wave and deform the mesh, and it hands the pixel shader the values it will need.

1 The picture

2 In plain words

A vertex shader is a short program that the GPU runs once for each vertex it draws. Each run is handed one vertex, a row of the vertex buffer, plus a few values shared by the whole draw, such as where the object is and where the camera is. It must work out where that corner lands on screen. It may also pass along extra values for the pixel shader, and it may move the corner first.

Each run sees only its own vertex. It cannot look at its neighbours, create new vertices or delete any. That isolation is what lets the GPU run thousands of them at once.

Everyday comparison

A stadium wave. Every spectator follows the same card: stand up when the wave reaches your seat number. Nobody sees the whole wave or talks to their neighbours, yet a ripple runs round the stadium.

Each spectator is a vertex, the seat number is its own data, the card is the shader, and the clock everyone shares is a constant.

The problem it solves

Every frame, millions of corners must be moved from where the artist built them to where they appear on screen. Doing that on the CPU would take all its time. On the GPU it is spread over thousands of lanes.

The same machinery makes movement cheap: grass, trees, flags and water can sway with no animation data and no CPU work at all.

Why a lead cares

Vertex shaders are how most worlds feel alive on a budget: wind in foliage, ripples on water, breathing on cloth. That movement exists only in the image. Physics, culling and some shadow systems never see it unless someone handles it, which is behind a family of bugs every open-world team meets. And the cost scales with vertex counts multiplied by every pass that draws them, shadows included.

3 How it works

Seven steps: what a vertex shader is given, the one job it must do, the values it hands on, and the four ways games use it to change shapes.

1 What goes in and what comes out

The input assembler hands each run one vertex: its position and whatever other vertex attributes the mesh carries. Values that are the same for the whole draw, such as matrices and the time, arrive as constants. A vertex shader can also read textures, for example a height map or a wind noise pattern.

Out comes exactly one vertex. It must include a position in clip space, the four numbers x, y, z, w that the GPU needs to place the corner on screen (3.4 Spaces and transforms). Direct3D's documentation says the vertex shader stage must always be active, even if all it does is pass data through.

2 The transform, vertex by vertex

The required job is the chain of spaces from 3.4, applied to each vertex. Its position starts in object space, where the artist built it. The model matrix puts it in the world, the view matrix moves the world so the camera sits at the origin, and the projection matrix squeezes the camera's view into clip space. Engines usually multiply the three into one MVP matrix per object, so the position needs a single multiply.

That is where the shader's work ends. The GPU then divides by w and maps the result to pixels on its own, in the fixed stages after the shader. Follow one corner of an object through, with real numbers:

Simplified

Normals need their own matrix when an object is scaled unevenly, and large open worlds keep positions relative to the camera to avoid running out of precision far from the origin. Godot's documentation, for example, recommends its combined model-view matrix over separate ones for precision with distant objects. The chain is the same in every case.

3 Interpolators: handing values to the pixel shader

Everything a vertex shader outputs besides the position is an interpolator: a value given at each corner, which the rasterizer blends for every pixel inside the triangle. A pixel near one corner gets mostly that corner's value; a pixel in the middle gets a mix. UVs, normals and world positions all reach the pixel shader this way. HLSL calls the output structure's fields by semantics such as TEXCOORD0; GLSL and Godot call them varyings.

The blend is linear across the triangle. So anything the vertex shader computes is only correct between corners if it changes in straight lines there. Multiplying and adding are fine; a sine wave, a square or a length() is not. Unreal's documentation of Customized UVs, its way of moving material maths into the vertex shader, gives exactly this warning.

Interpolators are not free. Each one is stored for every vertex and blended for every pixel, and on the tile-based GPUs in phones, every visible vertex's outputs are written to memory and read back. Arm's guidance is to send as few as possible and to use 16-bit precision where it holds up.

4 Moving vertices: wind, flags and water

Because the shader runs every frame, it can move vertices before transforming them. This is vertex animation, and it is how most games make foliage sway, flags ripple and water swell, with no animation data and no CPU cost per object.

The trick is in the masks. A tree's trunk must stay planted while its branch tips move most, so artists paint a weight into each vertex, usually in its vertex colour channels, and the shader scales the movement by it. Crysis stored separate channels for edge stiffness, a per-leaf phase and overall leaf stiffness. A phase taken from each tree's world position keeps neighbours from swaying in step. Unreal ships the same idea as the SimpleGrassWind material function, which takes a wind intensity, a weight map and a speed.

Code The flag's vertex shader in 15 lines of HLSL

This is a minimal version of the shader behind the picture at the top of the chapter, written in plain HLSL rather than any one engine's dialect. Engines generate the same shape from a material graph. It leaves out one thing the picture includes, on purpose.

cbuffer PerDraw                         // constants: the same for every vertex in this draw
{
    float4x4 ModelToWorld;              // the model matrix
    float4x4 WorldToClip;               // view and projection, combined
    float    Time;                      // seconds, set by the CPU every frame
};
struct VertexIn  { float3 pos : POSITION; float3 normal : NORMAL; float2 uv : TEXCOORD0; };
struct VertexOut { float4 clipPos : SV_Position; float3 normalWS : NORMAL; float2 uv : TEXCOORD0; };

VertexOut main(VertexIn v)              // runs once per vertex: 117 times for the flag
{
    float3 p = v.pos;
    p.z += 0.16 * v.uv.x * sin(7.0 * p.x - 3.0 * Time + 1.2 * p.y);  // the wave; uv.x is 0 at the pole
    VertexOut o;
    o.clipPos  = mul(WorldToClip, mul(ModelToWorld, float4(p, 1.0)));  // the one required output
    o.normalWS = mul((float3x3)ModelToWorld, v.normal);              // still the flat normal: a bug, see below
    o.uv       = v.uv;                                                // passed on as an interpolator
    return o;
}

Three things to check in code like this. The normal is the one from the buffer, so the rippled flag would be lit as if it were flat; a fix computes the slope of the wave and tilts the normal to match. A shadow pass needs the same wave, or the shadow stays flat. And the flag's bounds must allow for the 0.16 m it can move, or it will be culled early. Section 5 shows all three going wrong.

5 Skinning in the vertex shader

Characters bend at their joints by GPU skinning. Each vertex stores up to four bone numbers and weights (4.2), the constants hold every bone's current transform, and the shader moves the vertex by each of its bones and blends the results by weight. A vertex near the elbow, weighted 30% to the upper arm and 70% to the forearm, ends up between where each bone alone would put it.

Done in the vertex shader, skinning is repeated by every pass that draws the character: depth, shadows, the main pass, motion vectors. Engines therefore often skin once per frame in a compute shader, write the bent vertices to a buffer, and let every pass read that with a plain vertex shader. Unity does this by default; Unreal does it when its Skin Cache is on.

6 Displacement: real bumps from a texture

Displacement reads a height from a texture at each vertex's UV and pushes the vertex out along its normal by that much. Unlike a normal map, which only changes the lighting (6.4), displacement changes the real shape: silhouettes, shadows and intersections all show it.

The catch is that only vertices move. The texture's detail survives only where there are vertices to carry it, so displacement needs dense meshes, or a way to add vertices on the fly. Unreal's Nanite Tessellation does that for Nanite meshes, as programmable displacement at runtime.

7 What the rest of the engine does not see

A vertex shader changes only the picture. The moved positions exist only in the GPU, for the length of one draw, and are thrown away afterwards. Every other system still works from the mesh as stored:

  • Physics collides with the collision shape built from the undeformed mesh, or a simpler one. A waving flag or a swelling wave is not where the physics engine thinks it is.
  • Culling tests each object's bounding box, computed from the stored mesh. Move vertices outside it and the object can be culled while part of it is still on screen.
  • Shadows are drawn by a separate pass with its own vertex shader. If that pass does not apply the same movement, the shadow stays still. Baked shadows never move at all, and cached shadows must be redrawn when anything moves.
  • Motion vectors, which temporal anti-aliasing uses, need to know where each vertex was in the previous frame, so the shader must also compute last frame's movement.

4 What it costs

A vertex shader's bill is runs times cost per run, and runs are vertices times passes. Take a tree of 12,000 vertices at its current level of detail, drawn in a depth pre-pass, four shadow cascades, the main pass and a motion vector pass:

The arithmetic of wind itself is cheap. Suppose wind adds 30 instructions to each run: 33.6 million runs × 30 = about 1 billion instructions per frame. An RTX 5070 has 6,144 lanes at up to 2.51 GHz, about 15.4 trillion simple instructions a second, so that is 0.07 ms at best. Real shaders wait on memory and rarely reach the best case, but vertex maths is seldom what breaks a budget.

The real bills are indirect. In Unreal, any material with World Position Offset invalidates its cached virtual shadow map pages every frame, so moving foliage is redrawn into the shadow map constantly. Moving objects need a motion vector pass. Bounds expanded for movement cull less. And dense meshes for displacement multiply every pass.

What makes it grow

  • Vertex countThe main driver. Level of detail is the main control.
  • PassesDepth, every shadow cascade, the main pass and motion vectors each run the shader again.
  • Skinning in the vertex shaderUp to four matrix blends per vertex, repeated in every pass, unless the engine skins once in compute.
  • Texture readsDisplacement and wind noise read memory per vertex; memory waits cost more than arithmetic.
  • InterpolatorsStored per vertex and blended per pixel; on phones, written to memory and read back.
  • Cache invalidationMoving vertices can force cached shadows and other cached results to be redrawn every frame.

5 How it breaks

Most vertex shader bugs come from the gap in step 7, where the image moved and something else did not.

Foliage pops out at the screen edge

Cause
The bounding box still fits the mesh as stored, so when wind leans it outside, the object is culled while part of it is still visible.
Ask for
Bounds expanded by the largest offset the shader can produce: Unreal's Max World Position Offset Displacement, Unity's Renderer.localBounds, Godot's extra_cull_margin.

The shadow does not sway with the tree

Cause
The shadow pass runs a vertex shader without the offset: a hand-written shader that borrows a stock shadow pass, baked lighting, or a shadow cache told not to update.
Ask for
The same displacement in the shadow, depth and motion vector passes, and a decision on cached shadows, such as Unreal's Shadow Cache Invalidation Behavior.

Waves that look flat

Cause
The shader moves positions but passes on the normals from the buffer, so lighting still sees a flat surface. The silhouette waves; the shading does not.
Ask for
Normals recomputed from the slope of the displacement in the same shader, checked in a normals debug view.

Smearing on swaying foliage

Cause
Motion vectors are computed without the movement, so temporal anti-aliasing blends each leaf with the wrong history.
Ask for
Motion vectors that include the vertex offset, by evaluating the offset at last frame's time as well, and a check in the engine's motion vector view.

Wind stutters after a long session

Cause
Time is passed as a 32-bit float. After 36.4 hours, 131,072 seconds, it can only step in 1/64 s, about one frame at 60 fps, so movement turns jerky. Wrapping time avoids that, but any wave whose period does not divide the wrap jumps when it happens; Godot wraps TIME every 3,600 s by default.
Ask for
Time wrapped on the CPU at a period every wave in the shader repeats on, or phase passed in instead of raw time.

A frame capture tool shows each pass's vertex shader output as a mesh, which is the fastest way to see which pass is missing the movement.

6 In the engines

No engine asks you to write the transform yourself; it is generated from the material. What you add is movement, extra interpolators and the settings that keep the rest of the engine in step.

Borrowed shadow passes

A hand-written shader often reuses another shader's shadow pass to save effort. That pass runs its own vertex shader, without your offset, so the shadow is cast by the mesh as stored. Whatever the tool, confirm in a frame capture that the shadow pass moves too.

7 Say it to your AI

Vertex shader briefs go wrong when they ask for the look and forget the rest of the engine. Name the passes, the bounds and the budget in the brief.

BriefUse when adding wind or other vertex animation
Engine: Unity 6.6, URP, Shader Graph. Platforms: PC and PlayStation 5, 60 fps.
Add wind to our 40 tree and bush meshes. Artists have painted vertex colour: red is how much each vertex bends (0 at the trunk base), green is a per-leaf phase.

Requirements:
1. Main bend from a global wind direction and strength, plus a smaller leaf flutter. Neighbouring trees must not move in step: take phase from world position.
2. Recompute normals so lighting follows the bend.
3. The same movement in the shadow, depth and motion vector passes.
4. Bounds expanded by the largest offset the shader can produce, and tell us that number.
5. Time wrapped so the wind does not stutter or jump in long sessions.

  • Items 2 to 5 are the four classic bugs, asked for up front.
  • Asking for vertex counts across passes makes the real cost visible.
Bug reportUse when moving geometry vanishes or its shadow misbehaves
Unreal Engine 5.9, Nanite foliage with World Position Offset wind. Two problems since we raised wind strength:
- Tree tops disappear near the edges of the screen during strong gusts.
- Shadows of distant trees stop swaying, while near trees are fine.

Explain the cause of each with reference to the material's Max World Position Offset Displacement, the bounds, and World Position Offset Disable Distance. Propose settings, the visual and performance cost of each, and how to confirm the fix.
  • Edge-of-screen popping points at bounds; distance-dependent shadows point at a disable distance.
  • Naming the settings keeps the answer inside the engine's existing settings.
  • Asking for costs stops a fix that simply turns culling off.

Questions to ask when reviewing vertex shader work

  1. Which passes run this vertex shader, and do they all apply the same movement?A pass that skips it gives still shadows or smeared motion.
  2. What is the largest offset it can produce, and are the bounds expanded by it?Otherwise objects are culled while partly visible.
  3. Are normals updated where positions move?Moved positions with old normals light as if nothing moved.
  4. Is anything here non-linear and passed on as an interpolator?Curved maths blended linearly across large triangles comes out wrong.
  5. Could this work be done once per draw on the CPU, or once per frame in compute, instead of per vertex per pass?Per-vertex work is multiplied by vertex count and by every pass.

8 Check yourself

  1. A rock of 10,000 vertices is drawn in a depth pre-pass, three shadow cascades and the main pass. A change adds 40 instructions to its vertex shader. How many extra instructions per frame?

    Show answer

    10,000 vertices × 5 passes × 40 instructions = 2 million instructions per frame for that rock.

  2. A swaying flag's shadow stays perfectly still. The flag uses a hand-written shader. What do you check first?

    Show answer

    The shadow caster pass. It runs its own vertex shader, and if it does not apply the same wave, for example because it was borrowed from a stock shader, the shadow is drawn from the mesh as stored.

  3. Why can't a 4-vertex quad show a fine stripe pattern computed with sin() in its vertex shader?

    Show answer

    The vertex shader runs only at the 4 corners, and interpolators blend linearly between them, so the curve between corners is lost. The pattern must be computed in the pixel shader, or the mesh must have enough vertices to follow it.
