2.1 Anatomy of an engine

An engine is a stack of systems, each owning one job: drawing, simulating, animating, playing sound, loading content. Knowing where each one sits tells you who should change it, what a change can break, and which parts end up in the game players install.

1 The picture

2 In plain words

Every game needs the same plumbing. It must open a window, read a controller, load files, draw thousands of objects many times a second, make things fall and collide, play sounds and move characters. A game engine is that plumbing, written once and reused across many games, plus the tools to make content for it.

Inside, the engine is split into systems that each own one job. The renderer turns the game world into an image every frame. Other systems simulate physics, pose animated characters and mix sound. Gameplay code sits on top and tells them what to do. The systems sit on a thin layer that talks to the operating system and the graphics hardware for them.

There are two halves to every engine. The runtime is the part that runs the game and ships to players. The editor is the application your team uses to build levels, import art and test. It contains the runtime, but the runtime does not contain it.

Everyday comparison

Think of a theatre. The stage machinery, lighting rig and sound desk are the engine systems. The script and the actors are the gameplay code. The building's wiring and plumbing are the platform layer that everything plugs into.

The workshop where sets are built and painted is the editor. The audience never sees it, but nothing reaches the stage without it.

The problem it solves

Without an engine, every team would rebuild windowing, file loading, rendering, physics and audio before making anything players can see, and rebuild them again for every platform.

Splitting that work into layers with clear jobs lets specialists own each one, lets most of the team work high up the stack, and lets the same game run on very different hardware.

Why a lead cares

Most scope, risk and hiring questions map onto these layers. A change high in the stack, such as a script or a level, touches one feature. A change low in the stack, such as the renderer's internals or the RHI, touches every frame on every platform and needs a specialist to review it. When someone, or an AI, proposes a change, the first question to ask is which layer it touches.

3 How it works

Walk through the stack from the top, follow one event down through it, then open the renderer and the layers beneath it. Six steps.

1 The layers, top to bottom

At the top is your game: levels, characters, rules and the code that ties them together. Most of that code is written in the scripting layer, a language chosen so that gameplay programmers and designers can work quickly: Blueprints in Unreal, C# in Unity, GDScript in Godot. It calls into a gameplay framework, the engine's model of a world full of objects with components, which 2.3 Scenes, objects and components covers.

Below that are the engine systems. Besides the renderer there is a physics engine that moves bodies and resolves collisions, an animation system that poses skeletons and blends motions, and an audio engine that mixes sounds and places them in 3D. Most engines also have systems for input, UI and networking.

Under the systems are shared services. The core provides memory, maths, logging and a way to spread work across CPU cores. The asset system finds, loads and unloads content, so the renderer can ask for "the rock mesh" without knowing which file or package it lives in. At the bottom, the platform layer wraps each operating system's way of opening windows, reading controllers, reading files, keeping time and starting threads.

Calls flow downward. A grenade script does not open an audio device; it asks the audio engine to play a sound, which asks the platform layer to hand samples to the operating system. Follow one event and you meet most of the stack.

2 The runtime and the editor

The editor is a large application built on top of the runtime. Its viewport draws your level with the same renderer the game uses. Its play button runs the game inside the editor. Around that it adds everything needed to make content: importers that turn source files from tools such as Blender or Photoshop into engine assets, material and animation editors, profilers and the build tools.

None of that ships. When you build the game, the engine cooks the content into formats the target platform reads quickly, compiles your code for that platform, and leaves the editor's code and the source files behind. 1.3 The content pipeline covers the cooking step in detail. Engines enforce the split in code: Unreal marks each code module as Runtime or Editor, Unity keeps scripts in folders named Editor out of player builds, and Godot exports games with a separate engine binary that has no editor in it.

3 Inside the renderer

The renderer does four things every frame. It keeps its own representation of the scene: for every drawable object, which mesh and material it uses and where it is, plus the lights and the camera. It works out visibility, throwing away objects outside the camera's view or hidden behind others. It organises the survivors into render passes, such as shadows, the main pass and post-processing. Finally it turns each pass into commands for the GPU, mostly draw calls, and hands them to the layer below.

Simplified

Real renderers have more stages than four: choosing a level of detail per object, sorting draws, uploading per-frame data, and often a frame graph that schedules the passes automatically. The four boxes are the shape they all share.

4 The RHI and the platform layer

A PC game may run on DirectX 12 or Vulkan, a Mac or iPhone build uses Metal, and each console has its own graphics API. These APIs do the same jobs with different names, rules and quirks. 3.5 CPU, GPU and graphics APIs explains what they are. Writing the renderer once for each would multiply the work.

So engines put an adapter in between. The RHI, Unreal's name for its render hardware interface, gives the renderer one set of commands: create a buffer, set up a pipeline, draw, submit. Each platform has a backend that translates those commands into its own API. Godot calls the same layer RenderingDevice. Unity does not expose its layer by name, but you see it in Player settings, where each platform has a list of graphics APIs to choose from.

The platform layer is the same idea for everything else: one interface for windows, controllers, files, clocks and threads, with a backend per operating system. Together these two adapters are why one project can build for Windows, consoles and phones.

5 Modules and plugins

Engines are built from modules: separately compiled units such as the renderer, the audio engine or the UI system, each with a list of the modules it depends on. A build includes only the modules it needs, which is how editor modules stay out of the game.

A plugin uses the same mechanism to add a feature without touching the engine's own code. Audio middleware, online services, platform SDKs and a studio's in-house tools usually arrive as plugins. A plugin often has a runtime part that ships with the game and an editor part that adds tools and settings. Turning a plugin off removes it cleanly, and upgrading the engine leaves it alone unless the interfaces it uses have changed.

6 Where change is cheap and where it is risky

The higher a change sits in the stack, the less it can break. A gameplay script affects one feature. An editor tool affects how the team works, but never ships. A change to the renderer's internals runs every frame for every player; a change to the RHI or platform layer runs on every platform, in every game built on your copy of the engine.

This is also the map for AI-written code. Gameplay scripts, editor tools, import scripts and material shaders are well-bounded tasks an AI can do and a reviewer can check by playing the game. Threading, memory management, the RHI and the platform layer fail in ways that only show up under load, on one platform or once a week, and need an engine programmer to lead.

4 What it costs

The big cost decision is how much of the engine you own. There are three broad options. You can use an off-the-shelf engine as it comes, take a licensed engine's source and change it, or build your own. Each moves cost from licence fees and limits into people and time.

Here is how the upgrade cost adds up. Say your team has changed 50 files in the engine's renderer and you take two engine releases a year. If merging and retesting those changes takes one engine programmer three weeks per release, that is six weeks a year spent standing still. Move half of those changes into a plugin that uses the engine's public interfaces and that time roughly halves, because the plugin only breaks when those interfaces change.

What makes the cost grow

  • Engine changesEach modified engine file is a possible conflict at every upgrade. Keep a list of them, with the reason for each.
  • PlatformsEach new platform needs a platform-layer backend, an RHI backend, testing and certification.
  • Third-party pluginsEvery plugin must be updated for each engine release, by you or by its vendor, before you can upgrade.
  • In-house toolsEditor tools are code too. They need owners, and they break when the editor's interfaces change.

The licence question

Engine licences differ in what they charge and what source you get. Unreal gives you the full C++ source and takes a royalty on a game's revenue once it passes US$1 million. Unity's engine source needs an Enterprise plan, and only its Source Code Adapt option lets you ship a modified engine. Godot is MIT-licensed: free, with full source, as long as you include its licence text. Read the current terms before deciding; they change.

5 How it breaks

Engine-structure problems rarely look like graphics bugs. They show up as builds that differ from the editor, platforms that disagree and upgrades that stall.

Works in the editor, broken in the build

Cause
Code or content that only exists in the editor: editor-only code called from game code, or an asset loaded by name that the cook never included.
Ask for
A packaged build tested automatically on every change, and a search for game code that references editor-only modules or loads assets by path.

Fine on one platform, wrong on another

Cause
A difference between RHI backends or drivers, or code that bypassed the RHI and relies on one graphics API's behaviour.
Ask for
Captures from both platforms of the same frame, a check for platform-specific code paths, and every target graphics API in automated tests.

An engine upgrade stalls the project

Cause
Local changes to engine source conflict with the new release, or a plugin has not been updated for it.
Ask for
A list of every engine modification and plugin with its version, and the upgrade done on a branch with automated tests before anyone else moves.

Systems out of step

Cause
Two systems write the same object in the wrong order, for example animation posing a character after physics has moved it, so feet slide or ragdolls pop.
Ask for
The order in which each system updates that object every frame, and which system owns its position.

A bloated build

Cause
Plugins and modules left enabled that the game does not use, or test content referenced from something that ships, so the cook pulls it in.
Ask for
A size report per module and per asset folder for the packaged build, and a review of every enabled plugin.

For performance problems, the layer map is also the first step of profiling. Every engine's profiler groups time by system, so the question becomes "which box is slow?" before anyone opens the code. 2.2 The game loop and threads shows how those boxes share each frame.

7 Say it to your AI

Good briefs about engine work say which layer the change belongs in, and which layers it must not touch. Without that, an AI will often reach for the engine's internals because that is where the most direct fix is. Adapt these.

BriefUse when adding a gameplay feature
Engine: Unreal Engine 5.9, Blueprint and C++ project, shipping on PC and PlayStation 5.
Feature: a grenade that damages objects within 5 m, knocks back physics bodies, plays a sound and spawns a smoke effect.

Constraints:
- Implement it in game code and Blueprints only. Do not modify engine source.
- Use existing engine systems through their public interfaces: physics, audio, Niagara for effects.
- Keep any editor-only helpers in an Editor module.

Deliver: the classes or Blueprints you add, which engine systems each one calls, and how we test it in a packaged build, not only in the editor.
  • Naming the layer and forbidding engine changes keeps the fix where it is cheap.
  • Listing the systems it calls gives the reviewer a map to check against.
  • Asking for a packaged-build test catches editor-only dependencies.
DecisionUse when someone proposes changing the engine
We use Unity 6.6 with URP on PC and Android. A programmer proposes editing the engine package to change how shadows are culled, to fix a performance problem in our forest levels.

1. Which layers and which modules or packages would this change touch?
2. Can the same result be reached without editing the engine: a project setting, a custom render pass, a renderer feature, or a change to our content?
3. If we do edit it, what will each Unity upgrade cost us, and how would we carry the change forward?
4. What could break on Android that would not show up on PC?
  • Asking for alternatives first often finds a plugin-level or content-level fix.
  • Upgrade cost is the hidden price of engine changes; make it explicit.
  • Low layers affect every platform, so ask about the one you are not testing.

Questions to ask when reviewing engine-level work

  1. Which layer does this change live in, and does it reach into a lower one?The deepest layer touched sets the risk and who must review it.
  2. Does any of this modify the engine's own source? How will we carry it through upgrades?Every engine change is a merge on every future upgrade.
  3. What part of this runs in the shipped game, and what only in the editor?Editor-only code called from game code works in the editor and fails in the build.
  4. Does it call a graphics API or an operating system function directly, instead of going through the RHI or platform layer?Direct calls work on one platform and break or fail to compile on the others.
  5. Has it been tested on every platform and graphics API we ship?Bugs in low layers often appear on one backend only.

8 Check yourself

  1. A tool that checks level names when an artist saves a map works perfectly. The game build fails because it cannot find one of the tool's classes. What went wrong?

    Show answer

    Game code references code that lives in the editor half of the engine. Editor code is stripped from builds. The tool belongs in an editor module or Editor folder, and nothing in the game should depend on it.

  2. Your game renders correctly with DirectX 12 but shows corrupted shadows with Vulkan. Which layer do you suspect first?

    Show answer

    The RHI backend for Vulkan, or the driver beneath it, or code that bypassed the RHI and assumed DirectX behaviour. The renderer above the RHI is the same code on both, so a difference between them points below it.

  3. A programmer wants to fix a performance problem by editing the engine's renderer source. Name two questions you ask before agreeing.

    Show answer

    Can it be done without changing the engine, through a setting, a plugin, a custom pass or content? And what will it cost to carry this change through every engine upgrade, and who owns that? Also useful: which platforms does it affect, and how will we test them?
