4.2 Vertex buffers and index buffers

A mesh reaches the GPU as two plain lists of numbers: one row for every corner, and a list of which corners make each triangle. How those lists are laid out decides how much memory a mesh takes and how quickly the GPU can read it.

1 The picture

2 In plain words

In an artist's tool, a model is a rich file full of names, groups, edit history and settings. The GPU wants none of that. It wants a flat block of numbers in its own memory, arranged so that thousands of small cores can each grab the data they need without asking anyone.

A vertex buffer is that block. Think of a spreadsheet with one row for every corner of the mesh. Every row has the same columns: where the corner is, which way the surface faces there, and which point of the texture lands on it. An index buffer is a second, much shorter list. It says which three rows make each triangle.

Everyday comparison

Your phone stores each contact once, with their number, photo and address. A group chat does not copy those details. It lists who is in it. A friend who is in five group chats is still stored once.

The vertex buffer is the contact list. Each triangle is a group chat of exactly three, and the index buffer is the list of members.

The problem it solves

Without an index buffer, every triangle carries its own copy of its three corners. On a typical smooth mesh each corner touches about six triangles, so it would be stored five or six times, and the GPU would process it five or six times.

Indexing stores each corner once and lets the GPU reuse the work it already did for it.

Why a lead cares

Vertex data is usually smaller than texture data, but it is read again in every pass that draws the mesh, every frame. Layout choices appear as import settings in every engine and in any rendering code an AI writes for you. And when a buffer and the code reading it disagree, you get some of the most dramatic bugs in graphics: meshes that explode into spikes.

3 How it works

Follow one mesh from its file to the moment the GPU draws it. There are seven steps.

1 What one vertex holds

A vertex is a corner plus everything the renderer needs to know about the surface at that corner. Each separate piece of data is a vertex attribute. Position is the only one every mesh needs. The rest depend on how the mesh is shaded and animated.

AttributeWhat it tells the rendererUsed by
PositionWhere the corner sits, relative to the model's own origin.Every pass that draws the mesh
NormalWhich way the surface faces at this corner. See normal.Lighting
TangentWhich way the texture's horizontal axis runs across the surface. See tangent.Normal maps
UVWhich point of a 2D texture lands on this corner. See UV coordinates. A second set often holds lightmap coordinates.Texturing, baked lighting
ColourA tint or mask painted onto the corners, often used to blend materials.Material blending, wind, effects
Bone indices and weightsWhich bones of a skeleton move this corner, and how much each one pulls.Animated characters

2 Rows, stride and offsets

In memory there are no rows or columns, only bytes one after another. Two numbers turn them back into a table. The stride is the size of one row: how many bytes to skip to get from one vertex to the next. The offset is where an attribute starts inside a row.

The code that draws the mesh hands the GPU a vertex layout: the list of attributes, each with its format and offset, plus the stride. It works like a decoder ring. Nothing in the buffer itself says where the normal is. If the layout says the wrong thing, the GPU reads the wrong bytes and has no way to know.

Maths The two formulas behind every number in this chapter

Where an attribute lives:

address = buffer start + vertex number × stride + attribute offset

How much memory a mesh takes:

vertex buffer = vertex count × stride

index buffer = triangle count × 3 × bytes per index

Stride is the sum of the attribute sizes, sometimes rounded up so each row starts on a 4-byte boundary. A float32 is 4 bytes and a float16 is 2.

3 One buffer or several streams

There are two common ways to arrange the rows. In an interleaved layout, each vertex's attributes sit side by side, then the next vertex follows. Alternatively the mesh can be split into several vertex streams, separate buffers that each hold some of the attributes.

The split matters because not every pass needs every attribute. Shadow passes and the depth pass only need positions. Memory is fetched in blocks of 32 to 128 bytes, so with an interleaved buffer those passes drag normals and UVs through the cache too. Many engines keep positions in a stream of their own for this reason.

4 Index buffers: drawing by row number

The index buffer is a list of row numbers. In the usual triangle list arrangement, every three numbers form one triangle. Because a row number is far smaller than a row, a corner shared by six triangles costs one row plus six small numbers instead of six rows.

The size of each number is the index format. A 16-bit index takes 2 bytes and can count up to 65,535, so it can address 65,536 vertices. Larger meshes need 32-bit indices at 4 bytes each, or must be split into pieces that each fit. Most engines pick the smaller format automatically when a mesh allows it.

Try it below. Switch the index buffer off and watch the shared corners turn into duplicate rows. Then change the precision and the attributes, and watch the stride and the totals move.

Simplified

Triangle lists are the most common arrangement, but there are others, such as triangle strips, where each new index adds one triangle to the previous two. Modern engines almost always use lists, because they are simpler and lose nothing once indices and the vertex cache are in play.

5 Why a cube has 24 vertices, not 8

A vertex is a corner plus all of its data, so two triangles can share a vertex only if they agree about everything at that corner. At a hard edge they do not: the faces point in different directions, so they need different normals. At a texture seam they need different UVs. The mesh then stores a split vertex: two or more rows with the same position and different data.

A cube is the extreme case. Every corner touches three faces at right angles, so each of its 8 corners becomes 3 vertices, 24 in total. This surprises people when an artist's tool reports 8 and the engine reports 24. Nothing is wrong; it is the price of hard edges and seams.

6 Getting the data onto the GPU

When a level loads, the engine reads each mesh from disk into ordinary memory, then copies it once into VRAM, the GPU's own memory. From then on the GPU reads it directly, frame after frame, with no help from the CPU.

Most meshes go into a static buffer: written once, then only read. Geometry that changes every frame, such as particles, UI or procedurally generated meshes, uses a dynamic buffer that the CPU rewrites as it goes. Dynamic buffers are cheap to update but cost CPU time and transfer bandwidth every single frame.

7 What happens at draw time

A draw call names the buffers, the layout and the number of indices to draw. The GPU's input assembler then walks the index buffer, fetches each row it points to, and hands the vertex to the vertex shader, the small program that places it on screen.

Here indexing pays off a second time. The GPU keeps the last few processed vertices in a post-transform vertex cache. When an index repeats soon after it was first seen, the GPU reuses the result instead of running the vertex shader again. With triangles ordered so shared corners come close together, a mesh needs little more than one vertex shader run per unique vertex. Tools such as meshoptimizer reorder triangles for exactly this.

Code The same quad in about ten lines of WebGL 2

Every graphics API has the same three moves: create a buffer and copy bytes into it, describe the layout, then draw with indices. Here they are in WebGL 2, which runs in any browser. You will see the same shape in Direct3D, Vulkan and Metal code.

// 1. Copy the vertex rows into a buffer in GPU memory.
const vbo = gl.createBuffer();
gl.bindBuffer(gl.ARRAY_BUFFER, vbo);
gl.bufferData(gl.ARRAY_BUFFER, vertexBytes, gl.STATIC_DRAW);  // static: written once

// 2. The vertex layout: attribute, count, type, normalise?, stride, offset.
gl.vertexAttribPointer(0, 3, gl.FLOAT, false, 32, 0);   // position
gl.vertexAttribPointer(1, 3, gl.FLOAT, false, 32, 12);  // normal
gl.vertexAttribPointer(2, 2, gl.FLOAT, false, 32, 24);  // uv

// 3. The index buffer: six 16-bit row numbers.
const ibo = gl.createBuffer();
gl.bindBuffer(gl.ELEMENT_ARRAY_BUFFER, ibo);
gl.bufferData(gl.ELEMENT_ARRAY_BUFFER, new Uint16Array([0, 1, 2, 2, 1, 3]), gl.STATIC_DRAW);

// 4. Draw: 6 indices, each 16 bits, starting at the beginning.
gl.drawElements(gl.TRIANGLES, 6, gl.UNSIGNED_SHORT, 0);

When reviewing code like this, check that the stride and offsets in step 2 match the bytes written in step 1, and that the index type in step 4 matches the array in step 3. Mismatches there are the bugs in section 5.

4 What it costs

Take a typical game character: 50,000 triangles and about 30,000 unique vertices after split vertices, with position, normal and UV in each vertex. Here is what each layout choice does to it.

LayoutStrideVertex bufferIndex bufferTotal
Full precision, no index buffer (150,000 rows)32 B4.58 MB04.58 MB
Full precision, 32-bit indices32 B0.92 MB0.57 MB1.49 MB
Full precision, 16-bit indices32 B0.92 MB0.29 MB1.20 MB
Compact attributes, 16-bit indices16 B0.46 MB0.29 MB0.74 MB

Compact means vertex quantization: storing attributes in fewer bits. Positions as 16-bit numbers relative to the mesh's bounding box, normals packed into 4 bytes, UVs as 16-bit floats. Visually it is usually lossless for props and characters, and it halves the bytes every pass has to read.

Memory is only part of the bill

  • Every pass reads it againA mesh drawn into a depth pass, four shadow cascades and the main pass is fetched six times per frame. Halving the stride halves all six.
  • Vertex shader runsClose to one per unique vertex with good triangle order; about three per triangle with no index buffer.
  • Dynamic updatesRewriting a buffer each frame costs CPU time and bus bandwidth in proportion to its size.
  • Split verticesEvery hard edge and UV seam adds rows. Hard-surface props often have 1.5 to 2 times the vertices of a smooth mesh with the same triangles.

In proportion

One 2048 × 2048 texture compressed with BC7, with its mip chain, takes about 5.3 MB, more than four times the whole character mesh above. Vertex memory rarely decides whether a game fits. Vertex bandwidth and vertex counts matter more: in dense open worlds, in shadow passes that redraw everything, and on mobile GPUs where memory bandwidth also costs battery and heat.

5 How it breaks

Vertex data bugs are rarely subtle. Learn these five pictures and you can usually name the cause from a screenshot.

Exploding spikes

Cause
The vertex layout in code does not match the bytes in the buffer: wrong stride, offset or format. Positions are read from the middle of normals or UVs.
Ask for
A comparison of the declared layout against what the importer writes, for every mesh variant, and a check in a frame capture's mesh viewer.

Triangles stretched across the model

Cause
A mesh with more than 65,536 vertices was given 16-bit indices. Large row numbers wrap around and point at the wrong corners.
Ask for
32-bit indices for that mesh, or splitting it, plus an import check that flags meshes over the limit.

Missing or inside-out faces

Cause
The triangles' winding order is flipped, often by an axis conversion on import, so backface culling removes the faces you should see.
Ask for
A check of the import's axis and handedness settings, or flipping the index order for the affected meshes.

Seams and wrong smoothing

Cause
Normals were merged across an edge that should be hard, or split where the surface should be smooth, often by recomputing normals on import instead of keeping the artist's.
Ask for
The importer's normal and tangent settings for the mesh, and whether they import or recompute.

Wobbling or cracking surfaces

Cause
Positions were compressed too far for the mesh's size. On very large meshes 16-bit positions cannot land exactly, so edges step and neighbouring pieces stop meeting.
Ask for
Full-precision positions for large or tiling meshes, or splitting them, while keeping compression for everything else.

To confirm any of these, take a frame capture with a frame capture tool such as RenderDoc or PIX. Both show each draw's vertex and index buffers as tables, with the layout the GPU used to read them.

No engine asks you to fill a vertex buffer by hand. You meet these ideas as import settings, mesh statistics and, in code, as layout descriptions.

Mobile caveat

Some older mobile GPUs cannot use 32-bit indices at all. Unity's documentation names the Mali-400 as one. If you ship to low-end Android, keep every mesh under the 16-bit limit.

7 Say it to your AI

Good briefs about vertex data name the engine and platform, state the current layout in numbers, and ask for risks and a way to verify, not just a change. Adapt these.

BriefUse when meshes take too much memory or bandwidth
Engine: Unity 6, URP. Target: Meta Quest 3 at 72 fps.
Our 40 character meshes use 56 bytes per vertex: position, normal and tangent at full precision, two UV sets and a colour. All use 32-bit indices.

1. Propose a compact vertex layout for these meshes. List each attribute, its format and size, and the new stride.
2. For each change, name the visual risk and how we would spot it in game.
3. Tell us which import or Player settings to change, and which meshes, if any, genuinely need 32-bit indices.
4. Estimate the saving per mesh and in total, and explain how to confirm the new layout in a RenderDoc capture.
  • Platform and frame rate tell the AI why bandwidth matters.
  • Stating the current stride gives it numbers to reason from.
  • Asking for risks and verification stops a blind "compress everything" answer.
Bug reportUse when meshes explode into spikes
Since we merged the new mesh import code, some static meshes render as long spikes radiating from the model. Others look fine. Unreal Engine 5, DirectX 12. Every broken mesh has a second UV channel; none of the working ones do.

Find the cause. Compare the vertex layout the code declares with the bytes the importer writes, for meshes with and without the second UV channel: stride, offsets and formats. Show me the mismatch, the fix, and an automated test that would have caught it.
  • The pattern (only meshes with a second UV set) points straight at a stride or offset mismatch.
  • Naming the three things to compare keeps the search narrow.
  • Asking for a test turns a one-off fix into a guard.

Questions to ask when reviewing vertex code

  1. Is this buffer created once, or rewritten every frame? Why?Per-frame rewrites cost CPU time and bandwidth for as long as the game runs.
  2. Where is the vertex layout declared, and what keeps it in step with the importer and the shader?Two copies of the same layout drift apart, and the result is spikes.
  3. Which meshes can exceed 65,536 vertices, and what happens to them?The 16-bit limit fails silently.
  4. Do we keep a CPU copy of this mesh? What reads it?An unneeded copy doubles the mesh's memory.
  5. Is the triangle order optimised for the vertex cache?It is free performance, usually one call to a library such as meshoptimizer at import time.

8 Check yourself

  1. A square has 4 corners and 2 triangles. With a 32-byte stride and 16-bit indices, how many bytes do its vertex and index buffers take together? How many without an index buffer?

    Show answer

    Vertex buffer 4 × 32 = 128 bytes, index buffer 6 × 2 = 12 bytes, so 140 bytes. Without indices it needs 6 rows: 6 × 32 = 192 bytes.

  2. An artist's tool says a crate has 8 vertices. The engine says 24. Is something broken?

    Show answer

    No. Each corner of a hard-edged box touches three faces with different normals, so it is stored as three split vertices: 8 × 3 = 24. UV seams can add more.

  3. A 90,000-vertex terrain tile renders with long triangles connecting distant parts of it. What do you check first?

    Show answer

    The index format. 16-bit indices can only address 65,536 vertices, so higher row numbers wrap around. Use 32-bit indices or split the tile.
