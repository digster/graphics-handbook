5.1 The pipeline in one picture

Every triangle a game draws takes the same route through the GPU. Its corners are fetched and moved into place, the triangle is turned into pixels, and each pixel is coloured and merged into the image. Two of the six stages run code written for the game; the other four are fixed hardware that you set with switches.

1 The picture

2 In plain words

A GPU does not draw a triangle in one go. It pushes it through a fixed sequence of steps called the graphics pipeline. Each step, a pipeline stage, takes what the step before produced, does one kind of job, and passes the result on. Every triangle of every mesh in every frame goes through the same stages in the same order.

Some stages run a shader: a small program written for the game, which the GPU runs thousands of times side by side. These are the programmable stages. A normal draw has two: one places each corner, the other colours each pixel. The rest are fixed-function stages, circuits built into the chip that always do the same job, such as working out which pixels a triangle covers. You cannot change what they do, only set their switches.

Everyday comparison

A car plant's assembly line. Some stations are machines bolted to the floor: the press stamps every door panel the same way, and all you can change is the setting on its dial. Other stations are crews who follow whatever work sheet they are handed: paint it this colour, fit these seats.

Every car visits every station in the same order. While the paint crew works on car 40, the press is already stamping panels for car 41.

The problem it solves

A frame needs the same few jobs done millions of times. Building the jobs that never change into hardware makes them fast and cheap. Keeping two stations programmable lets each game decide how things move and how they look.

Because every stage works at the same time on different triangles, the line moves at the pace of its slowest station. That one fact explains most GPU performance problems.

Why a lead cares

GPU performance talk is talk about stages: a scene is vertex-bound or pixel-bound, a smoke effect is limited by blending. Knowing what each stage does and what makes it busy tells you whether a slow frame needs fewer triangles, fewer pixels or simpler shaders before anyone opens a profiler. It also tells you what a shader change can fix, since shader code only ever changes the two programmable stages.

3 How it works

Follow one triangle through the six stages, then see how the stages share hardware and memory, how often each one runs, and the two newer paths that sit beside the classic route.

1 The six stages

A draw call starts the route. It names the buffers to read, the two shaders to run and the settings for everything else. Then:

  1. The input assembler reads the index buffer and fetches the vertex buffer rows it points to, exactly as 4.2 Vertex buffers and index buffers described.
  2. The vertex shader runs once per vertex and works out where that corner lands on screen.
  3. Primitive assembly joins each three shaded corners into a triangle, drops triangles that face away from the camera, and deals with any part outside the view.
  4. The rasterizer finds which pixels each triangle covers, and blends the corners' values for each one.
  5. The pixel shader runs once per covered pixel and returns its colour.
  6. The output merger compares each pixel's depth with what the depth buffer already holds, then writes or blends its colour into the image.

Step through them below. The screen is shrunk to 16 × 10 pixels so you can see every one. Try all three triangles: one on screen, one crossing the edge of the screen, and one seen from behind.

Simplified

Real GPUs blur these boundaries. Direct3D documents clipping, the divide by w and the mapping to the screen as part of its rasterizer stage, and most GPUs test depth before the pixel shader whenever they can, which 5.4 Pixel shaders and overdraw covers. Hardware also rarely cuts triangles exactly at the sides of the screen: it clips precisely where it must, mainly at the near plane, and elsewhere just skips pixels that are off screen. The order of the work, and what each stage needs and produces, is as shown.

2 Your code and fixed hardware

The two programmable stages run on the GPU's compute units, the groups of lanes that 3.5 CPU, GPU and graphics APIs described. The same lanes switch between vertex work, pixel work and compute work as the frame needs. The fixed stages are separate blocks of circuitry beside them, each built for one job.

Fixed does not mean unconfigurable. Every draw carries a set of switches for the fixed stages: which order of corners counts as the front of a triangle, whether to cull the back, whether to test and write depth, and how to blend. Together with the two shaders, these switches make up the draw's pipeline state, which 5.6 Shaders in practice covers in detail.

3 Where the data lives

Only the ends of the route move data in bulk. The input assembler reads vertex and index buffers from VRAM. The shaders read constants, such as the object's matrices and the time, and textures. The output merger reads and writes the depth buffer and the image being drawn, which is called a render target (5.6). Between stages, work passes through small buffers on the chip and is gone once the next stage has used it.

That is why the output merger is so often a memory problem. Every pixel it writes is a write to VRAM, and blending adds a read of the colour already there. A 2560 × 1440 image at 8 bytes per pixel is 28.1 MB, and it is touched again for every layer drawn over it.

4 How often each stage runs

Each stage runs at its own rate. Constants and switches are set once per draw, the vertex shader runs once per vertex, the rasterizer works once per triangle, and the pixel shader and output merger work once per covered pixel. Direct3D exposes these counts as pipeline statistics, such as VSInvocations and PSInvocations, and GPU profilers report them per draw.

Take a mid-sized frame at 2560 × 1440: 3,000 draw calls, 2 million vertex shader runs and 1.5 million triangles reaching the rasterizer in the main pass. The screen has 3,686,400 pixels. If each is covered twice on average, because surfaces overlap, the pixel shader runs about 7.4 million times.

Per object the gap is much wider. The crate in 0.1 The whole journey on one page costs 24 vertex shader runs and about 25,000 pixel shader runs. Raw triangle throughput is rarely the limit either: Brian Karis of Epic puts the triangle setup rate of modern GPUs at 4 per clock, which at 2.5 GHz is 10 billion a second. The trouble comes from triangles much smaller than a pixel, which waste most of the rasterizer's effort; 5.3 Rasterization shows why.

5 Compute shaders: the side door

A compute shader skips the route altogether. It runs as many copies of a program as you ask for, each reading and writing buffers and textures in memory, with no vertices, no rasterizer and no output merger. A request to run one is called a dispatch.

Modern renderers lean on it heavily: ambient occlusion and other effects computed from the depth buffer, deforming animated characters before they are drawn (Unity does this by default), lists of what to draw built on the GPU, particles and post effects. Results go back to memory, where later draws read them.

Compute can even beat fixed hardware at its own job. Unreal's Nanite rasterizes clusters of triangles less than about 32 pixels long in a compute shader, which Epic measured at about three times faster on average than its fastest hardware path, and sends larger triangles to the hardware rasterizer, which is good at those.

6 Mesh shaders: a new front half

The front half of the classic route, from the input assembler to primitive assembly, was designed around one index buffer read in order. A mesh shader replaces it with a program that works like compute. Each group of threads loads a small piece of a mesh, a meshlet, from any buffer it likes, transforms its vertices together and hands up to 256 vertices and 256 triangles straight to the rasterizer.

An optional stage in front of it can cull whole meshlets before any vertex work and decide how many mesh shader groups to launch. Direct3D 12 calls it the amplification shader, Vulkan the task shader and Metal the object shader. The back half of the route, from the rasterizer on, does not change.

Direct3D 12 added mesh and amplification shaders with Shader Model 6.5 in 2020, as part of DirectX 12 Ultimate, which AMD's RDNA 2 GPUs and the Xbox Series X and S support in full; NVIDIA introduced the idea with its Turing GPUs. Vulkan has them through the VK_EXT_mesh_shader extension, and Metal has object and mesh shaders on recent Apple GPUs. Khronos's own advice is that the classic pipeline may still be the better choice for many uses, so treat mesh shaders as a tool for heavy geometry and GPU-driven culling, and measure before switching.

Simplified

Between the vertex shader and primitive assembly, Direct3D 11 and 12 also offer optional hull, tessellator, domain and geometry stages, and a stream output stage that writes vertices back to memory. Most draws switch them off. Microsoft intends amplification shaders to replace the hardware tessellator over time.

4 What it costs

Every stage works at the same time on different parts of the frame, so a draw takes as long as its busiest stage, and the others wait. Speeding up any other stage saves nothing, so the first job is always to find that one.

A worked example of the last row. A smoke effect covers half of a 2560 × 1440 screen with 10 layers of blended sprites, into an 8-byte-per-pixel image. Blending reads and writes each pixel, so that is 1,843,200 pixels × 10 layers × 16 bytes = 281 MB of memory traffic per frame, 16.5 GB per second at 60 fps, before any texture is read. On a tile-based phone GPU the blending happens in on-chip tile memory, so the same effect is limited by its pixel shader instead.

What makes the frame slower

  • More verticesVertex shader runs and triangle setup, multiplied by every pass that draws the mesh, shadows included.
  • More pixelsResolution multiplies the pixel shader and the output merger: 4K is four times 1080p.
  • OverdrawEvery layer of surface drawn over another pays the pixel shader again, and blended layers pay the output merger twice.
  • Longer shadersCost per run, multiplied by the run count: a small pixel shader change matters millions of times a frame.
  • Tiny trianglesTriangles smaller than a pixel cost full triangle setup and shading work while drawing almost nothing.
  • More passesEach pass sends its geometry through the whole route again.

5 How it breaks

Most pipeline bugs come from one stage receiving something it did not expect, or one switch set wrongly. Name the stage and the fix is usually close.

An object vanishes completely

Cause
None of its pixels reach the image. The vertex shader writes bad positions (a wrong or missing matrix, or w of zero), the cull switch drops every triangle because the front is defined the wrong way round, or the depth test rejects every pixel.
Ask for
A frame capture of the draw showing its vertex shader output, triangles reaching the rasterizer and pixels written, plus its cull and depth settings.

Things show through walls

Cause
The output merger's depth test or depth write is off for one of the draws, or its comparison is set the wrong way, so whatever is drawn later wins.
Ask for
The depth settings of the wall's draw and the figure's draw in a capture, and why either was changed.

Geometry sliced open near the camera

Cause
Clipping doing its job. Anything nearer than the camera's near plane is cut away, so a camera inside or too close to an object shows its hollow inside.
Ask for
The camera's near-plane distance and the collision that keeps the camera out of walls, especially for first-person weapons and tight corners.

Fine at 1080p, slow at 4K

Cause
The pixel half of the route is the limit: pixel shader cost, overdraw or output merger bandwidth. Vertex work does not change with resolution, so it cannot be the cause.
Ask for
GPU time at two resolutions, then the most expensive pixel passes, and whether rendering at a lower internal resolution and upscaling (9.3) is acceptable.

Slow with detailed meshes, even far away

Cause
Vertex and triangle work: millions of triangles, many smaller than a pixel, keep the vertex shader and triangle setup busy while drawing few pixels. Shadow passes multiply the cost.
Ask for
Triangle counts per draw and per pass for the worst meshes, and level-of-detail or Nanite settings for them.

A frame capture tool such as RenderDoc or PIX confirms any of these: it shows each draw's inputs, its shaders and settings, and what it wrote.

6 In the engines

Every engine exposes the same split. The two programmable stages appear as two halves of a material or shader, and the fixed stages appear as material settings.

Names checked against the documentation for Unreal Engine 5.9, Unity 6.6 (Shader Graph 17.6) and Godot 4.7 in November 2026. Engines rename settings between versions; if one is missing, search for it in your version's documentation.

Platform caveat

Godot's documentation warns that compute shader support is generally poor on mobile devices because of driver bugs, even where it is technically available. Test compute-based effects on your lowest-end target phones before planning around them.

7 Say it to your AI

Good briefs about the pipeline name the stage you suspect, ask for counts per stage, and ask how to measure before anything is changed.

BriefUse when a scene misses its GPU budget and nobody knows why
Engine: Unreal Engine 5.9, DirectX 12. Target: 60 fps at 2560 × 1440 on an RTX 3060.
Our forest level takes 22 ms of GPU time per frame. We do not know whether vertex work, pixel work or blending is the limit.

1. Measure GPU time at 100% and 50% screen percentage, and again with shadows off. Report the numbers.
2. From a frame capture, list the 10 most expensive passes and, for each, its vertex shader runs, triangles drawn and pixel shader runs.
3. For each of those passes, say which pipeline stage limits it and why, citing the numbers.
4. Propose fixes ranked by milliseconds saved, with the visual cost of each.
  • The resolution test separates the pixel half of the pipeline from the rest in one step.
  • Counts per pass make every claim checkable.
  • Ranking by milliseconds keeps the work on the stage that sets the pace.
Bug reportUse when a shader change makes objects disappear
After a change to our custom foliage shader, every tree disappears in game but still shows in the material preview. Unity 6.6, URP, on Vulkan (Android) and DirectX 12 (PC); both are affected.

Take a frame capture and find the tree draws. Tell me at which pipeline stage they are lost: does the vertex shader run, how many triangles reach the rasterizer, how many pixels pass the depth test? Then show me the line of the change that causes it, the fix, and how to check the fix in a capture.
  • Asking stage by stage stops guesswork about the cause.
  • Both platforms failing rules out a driver bug on one of them.
  • Preview working and game failing points at per-object data, such as matrices, rather than the shader's maths.

Questions to ask when reviewing pipeline work

  1. Which stage does this run in, and how many times per frame?Once per draw, per vertex and per pixel differ by factors of thousands.
  2. Could this per-pixel calculation run per vertex, or once per draw?Moving work earlier in the route divides its run count, as long as the result can be blended linearly across the triangle.
  3. Does the change touch culling, depth or blend settings?These switches are easy to change by accident, and the results look like missing or see-through objects.
  4. Does it add a pass?Each pass sends its geometry through the whole route again.
  5. Does it need compute or mesh shaders, and do all our platforms have them?Godot's Compatibility renderer has no compute shaders, and mesh shaders need recent GPUs.

8 Check yourself

  1. Which of the six stages run code written for the game, and what can you change about the others?

    Show answer

    The vertex shader and the pixel shader run game code. The input assembler, primitive assembly, the rasterizer and the output merger are fixed hardware; you can only set their switches, such as the cull mode, the depth test and the blend mode.

  2. The same scene runs at 60 fps at 1080p and 35 fps at 4K. Which half of the pipeline is most likely the limit?

    Show answer

    The pixel half. 4K has four times the pixels, 8,294,400 against 2,073,600, so pixel shader and output merger work grows fourfold, while vertex work stays the same.

  3. A triangle faces away from the camera and backface culling is on. Which stages does it cost?

    Show answer

    Vertex fetch and the vertex shader for its corners, then primitive assembly, which drops it. The rasterizer, pixel shader and output merger never see it.
