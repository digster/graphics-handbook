3.5 CPU, GPU and graphics APIs

A game runs on two very different processors. The CPU has a handful of fast, flexible cores that decide what should be drawn; the GPU has thousands of simple lanes that do the drawing. Between them sits a stack of software, from the engine down to the driver, that turns one into work for the other.

1 The picture

2 In plain words

Every frame, a game has two very different kinds of work. One kind is decisions: where the player moved, what each enemy does next, which objects are worth drawing. The other kind is arithmetic on an enormous scale: move two million corners into place, then colour eight million pixels, each with the same small recipe.

The CPU is built for the first kind. It has a few cores, each very fast and very good at following branching logic. The GPU is built for the second. It has thousands of simple lanes that all run the same small program at the same moment, each on its own corner or pixel. Doing many pieces of one job at once like this is parallelism. The GPU keeps its data in VRAM, memory of its own that it can read very quickly, or in a share of the main memory on consoles and phones.

The two processors never talk directly. The game asks the engine for a picture. The engine speaks a graphics API, a published set of commands such as DirectX 12, Vulkan or Metal. The GPU maker's driver translates those commands into the instructions that one particular GPU understands.

Everyday comparison

A wedding caterer has a small team of planners and a long kitchen line. The planners decide the menu, the seating and the timing, and any of them can handle a surprise. The cooks on the line each plate the same dish, and together they plate three hundred in the time one person would plate a few.

The planners never cook. They write order sheets in a fixed format, which is the graphics API, and the kitchen manager, the driver, turns each sheet into instructions for this particular kitchen.

The problem it solves

A frame needs the same small calculation done millions of times, sixty or more times a second. A handful of clever workers cannot keep up with that. Most game logic, though, is a tangle of one-off decisions that thousands of identical workers would handle badly.

Splitting the work lets each processor do what it is built for, and the API layer lets one game run on GPUs from many makers.

Why a lead cares

Your platforms decide your graphics APIs, and the APIs decide some features: Unreal's Nanite needs DirectX 12 or Vulkan with 64-bit atomic operations. Whether a slow frame is the CPU's fault or the GPU's decides who on the team fixes it. Driver and shader compilation problems cause bugs that appear on one vendor's hardware only, or only the first time an effect plays. And on phones, memory traffic turns directly into battery drain and heat.

3 How it works

Start with the hardware, then follow the software that drives it. There are nine steps: five about chips and memory, four about the layers above them.

1 Few fast cores, thousands of simple lanes

A CPU core spends most of its chip area on making one stream of instructions go fast. Large caches keep data close by, and control logic predicts which way branches will go and reorders work to avoid waiting. A current console has 8 such cores; a Steam Deck has 4.

A GPU spends most of its area on arithmetic. NVIDIA's CUDA guide says GPUs devote more transistors to data processing, while CPUs devote more to caching and flow control. The result is thousands of lanes, each slower and simpler than a CPU core, that together get through far more work per second. There is one condition. The work must split into many independent pieces.

That condition is the whole story of real-time graphics. Vertices and pixels are independent: shading one pixel does not need the answer for its neighbour. Gameplay logic is usually the opposite, a chain of decisions where each step depends on the last.

2 Lanes move in lockstep

GPU lanes are not independent workers. They come in groups that share one stream of instructions: the hardware fetches an instruction once, and every lane in the group applies it to its own data. This is SIMD, single instruction, multiple data. NVIDIA calls its version SIMT, single instruction, multiple threads, because each lane looks like a separate thread to the programmer.

The group is a warp. On NVIDIA GPUs a warp is 32 lanes. AMD calls it a wavefront, and its RDNA GPUs run wavefronts of 32 lanes natively and of 64 for compatibility. Other vendors and APIs use other names for the same idea.

Lockstep has a price. When the lanes of one warp disagree at an if, the warp runs both sides, one after the other, with the lanes that went the other way switched off. Neighbouring pixels usually take the same branch, so in practice this costs less than it sounds. A shader that branches on noisy data, though, pays for every branch it contains.

3 Inside a GPU

A GPU is built from one block repeated many times. NVIDIA calls the block a streaming multiprocessor (SM), AMD a compute unit (CU), Apple a GPU core. This book says compute unit. Each one holds lanes, a scheduler that picks which warp runs next, a large set of registers for the warps it is running, a small fast cache shared by its lanes, and texture units that fetch and filter textures.

All compute units share a larger second-level cache, and behind that sits VRAM. Each step outward is bigger and slower. A GPU deals with the slow end by hiding the wait instead of avoiding it. Each compute unit keeps many warps in flight; AMD's RDNA design holds up to 20 per group of 32 lanes. When one warp stops to wait for memory, the scheduler runs another that is ready, and the lanes stay busy.

This is why GPUs need big jobs. Hiding the wait only works when there are thousands of vertices or pixels ready to go. A draw that touches a few dozen pixels leaves most of the chip idle.

4 Where the data lives: discrete and unified memory

On most gaming PCs the GPU is a discrete GPU: a separate card with its own VRAM, connected to the CPU through a PCI Express slot. The card reads its own VRAM very fast. The slot between the card and the rest of the PC is far slower: a PCIe 5.0 ×16 slot moves about 64 GB per second each way, roughly a tenth of what an RTX 5070 reads from its VRAM. So engines copy meshes and textures across once, when a level loads, and keep them there.

Consoles, Apple silicon Macs, the Steam Deck and phones use unified memory. The CPU and GPU sit on one chip and share one pool. A PlayStation 5 has 16 GB of GDDR6 at 448 GB per second for both; an Apple M5 has 153 GB per second. Nothing has to be copied between pools, but the CPU and GPU now compete for the same bandwidth, and the GPU gets whatever memory the rest of the game leaves free.

The number to watch in both designs is memory bandwidth, the number of bytes per second the memory can deliver. Many rendering passes spend more time waiting for bytes than doing arithmetic, so bandwidth often sets their speed.

5 Tile-based and immediate-mode GPUs

Desktop and console GPUs are immediate-mode GPUs. They draw triangles in the order they arrive and write each covered pixel's colour and depth straight to full-screen buffers in VRAM. Where triangles overlap, the same pixel is read and written again and again.

Phones cannot afford that traffic, because reaching main memory is one of the most power-hungry things a phone chip does. Tile-based GPUs split the screen into small tiles, 16 × 16 pixels on Arm's Mali GPUs, and work in two passes. First they position every triangle of the pass and sort them into a list per tile. Then they render one tile at a time entirely inside a small, fast tile memory on the chip, and write each finished tile out once. Depth values usually never leave the chip at all. Arm puts the energy of an on-chip access at about a tenth of an external one. Apple's GPUs and Arm Mali GPUs, among others, work this way.

The design has two costs. The sorted triangle lists themselves go out to memory and come back, so very high vertex counts cost a tile-based GPU more. And anything that needs a tile's colour or depth again in a later pass forces the GPU to write it out and read it back, which throws the saving away. 10.2 A mobile frame shows how renderers arrange their passes around this.

Simplified

The line between the two families is blurrier than this picture. Vendors mix techniques, desktop GPUs use caches that work in screen regions too, and the inner details of most GPUs are only partly public. What holds is the advice: on phones, keep work on the chip and avoid passes that send whole-screen images back to memory.

6 From engine to driver

Go back to the layer cake. The engine's renderer decides what to draw. Below it, most engines keep a thin layer of their own, which Unreal calls the RHI, its rendering hardware interface, and Godot calls RenderingDevice. The rest of the engine talks only to this layer, and the layer has one back end per graphics API. That is how one engine ships on Windows, PlayStation and phones without rewriting its renderer three times. 2.1 Anatomy of an engine covers it from the engine's side.

DirectX 12, Vulkan and Metal are explicit, or low-level, APIs. The engine manages GPU memory, threading and synchronisation itself, and the driver does less guessing on its behalf. Microsoft describes Direct3D 12 as a lower level of hardware abstraction than its predecessors, with greatly reduced CPU overhead, and says it needs significant graphics expertise to use. Older APIs such as OpenGL and DirectX 11 left more of that work to the driver, which was easier to program and harder to predict.

7 Which API runs where

Five APIs cover almost every platform a game ships on, and consoles add their own.

  • DirectX 12 is Microsoft's API for Windows and Xbox; Xbox uses its own version of it. DirectX 11, its older, higher-level predecessor, is still a common fallback on PC.
  • Vulkan is the Khronos Group's cross-platform explicit API. It is the main API on Android and on Linux, including the Steam Deck, and it runs on Windows. It also runs on both Nintendo Switch consoles.
  • Metal is Apple's API for Mac, iPhone, iPad and Vision Pro, and the only modern API native to them. Vulkan runs there through MoltenVK, a layer that translates it to Metal.
  • WebGPU is the browser's modern API. Google announced in November 2025 that it now ships in Chrome, Edge, Firefox and Safari, with some systems, such as Firefox on Linux and Android, still to come.
  • OpenGL is the older cross-platform API. Its last version, 4.6, came out in 2017. Its cut-down relatives are OpenGL ES on phones and WebGL in browsers. Apple deprecated it in 2018, and Android keeps supporting OpenGL ES but no longer develops it. It lives on in compatibility renderers for old and low-end devices.

PlayStation uses Sony's own graphics API, available only to licensed developers. The original Nintendo Switch has NVN, an API NVIDIA built for it, and Khronos lists both Switch consoles as conformant Vulkan devices.

8 Submitting work: command buffers and queues

The CPU does not call the GPU and wait for an answer. It writes a list of commands into a command buffer: set this pipeline, bind these buffers, draw 3,000 indices, and so on. Nothing runs while the list is being written. When it is finished, the CPU submits it to a queue, and the GPU works through the queued buffers in order, at its own pace. DirectX 12 calls them command lists; Vulkan, Metal and WebGPU call them command buffers.

Two things follow. First, recording can be spread across CPU threads, each filling its own command buffer, which is how explicit APIs use many-core CPUs. Microsoft designed Direct3D 12 so that several command lists can be recorded at the same time. Second, the GPU usually runs about a frame behind the CPU: while the GPU draws frame 10, the CPU is recording frame 11. Simple counters called fences tell the CPU when the GPU has finished with memory it may now reuse.

A GPU can have more than one queue. Besides the main graphics queue, DirectX 12 and Vulkan expose compute and copy queues, so an upload or a compute job can overlap the main rendering. 2.2 The game loop and threads follows the same flow from the engine's threads.

9 Shaders are compiled twice

A shader is a small program the GPU runs for every vertex or pixel. Each GPU family has its own machine code, and a game cannot know in advance which GPU a player owns. So shader compilation happens in two stages.

On the developer's side, the build compiles shader source, usually written in HLSL, into an in-between form for each API: DXIL for DirectX 12, SPIR-V for Vulkan, a Metal library for Metal. Microsoft's DXC compiler produces both DXIL and SPIR-V. A large game has many variants of each material's shader, so this step takes real build time.

On the player's machine, the driver turns that in-between form into the GPU's machine code. With the explicit APIs this happens when the engine creates a pipeline state object, the bundle of shaders and fixed settings for one kind of draw, covered in 5.6 Shaders in practice. It is slow enough that doing it in the middle of gameplay causes a visible hitch. Engines therefore try to create pipelines during loading, and engines and drivers keep compiled results in caches on disk.

4 What it costs

The CPU and GPU split has three running costs: memory bandwidth, CPU time spent feeding the GPU, and the time and care it takes to compile and test shaders on every API. Bandwidth is the one leads most often underestimate, so start there.

A worked example shows how fast bandwidth goes. A 4K frame has 3,840 × 2,160 = 8,294,400 pixels. One full-screen image at 4 bytes per pixel is 33.2 MB. A renderer that writes four such images of surface data plus a 4-byte depth buffer, then reads them all back to light the scene, moves 332 MB before it has sampled a single texture.

33.2 MBone full-screen 4K image at 4 bytes per pixel
332 MBfive such images written once and read once
7.5 GBthe most a PlayStation 5 can move in one 60 fps frame
4.4%of that 7.5 GB spent on those five images alone

Four per cent looks harmless until you add every texture read, every shadow map, the post-processing passes that each read and write whole-screen images, and the CPU's own traffic on the same shared memory. On a tile-based phone GPU the same images can stay on the chip if the passes are arranged for it, or cost full price if they are not.

CPU time is the second cost. Every draw passes through the engine, the RHI, the API and the driver, and each layer spends CPU time on it. Explicit APIs cut the driver's share and let recording spread across cores; the engine's own work per draw remains. 4.3 Draw calls, batching and instancing is about keeping that number down.

What makes the costs grow

  • ResolutionFull-screen passes scale with pixel count. 4K is four times the pixels of 1080p.
  • Full-screen passesEach pass that writes a whole-screen image and reads it back adds its full size twice.
  • Bytes per pixelHigher-precision render targets double or quadruple the traffic of each pass.
  • Draw countEach draw costs CPU time in every layer of the stack.
  • Shader variantsMore variants mean longer builds, bigger caches and more chances of a pipeline missing from the cache.
  • APIs and vendorsEach API back end and each GPU vendor adds rows to the test matrix and its own driver quirks.

5 How it breaks

Problems at this level rarely look like rendering bugs. They look like stutter, heat, crashes on one brand of graphics card, or a GPU sitting idle. These are the common patterns.

A hitch the first time something appears

Cause
A pipeline is created, and its shaders compiled by the driver, at the moment of first use instead of during loading. It often returns after a driver update, which clears the driver's cache.
Ask for
The engine's pipeline precaching or warm-up to be set up and verified, and a log of pipeline compiles during play.

Corruption or crashes on one vendor's GPUs

Cause
Code that breaks an API rule one driver happens to tolerate, such as missing synchronisation, or a genuine driver bug. Explicit APIs check very little at runtime.
Ask for
A run with the API's validation layer turned on, and testing on each GPU vendor and current driver before a release.

The GPU sits idle and the frame is still late

Cause
The game is CPU-bound: the CPU cannot record and submit work fast enough, often because of too many draws or recording on a single thread.
Ask for
A capture that shows CPU and GPU timelines side by side, then draw-count and threading work before any shader optimisation.

A phone runs well, then heats up and slows down

Cause
Too much memory traffic for a tile-based GPU: full-screen passes whose images go out to memory and back, high resolution, or large render targets. The chip throttles to cool down.
Ask for
A bandwidth capture with the vendor's mobile profiler, and a review of which render targets are stored to memory each frame.

Sudden slowdowns on cards with less VRAM

Cause
The game asks for more GPU memory than the card has, so some data lives in system memory and is fetched over the much slower link.
Ask for
A VRAM budget per quality setting, a memory report on the smallest supported card, and texture streaming limits that respect it.

To see these, use the engine's own profiler first, then a frame capture tool such as RenderDoc or PIX for the GPU side. Every explicit API has a validation layer that reports rule breaks; ask for it to be part of regular testing.

Console caveat

Console APIs, and engine support for them, sit behind each platform holder's developer agreement. Plan console work with the engine vendor or a porting partner from the start. Godot, for instance, officially supports no console except the Steam Deck; console versions come from third-party ports.

7 Say it to your AI

Good briefs at this level name the engine and version, every target platform and the API on each, and ask for what you lose on each fallback. Adapt these.

BriefUse when choosing graphics API back ends
Engine: Unity 6.6, URP. Platforms: Windows PC on Steam, Android phones from 2021 onward, and a browser demo.

1. For each platform, list the graphics APIs Unity can use, recommend the order for the Graphics APIs list, and say what we lose if a player falls back to the second one.
2. Flag any feature we plan to use (compute shaders, GPU instancing, async compute) that is not available on every API in that list.
3. Propose a test matrix: GPU vendors, driver versions, APIs and minimum devices.
4. Describe the shader and pipeline warm-up we need on each API to avoid hitches the first time an effect appears.
  • Naming every platform lets the AI work out the API list instead of guessing.
  • Asking what each fallback loses surfaces missing features early.
  • A test matrix and warm-up plan cover the two most common late surprises.
Bug reportUse when effects hitch on first use
Unreal Engine 5.7, DirectX 12, Windows. Players report a 100 to 300 ms freeze the first time each new enemy type or spell effect appears in a session. Later appearances are smooth. The freezes come back after a GPU driver update.

Find the cause. Check whether PSO precaching is enabled and covers these materials, whether we ship a bundled PSO cache, and which pipelines compile during play. Show the fix, and how to confirm it with logs or a capture on a machine with an empty driver cache.
  • "First time only" and "back after a driver update" point straight at pipeline compilation.
  • Naming PSO precaching and the bundled cache keeps the search on the right systems.
  • Testing with an empty driver cache reproduces what a new player sees.

Questions to ask when reviewing low-level graphics code

  1. Does this create pipelines, shaders or large buffers during gameplay? When exactly?Creation at first use is the classic source of hitches.
  2. Does the CPU read GPU results back in the same frame?Waiting for the GPU stalls both processors and throws away the frame of overlap.
  3. Is it written against the engine's RHI or straight against one API?Code tied to one API has to be written again for every other platform.
  4. Which API features does it assume, and what happens on hardware without them?Without a fallback, one missing feature becomes a crash on some players' machines.
  5. Was it tested with the API's validation layer on, on more than one GPU vendor?Explicit APIs trust the code; drivers differ in what they forgive.

8 Check yourself

  1. Why is a GPU fast at shading pixels but a poor choice for running enemy AI?

    Show answer

    Pixels need the same small program run millions of times on independent data, which suits thousands of lanes in lockstep. Enemy AI is a chain of branching decisions for a few dozen characters, so most lanes would sit idle or diverge. CPU cores are built for that kind of work.

  2. A 32-lane warp reaches an if. Four lanes take a branch that costs 10 instructions; the other 28 take one that costs 30. How many instruction steps does the warp spend on the if?

    Show answer

    About 40. The warp runs both branches one after the other, with the lanes that went the other way switched off, so it pays 10 + 30 even though no single lane needs more than 30.

  3. Your mobile game holds 60 fps for five minutes, then drops to 40 as the phone gets hot. The PC build is fine. Where do you look first?

    Show answer

    Memory traffic on the phone's tile-based GPU. Look for full-screen images written out to memory and read back each frame, render resolution and render target sizes. The phone is throttling to shed heat, and memory traffic is one of its most power-hungry activities.
