12.3 Reviewing AI-written graphics code

AI-written graphics code fails in a small number of recognisable ways, and most of them compile, pass simple tests and look almost right. This chapter turns them into a one-page checklist grouped by risk, shows each mistake on a short shader with five planted errors, and sets out a review loop where machines check first and people judge last.

1 The picture

2 In plain words

A code review checklist is a short, fixed list of questions a reviewer asks of every change. For graphics code, most of the questions are about agreement: does the shader agree with the CPU about where each value sits, does every vector agree about which space it is in, does the code agree with the platform about what the hardware can do. An AI coding agent gets these wrong in the same ways people do, but faster, in larger changes, and with a confident report attached.

Graphics bugs are hard to review because so many of them are legal. A colour decoded twice, a normal in the wrong space or a constant buffer packed differently on each side all compile, pass the API's validation and draw a picture. The picture is just slightly wrong, or wrong on one platform, or wrong once a week. A checklist moves the reviewer's attention from "does this look like reasonable code" to "does this code agree with everything around it".

An everyday comparison

Checking a translated contract. The translation reads fluently, which is exactly what makes errors easy to miss. A careful reader ignores the prose and checks the things that must agree with the original: names, numbers, dates, currencies, and the clauses whose meaning changes from one country to the next.

The problem it solves

Without a list, review depends on who happens to be reading and what they happen to notice. With one, every change gets the same twelve questions, the cheap ones are answered by machines before a person looks, and a new reviewer catches what an experienced one would.

Why a lead cares

Review is where the cost of AI work concentrates (12.1). A shared checklist makes that cost predictable: it tells reviewers where to look, tells the team which checks to automate, and can be pasted into the brief so the agent checks its own work against the same list before handing it back. It also gives a reason for every rejection, which turns review comments into better briefs.

3 How it works

The steps start with the loop every change goes through, then take the checklist's risks one at a time, and end with a worked review of a short shader with five planted mistakes.

1 The review loop: machines first, people last

An AI change arrives as a diff and a report. Before any person reads it, it should pass an automated gate: builds for every platform, shader compilation for every variant in use, the graphics API's debug layers, tests, timings at fixed camera positions, and screenshot comparison against approved images. These run in minutes on continuous integration and return their errors straight to the agent, which can usually fix them alone.

Validation is worth switching on everywhere it exists. Microsoft's guidance for Direct3D 12 is to run with the debug layer enabled most of the time, and to run its slower GPU-based validation on one or two test machines in a nightly pass. The Khronos validation layers do the same for Vulkan. They catch illegal API use: wrong resource states, uninitialised descriptors, out-of-range indices. They do not catch the legal mistakes that fill the rest of this chapter.

Human review reads in a fixed order. First the agent's report against the brief (12.2): what it changed, what it ran, where, and what it did not test. Then the diff, with the checklist. Then the evidence, to see whether each claim is backed by a capture or a screenshot. Reading the report first tells the reviewer which rungs of the ladder are already climbed, and which questions still need a person.

2 Colour-space mix-ups

A colour-space mix-up treats sRGB-encoded values as linear or the reverse. 3.2 Colour done right explained the rule: colour textures are stored in sRGB to spend their 8 bits where eyes notice, lighting must run on linear values, and the image is encoded back to sRGB on the way to the screen. Each conversion must happen exactly once.

AI-written shaders fall into this often, because older tutorials apply gamma by hand and the code looks responsible. Search the diff for 2.2, 1/2.2, 0.4545 and the sRGB curve's constants, then check each against the texture's import setting and the render target's format. The cheapest catch is a test scene with grey and coloured swatches of known values, compared against a golden image.

Data textures need the opposite rule. A normal map, a roughness map or a packed mask must never be decoded, because their numbers are directions and amounts. An AI that marks every texture as sRGB "for correctness" bends every normal (6.4).

3 Coordinate spaces, handedness and up axis

A coordinate-space mix-up combines vectors measured in different coordinate spaces. The classic case is a normal still in object space dotted with a light direction in world space. While the object sits unrotated, the two spaces happen to agree and the lighting looks right. Rotate the object and its lit side turns with it.

Ask the agent to name every vector by its space: normalWS, lightDirVS, positionCS for world, view and clip space. Mismatches then show in the diff as dot(normalOS, lightDirWS), which a reviewer can see without running anything. The test is just as simple: spin the object under a fixed light, and move it far from the origin.

A handedness and up-axis error is the same mistake at the scale of a whole asset or system. Unreal is Z-up and left-handed, Unity Y-up and left-handed, Godot Y-up and right-handed. Code copied from one engine's examples into another, or a conversion applied twice, lays models on their sides, mirrors them, or flips their winding order so backface culling removes the faces you should see (4.1). Check which up axis and handedness the code assumes, and where the one conversion happens.

4 Buffer layouts

A buffer layout mismatch is CPU code and shader code disagreeing about where each value sits in memory. In a vertex buffer the vertex layout tells the GPU which bytes are positions and which are normals (4.2); get a stride or an offset wrong and positions are read from the middle of other data, which shows as exploding spikes. In a constant buffer the rules are subtler, because HLSL packs values into 16-byte rows and C++ does not (5.6).

The robust fix is structural: declare each buffer once, in a header both sides include, or generate one side from the other, or add compile-time checks of every offset. In review, look for a struct and a cbuffer edited in the same change but in different files, and for any reordering of fields. A frame capture in RenderDoc or PIX shows the values the GPU actually received, which settles the question in a minute (11.5).

5 Precision and NaN

A precision problem is visible error from too few bits. Three kinds turn up in AI-written code. Positions or texture coordinates stored in 16-bit half floats, which wobble far from the origin. Colours stored or blended in 8 bits, which show as banding (3.2). And depth: a tiny near plane or a standard depth mapping where the engine expects reversed-Z brings back z-fighting (5.5).

Precision bugs are often platform bugs too. Unity's documentation says that by default half has no effect on higher-performance platforms such as macOS, where it becomes a 32-bit float, and that 16-bit precision can cause visible errors such as colour banding or stuttering geometry, so you should test on a platform that supports half. Code that looks fine on every desktop in the studio can wobble on every phone.

A NaN, short for not a number, comes from operations with no answer: zero divided by zero, the square root of a negative number, normalising a vector of length zero, or a pow whose exponent is infinite. GPUs carry on regardless, and the value spreads through bloom, blurs and TAA history until a black square grows across the screen. In review, look at every division and every normalize and ask what happens when the input is zero: a roughness of 0, a light exactly overhead, a vector between two equal points.

6 Allocation, variants, threads and claims

The second column of the checklist covers code that looks right and costs too much. None of it shows in a screenshot, so it is easy to wave through.

Per-frame allocation is the most common. Strings built for debug text, lists created inside a loop, closures captured in an update, and new GPU buffers created per draw all allocate every frame. In C# and other garbage-collected code that brings the next collection closer; in C++ it fragments memory and costs time in the allocator. Ask where each allocation lives and how often it runs, and check allocations per frame in the profiler.

Shader variant explosion is a slow-acting cost. A new keyword declared so that every combination is compiled, or a new static switch on a master material, can double compile time, shader memory and the PSO cache in one line. Ask for the variant count before and after, and for the reason the switch cannot be a dynamic branch or a material parameter.

A render-thread race happens when game code and render code touch the same data without the engine's hand-off. Epic's documentation describes Unreal's renderer as running a frame or two behind the game thread, says the game thread can never touch a primitive's render-side proxy once it is registered, and warns that blocking the game thread until the render thread catches up causes hitches. That gives the two ways AI code goes wrong: it writes render data directly and races, or it adds a wait and quietly throws away the parallelism. A long soak test, and a run with threading forced off as a control, are the usual evidence.

Finally, an unmeasured performance claim is a statement such as "this is faster" with no capture behind it, or with one taken on a different machine, scene, build or method from the baseline. Agents make these claims fluently. Treat every one as a hypothesis until the before and after numbers come from the same profiler, the same bookmark and the same target (11.1, 11.5).

7 Versions, fallbacks and platform assumptions

The third column covers code that is right on the machine it was written on. An API and version mismatch calls a function, setting or shader macro from another engine, another version, or nowhere at all. At best the build fails. At worst the code compiles against an older path that the engine still ships but no longer uses by default, and behaves differently. Ask for the engine version in the brief, and for links to that version's documentation in the report (2.4, 12.2).

A missing fallback uses one of those features without asking whether the device has it. A hard-coded platform assumption bakes one platform's behaviour into code: a 1920 × 1080 resolution, a 60 fps time step, a texture format, eight worker threads, or a graphics API convention such as which way texture coordinates or clip-space depth run. Both pass every test on the development PC. Both are caught by the same habit: build and run every change on the weakest target the game supports, which the automated gate should do for every platform it can reach (1.4, 10.2).

8 A worked review: five planted mistakes

The shader below is the kind of lit pixel shader an agent might draft for a prop. It is short, it compiles, and it draws a plausible picture on the development PC. It also contains five of the checklist's mistakes. Try to find them before reading the callouts.

Code The shader as drafted, and the review's fixes

As drafted, in HLSL. The comments numbered (1) to (5) are the reviewer's, added to match the figure.

// Lit prop shader, as drafted by an AI agent
Texture2D    BaseMap;      // colour texture, sRGB format
SamplerState LinearClamp;
cbuffer PerFrame : register(b0) { float3 CameraPosWS; };
cbuffer PerMaterial : register(b1)
{
    float3 Tint;        float Roughness;
    float3 LightDirWS;  float Exposure;
};  // C++ fills { tint, lightDir, roughness, exposure }   (1) order differs
struct PSIn
{
    float4 posCS  : SV_POSITION;
    float2 uv     : TEXCOORD0;
    half3  posWS  : TEXCOORD1;   // (2) a world position in 16 bits
    float3 normal : TEXCOORD2;   // object space   (3) used with a world-space light
};
float4 PSMain(PSIn i) : SV_Target
{
    float3 albedo = BaseMap.Sample(LinearClamp, i.uv).rgb;
    albedo = pow(albedo, 2.2);            // (4) the sRGB format already decoded it
    float3 n = normalize(i.normal);
    float3 v = normalize(CameraPosWS - i.posWS);
    float3 h = normalize(v + LightDirWS);
    float  diff = saturate(dot(n, LightDirWS));
    float  power = 2.0 / (Roughness * Roughness) - 2.0;   // (5) infinite at roughness 0
    float  spec = pow(saturate(dot(n, h)), power);      //     pow(1, infinity) gives NaN
    return float4((albedo * Tint * diff + spec) * Exposure, 1);
}

The review's fixes, one per mistake. Each is small; finding them is the work.

// (1) One definition of the layout, included by the shader and the C++ code,
//     or C++ offset checks for 0, 12, 16 and 28 bytes.
float3 posWS    : TEXCOORD1;      // (2) full float for positions and UVs
float3 normalWS : TEXCOORD2;      // (3) the vertex shader outputs world space
float3 albedo = BaseMap.Sample(LinearClamp, i.uv).rgb;   // (4) no pow: decoded once
float  r = max(Roughness, 0.05);                       // (5) never divide by zero
float  power = 2.0 / (r * r) - 2.0;

The minimum roughness of 0.05 is an example; engines choose their own clamp. The point for review is that every division has a stated range for its divisor.

Simplified

Real engine shaders get the camera position, light data and sampling from engine include files rather than declaring them, and their lighting model is more complete than this one. The mistakes are the same in either case, and so are the questions that find them.

4 What it costs

Review costs people's time, and the time scales with the size of the change and the number of platforms it touches. The checklist does not make review free. It makes it shorter and repeatable, and it tells the team which findings justify blocking a merge.

Worked example, illustrative. An agent hands back a 300-line change to a material system. The automated gate takes 25 minutes of machine time and catches a build failure on one console, which the agent fixes. Review with the checklist takes a graphics programmer 40 minutes and finds a buffer layout mismatch and a per-frame allocation. Without the gate and the list, the same review takes over an hour and the layout bug, which looks like a lighting problem, reaches QA; finding it there costs a day of a QA tester's and a programmer's time. The 40 minutes are cheap by comparison, but only if the reviewer knows where to look.

  • Change sizeReview effort grows faster than the diff. Ask for small, staged changes.
  • PlatformsEach one adds builds, captures and fallbacks to check, and a person with hardware.
  • Shared codeConstant buffers, materials and thread hand-offs used everywhere raise the damage of every mistake.
  • Missing automationEvery check the gate does not run becomes a person's job on every change.
  • Missing evidenceA report without captures turns review into a reading exercise.

The usual trade

Teams automate the cheap rungs first: builds for every platform, validation layers, a handful of fixed-camera screenshots and pass timings. They keep the checklist short enough to use on every change, and add a question only when the same mistake has slipped through twice.

5 How it breaks

Review itself fails in recognisable ways. Each of these lets a checklist mistake through.

Approved because it compiled

Cause
The reviewer read "build passed, tests passed" as "correct". Most graphics mistakes are legal code.
Ask for
Screenshots from fixed cameras and the checklist's answers in the agent's report, as well as the build status.

A long diff, and no evidence

Cause
The brief did not ask for captures or screenshots, so the reviewer could only read code and guess what it does.
Ask for
Evidence as a deliverable in every brief: captures, timings and before-and-after images from the same bookmarks (12.2).

The checklist became a rubber stamp

Cause
Every box is ticked on every change, so ticking stops meaning anything; questions that never apply train reviewers to skim.
Ask for
A short list, answered in words for the items the change touches, and "not applicable" for the rest.

The author reviewed its own work

Cause
The same agent, with the same context and the same guesses, was asked whether its change was right.
Ask for
A separate review pass with fresh context and the checklist, then a person's review of both. Self-checks catch typos; wrong assumptions survive them.

A speed-up nobody can reproduce

Cause
An unmeasured claim, or one measured on the development PC while the frame is bound elsewhere on the target.
Ask for
Before and after numbers from the same profiler, bookmark, build and target, with the baseline attached.

Every finding is a blocker

Cause
No agreed severity, so reviews stall on cosmetic points, or the team starts waving everything through to keep moving.
Ask for
The severity grid above, agreed by leads, with "block", "fix before the milestone" or "fix when convenient" on every finding.

6 In the engines

Each engine gives reviewers switches that turn hidden mistakes into visible ones. The table lists the ones that matter for the checklist.

API validation Command-line flags: -d3ddebug (a debug device for Direct3D), -gpuvalidation (Windows only), -RHIValidation, -vulkandebug. Pick the API with -force-d3d12 or -force-vulkan, then enable that API's own debug layer, for example Direct3D 12 GPU-based validation from the DirectX Control Panel. --gpu-validation enables the API's validation layers; --gpu-abort stops on GPU errors.
Threads The renderer runs a frame or two behind the game thread. -onethread, -norenderthread and -norhithread give single-threaded control runs. The job system's safety system throws an error when two scheduled jobs write the same NativeContainer. -force-gfx-direct forces single-threaded rendering. The active scene tree is not thread-safe; use call_deferred. The Thread Model project setting runs rendering on a separate thread, with known bugs.
Shader variants Static switch parameters and material usage flags each compile extra shaders (5.6). Strict shader variant matching, so Unity does not silently replace a missing variant with another; Log Shader Compilation in development and debug builds. Fewer variants by design: specialisation constants and ubershaders (5.6).
16-bit precision Half-precision maths in targeted mobile materials and passes, new in 5.8 (10.2). half is 32-bit on higher-performance platforms by default; Shader Precision Model set to Uniform uses 16 bits more widely. Precision qualifiers lowp, mediump, highp; the documentation advises avoiding them unless necessary, because mobile drivers can behave inconsistently.
Versioned docs Pages take ?application_version=5.8 in the address to show that version. docs.unity.com pages carry the version in the path, such as /engine/6000.6/. docs.godotengine.org pages carry it too, such as /en/4.7/.

7 Say it to your AI

Two briefs: one makes the agent check its own change against the checklist before it reports, the other asks a second, fresh review pass to look for the checklist's mistakes without fixing anything.

Self-check before reportingAppend to any graphics brief
Before you report back, check your change against each item below. For each, answer in one line: "not touched", or what you checked and how.

1. Colour space: every colour texture decoded once, output encoded once. Name the texture import settings and target formats involved.
2. Coordinate spaces: every vector named by its space (WS, VS, OS, CS); no dot product mixes spaces.
3. Axes: which up axis and handedness you assumed, and where any conversion happens.
4. Buffer layouts: every constant buffer and vertex layout you changed, with the byte offset of each field on the CPU and in the shader.
5. Precision: no positions or UVs in half; every division and normalize safe at zero.
6. Allocation: nothing allocated per frame.
7. Shader variants: the variant count before and after.
8. Threads: which thread touches each piece of data you changed.
9. Versions: links to [engine and version] documentation for every API you used.
10. Fallbacks and platforms: what runs on [weakest target] and [platforms without feature X].
11. Performance: every speed claim with before and after numbers, same scene and method.
  • The agent answers the questions a reviewer would ask, in a form that is quick to check.
  • "Not touched" keeps the list honest and short.
  • Byte offsets and variant counts are facts a reviewer can verify in a capture.
Second review passUse with fresh context on a finished change
Review the diff below as a graphics programmer. Do not change any code.

Context: [engine and version], [render pipeline], targets [platforms].

Look only for these problems: colour-space mix-ups, coordinate-space mix-ups, handedness or up-axis errors, CPU and shader buffer layouts that disagree, half precision for positions or UVs, divisions or normalize calls that can produce NaN, per-frame allocations, new shader variants, data shared between the game and render threads, APIs that do not exist in our version, missing fallbacks, and hard-coded platform assumptions.

Questions to ask when reviewing AI-written graphics code

  1. What did the agent run, on which platforms, and what did it not test?The report tells you which rungs of the ladder are still yours.
  2. Where is each colour decoded and encoded, and does each happen once?The most common legal mistake, and cheap to check.
  3. Is every vector named by its space, and does every buffer have one definition both sides share?Naming and sharing turn invisible mismatches into visible ones.
  4. What happens at zero, far from the origin, and on the weakest target?NaN, precision and fallback bugs hide at the edges.
  5. Which claims come with a capture, and was it taken the same way as the baseline?An unmeasured claim is a hypothesis, however fluent.

8 Check yourself

  1. After an AI change, every prop in the game looks darker and more saturated than its texture in the art tool. The build is clean and the tests pass. Which checklist item do you suspect first, and what is the cheapest test?

    Show answer

    A colour-space mix-up, most likely a colour decoded twice: the texture's sRGB format decodes it on sampling and the shader applies pow(c, 2.2) again. The cheapest test is a scene with grey and coloured swatches of known values, compared against a golden image, plus a search of the diff for 2.2.

  2. A new shader looks perfect on every desktop in the studio, and the highlights on props shimmer and step on phones, worst in the far corners of the map. What would you look for in the diff?

    Show answer

    A precision problem: a world position or texture coordinate stored in half. On desktop, Unity runs half as a 32-bit float by default, so the bug only appears where 16 bits are real. Far from the origin a half float moves in steps of tens of centimetres. Positions and UVs should be full float.

  3. An agent reports that its change makes the shadow pass "about 2 ms faster" and attaches a capture from the development PC. The target is a console. What do you ask for before accepting the claim?

    Show answer

    Before and after captures on the console, from the same bookmark, build and profiler, measured the same way as the baseline in the brief. Until then it is an unmeasured performance claim: the development PC may be bound by something else, and the change may even be slower on the target.
