2 In plain words

A game shows a moving world by drawing still pictures very quickly, one after another. Each picture is a frame. Drawing pictures fast enough to keep up with the player is called real-time rendering. A film studio can spend hours of computer time on one frame of an animated film. A game running at 60 frames per second gets about 17 thousandths of a second.

Everything a game draws is built from assets: models, textures, materials, animations, sounds and levels, made by artists and designers in their own tools and then brought into the engine. Before the game ships, the engine converts every asset into a form the hardware can use directly. Then, in every frame, two processors share the work. The CPU works out what has changed and what the camera can see, and lists what to draw. The GPU turns that list into millions of coloured pixels.

Everyday comparison

A busy restaurant does its slow work before the doors open: deliveries unpacked, vegetables chopped, sauces made. During service the head chef reads each order and calls out tickets, and a line of cooks plates dozens of dishes at once.

The prep is import and cooking. The head chef is the CPU, each ticket is a draw call, and the line cooks are the GPU's thousands of small cores.

The problem it solves

A frame has only a few milliseconds. Splitting the work keeps that per-frame work small. Anything that does not change during play, such as converting file formats or compressing textures, is done once, in the studio.

What is left for each frame is the work that depends on where the player is and what they just did.

Why a lead cares

Almost every graphics decision is a choice about where on this route work happens and how often. Moving work out of the frame and into the studio is the most common optimisation in games. And when something looks wrong, the most useful first question is which stage it belongs to: a crate of the wrong size is an import problem, a missing one is often a culling problem, a magenta one is a material problem. Naming the stage sends the bug to the right person, or gives an AI the right context.

3 How it works

Follow the crate along the route. There are eight steps. The first two are about work done before anyone plays; the rest happen in every frame.

1 From art tool to asset

A 3D artist builds the crate in a modelling tool such as Blender, Maya or 3ds Max. They shape it from flat faces, unwrap its surface so a flat image can be wrapped around it, and paint its wood and metal bands. The source file holds far more than a game needs: named parts, modifier stacks, edit history, paint layers.

To move it to the engine, the artist exports it to an exchange format such as FBX or glTF, with its textures as image files. The engine imports those files. Import is where the crate becomes an asset in the engine's sense: a mesh made of triangles, one or more textures, and a material that says how to draw them. When the game is built for a platform, a second step called cooking converts every asset into the exact formats that platform reads fastest: textures compressed in the GPU's own formats, meshes laid out as vertex buffers and index buffers. 1.3 The content pipeline covers this route in detail.

2 Two clocks: once, and every frame

From here the route runs on two very different clocks. Import and cooking happen once per change to an asset, on an artist's machine or a build server, and can take minutes. Everything after the scene runs again in every frame while the game is played, and must finish within a few milliseconds.

That split is the main lever a renderer has. Lighting that never changes can be calculated once and stored, which is called baked lighting. Texture compression happens at cook time because it is far too slow to do per frame. When someone says a feature is expensive, the first thing to ask is which clock it runs on.

3 The scene and the update

While the game runs, the crate is one object in a scene: the engine's list of everything in the level, each with a position, a rotation and a size, plus the lights and the camera. The same crate mesh can appear a hundred times; each copy is one more entry pointing at the same mesh and material.

Every frame starts by updating that scene. The engine reads the controller, runs the game's rules, steps the physics simulation and advances animations, so that everything is in its new place before anything is drawn. This cycle of update and draw is the game loop. 0.2 What a frame is introduces it and 2.2 The game loop and threads goes inside it.

4 Culling and draw calls

A level can hold tens of thousands of objects, but the camera sees only some of them. Before drawing anything, the CPU throws away objects that cannot appear in this frame: anything behind the camera, outside its view, or hidden behind a wall. This is culling, and 4.4 Culling covers how engines do it quickly.

For each object that survives, the CPU records a draw call: a command telling the GPU to draw this mesh, with this material, at this position. The commands go into a list that the GPU works through in order. Each draw call costs CPU time to prepare, so a scene made of thousands of small separate objects can run out of CPU time while the GPU sits idle. 4.3 Draw calls, batching and instancing covers how engines need fewer of them.

5 Two processors, one frame

The CPU and the GPU are built for different jobs. A CPU has a handful of large cores, each good at complicated work full of decisions: game rules, physics, choosing what to draw. A GPU has thousands of small cores that all run the same short program at once, each on a different vertex or pixel. 3.5 CPU, GPU and graphics APIs explains the hardware.

They talk in one direction. The CPU writes commands into a queue and the GPU works through them, usually about a frame behind. Neither waits for the other unless it must. That is why every frame has a CPU time and a GPU time, and why a game can be slow for two completely different reasons.

6 On the GPU: from corners to pixels

The crate's mesh already sits in the GPU's own memory, VRAM, copied there when the level loaded. When its draw call arrives, the GPU runs the vertex shader, a small program, once for each corner. It works out where that corner lands on the screen, given where the crate is and where the camera is looking.

The rasterizer, a fixed part of the GPU, then takes each triangle's three screen positions and finds every pixel whose centre the triangle covers. Triangles that face away from the camera are dropped just before this step by backface culling. A cube never shows more than three of its six faces at once, so at least 6 of the crate's 12 triangles go no further.

Finally the pixel shader runs once for every covered pixel and decides its colour. It reads the wood colour from the crate's texture, works out which way the surface faces, and adds up how much light reaches it from the sun and the sky, minus any shadow. Part 6 covers materials, Part 7 lights and shadows, and Part 8 the light that bounces between surfaces.

Simplified

GPUs actually shade pixels in 2 × 2 blocks and may shade some pixels more than once where triangles overlap, so the real count of pixel shader runs is higher than the covered pixels. 5.4 Pixel shaders and overdraw covers both effects.

7 A frame is a series of passes

So far the crate has been drawn once. A real frame draws the scene several times, each time into a different image, and later steps read what earlier steps wrote. Each of these steps is a render pass. The shadow pass draws the scene from the sun's point of view to record what the sun can see. A depth or G-buffer pass records each pixel's distance and surface properties. The lighting pass combines those into lit colour. Transparent objects, post-processing and the user interface follow, and the finished image is handed to the display.

Simplified

This order is typical of deferred rendering. Forward rendering lights each object as it draws it and has no G-buffer pass, and mobile renderers merge passes to save memory traffic. 7.3 Forward, deferred and clustered compares them.

8 Sixty times a second

When the last pass finishes, the image waits for the display's next refresh and then appears. Then the whole runtime part of the route starts again. At 60 frames per second the CPU and the GPU each get about 16.7 milliseconds per frame.

To keep both busy, they work on different frames at the same time, like stations on an assembly line. While the GPU draws frame 1, the CPU is already updating and culling frame 2. The cost is delay: the image you see started its journey a frame or two earlier. 0.2 What a frame is covers frame rates, budgets and what happens when a frame runs late.

4 What it costs

The route has two kinds of bill. Work in the studio costs people-time and build-machine time, paid once per change. Work in the frame costs milliseconds, paid again in every frame on every player's machine.

In proportion

Across a whole frame, the crate's pattern holds. Object counts drive CPU time, and resolution and per-pixel effects drive GPU time. When a game misses its frame rate, the first question is which of the two processors ran out of time; 11.1 Frame budgets shows how to find out.

5 How it breaks

Most visual bugs belong to one stage of the route. Naming the stage narrows the search to one tool, one team and one part of this book. Here are five common ones, from early in the route to late.

Giant, tiny or lying on its side

Cause
Stages 2 and 3. The art tool and the engine disagree about units or about which axis points up. Unreal works in centimetres with Z up. Unity expects 1 unit to be 1 metre, with Y up. Godot works in metres with Y up.
Ask for
The export settings and the engine's import scale and axis options, checked against a reference cube of known size.

A flat, bright magenta object

Cause
Stages 3 and 9. The engine could not run the object's material. Unity draws objects in magenta when there is no material, the shader does not compile, or the shader is not supported, often because it was made for a different render pipeline.
Ask for
The shader errors in the console, and whether the material was written for the project's render pipeline.

Objects vanish near the edge of the screen

Cause
Stage 5. Culling tests a simple box around each object, its bounds. If the bounds are smaller than the shape, often because a shader or animation moves the shape, the CPU culls an object that is still partly visible.
Ask for
A debug view of the object's bounds, and bounds that include everything animation or shaders can do to the shape.

Washed-out or muddy colours

Cause
Stages 3 and 10. A colour texture is treated as plain data, or the other way round, or the image is adjusted twice at the end. 3.2 Colour done right explains colour spaces.
Ask for
The colour-space setting of each texture involved, and a list of every step that changes the final image's brightness.

A freeze the first time something appears

Cause
Work that should happen before play happens during it: a shader compiled, or an asset loaded, the first time it is needed. One frame takes far longer than the rest, a hitch.
Ask for
A profiler capture of the slow frame, and a plan to prepare shaders and assets during loading.

To see which stage a problem sits in, look inside one frame with the engine's frame debugger or an external frame capture tool such as RenderDoc. Both list every pass and draw call in order.

7 Say it to your AI

The route gives you a shared map. Use it to ask an AI for a picture of your own project, and to keep bug hunts in the right stage. Adapt these.

BriefUse when starting or joining a project
Engine: Unreal Engine 5.7. Platforms: PC and PlayStation 5. Target: 60 fps.

Map this project onto the route from art tool to screen, as a table with one row per stage: art tools, export format, import settings, cooking, scene setup, update, culling, draw calls, render passes, post-processing, display settings.

For each stage, list the project settings, plugins and folders that control it, the role on a typical team that owns it, and the tool we would use to inspect it. Mark anything you are unsure of instead of guessing.
  • Engine, platforms and frame-rate target fix the context.
  • One row per stage gives you a map you can check against the project.
  • Asking it to mark uncertainty stops confident guesses about settings it cannot see.
Bug reportUse when an asset looks right in the art tool and wrong in the engine
Unity 6.6, URP. A crate exported from Blender as FBX appears 100 times too large and lying on its side, and its texture looks washed out. In Blender it looks correct.

Work through the route in order: the Blender export settings, the model import settings (scale, units, axis conversion), the texture import settings (colour space), then the material. For each stage, say what to check, what correct looks like, and how to confirm the fix. Do not change project-wide settings without asking.
  • Saying it looks right in Blender points the search at export and import.
  • Asking for the stages in order stops the AI jumping to one guess.
  • The last line protects settings that other assets rely on.

Questions to ask about any graphics change

  1. Which stage of the route does this change touch?It tells you which tool, which team and which chapter to involve.
  2. Is this work done once, at import or cook time, or in every frame?Per-frame work costs milliseconds for as long as the game runs.
  3. Does it run on the CPU or the GPU, and per object, per vertex or per pixel?That decides what makes it more expensive: object count, vertex count or resolution.
  4. Which render passes does it add or change?Every extra pass redraws or reprocesses part of the frame.
  5. How will we see the result in a frame capture or the profiler?A change you cannot measure is hard to review.

8 Check yourself

  1. A crate looks right in Blender but is enormous in the engine. Which stages of the route do you check first?

    Show answer

    Export and import, where units and the up axis are converted. Then check the object's scale in the scene. The GPU stages draw whatever size they are given.

  2. The crate covers about 25,000 pixels on screen and has 24 vertices. Which GPU program runs more often for it, and by roughly how much?

    Show answer

    The pixel shader, about a thousand times more often: roughly 25,000 runs against 24 for the vertex shader.

  3. An engineer proposes compressing textures on the player's machine at startup instead of when the build is made, to speed up builds. Which clock does that move the work onto, and what do you ask?

    Show answer

    It moves cook-time work onto the player's machine, at load or during play. Ask how much loading time it adds, whether it can cause hitches during play, and whether the result matches what the cooker produced.
