2.2 The game loop and threads

Every frame, an engine reads input, updates the game and draws the result, and it spreads that work over several threads and the GPU so they all run at once. That overlap is what makes high frame rates possible. It is also where input latency and hitches come from.

1 The picture

2 In plain words

A game is a loop. Each pass through it reads the controller, moves the world forward a little, and draws a picture of the result. 0.2 What a frame is called that the game loop, and one pass through it a frame. At 60 frames per second, each pass has 16.7 milliseconds.

Done one step at a time on one processor, that budget runs out fast. So engines split the loop into stages and run the stages at the same time on different frames. One CPU thread updates the game, another prepares the drawing, and the GPU draws. This is pipelining. The slowest stage sets the frame rate, and each frame takes longer from start to finish than one frame's time.

Everyday comparison

A launderette with a washer, a dryer and a folding table. With one load at a time, each load takes wash plus dry plus fold. Run all three at once on different loads and a clean, folded load comes out every time the slowest machine finishes.

But any single load still spends the whole wash, dry and fold time in the building, plus any time it sits in a basket waiting for the dryer.

The problem it solves

Game logic, preparing the drawing and the drawing itself each take several milliseconds. Done one after the other, they add up. Overlapped, the game runs as fast as its slowest stage allows, and every CPU core and the GPU stay busy.

The price is delay. A button press made now shows up a few frames later, and the deeper the pipeline, the later.

Why a lead cares

Frame rate and responsiveness are two separate numbers, and you can improve one while making the other worse. When someone says "we're GPU-bound" or "it's the game thread", they are naming the lane that sets the pace, and that decides who on the team can fix it. A profile that shows only fps cannot tell you which lane that is.

3 How it works

Start with one thread and one frame, then add a fixed physics rate, more threads, the GPU's queue and worker cores. Eight steps.

1 Update, and the time since the last frame

The heart of each frame is the update, also called the tick. The engine reads input, then calls every object that wants it: the player character, enemies, doors, timers. Unreal calls this Tick, Unity Update, Godot _process.

Frames never take exactly the same time, so each update receives the delta time: how long the previous frame took. A car moving at 30 metres per second moves 30 × 0.0167 = 0.5 m in a 60 fps frame and 1 m in a 30 fps frame. Multiplying by delta time keeps the speed the same on every machine.

For gameplay, that is enough. For physics it is not. A big delta time means a big jump, and a big jump can skip straight past a thin wall.

2 A fixed timestep for physics

Physics engines are stable and repeatable only when every step is the same length. So engines run physics on a fixed timestep: Godot steps 60 times a second by default, Unity 50. Each frame adds its real elapsed time to a running total and runs as many fixed steps as fit. A 144 fps frame often runs no physics step at all; a 30 fps frame runs two.

That creates a new problem. If the display shows 144 frames a second but physics only moves things 60 times, some frames show the same position as the frame before, then the object jumps. The cure is physics interpolation: keep the last two physics states and draw each object part of the way between them, by how far the frame lies between the two steps.

Code The fixed-timestep loop in twelve lines

This is the pattern from Glenn Fiedler's article "Fix Your Timestep!", which most engines follow. The renderer produces time; physics consumes it in fixed steps.

const STEP = 1 / 60;              // physics step: 16.7 ms
let accumulator = 0;
let previous = state, current = state;

function frame(dt) {                // dt: real time since the last frame
  accumulator += Math.min(dt, 0.25); // clamp, or a long hitch snowballs
  while (accumulator >= STEP) {
    previous = current;
    current = physicsStep(current, STEP);
    accumulator -= STEP;
  }
  const alpha = accumulator / STEP;   // 0 to 1: how far between steps
  draw(interpolate(previous, current, alpha));
}

When reviewing code like this, check that physics and anything that must be repeatable runs inside the while loop with STEP, that drawing uses the interpolated state, and that the clamp exists.

3 The game thread and the render thread

The update runs on the game thread, which most engines call the main thread. In a simple engine the same thread then walks the scene and prepares the drawing. Larger engines hand that second job to a render thread, so the two run side by side on different CPU cores: the game thread updates frame N+1 while the render thread prepares frame N.

Two threads must never change the same data at the same moment. So at the end of each update the game thread copies what the renderer needs, such as each object's mesh, material and position, into a separate snapshot. The render thread reads only that. Unreal's documentation describes its renderer as running a frame or two behind the game thread, with the game thread waiting at the end of each tick if it gets too far ahead.

4 Handing work to the GPU

The render thread does not draw anything itself. It records a command buffer: a list of instructions such as "use these settings, read this mesh, draw 5,400 triangles", thousands of them per frame. Then it submits the list to a GPU queue and moves on. The GPU works through the queue in order, as fast as it can.

Unreal adds a third CPU thread here. Its render thread records platform-neutral commands, and an RHI thread translates them into DirectX 12, Vulkan or Metal calls through the RHI from chapter 2.1, and submits them. Unity and Godot do that translation on their render or main thread, sometimes helped by worker threads.

The queue has a limit. If the CPU could run arbitrarily far ahead, a GPU-bound game would pile up frames, each one older than the last. Engines cap the number of frames in flight, typically at 2: Unity's QualitySettings.maxQueuedFrames defaults to 2 on PC, and Godot's frame_queue_size to 2. When the queue is full, the CPU waits.

5 Who sets the frame rate

Put the three lanes together and each frame moves along them like a car on an assembly line. When every lane has its own frame to work on, the time between finished frames is set by the slowest lane alone. If the GPU needs 14 ms and the CPU threads need less, the game runs at 1000 ÷ 14 = 71 fps and is GPU-bound. If the game thread needs 20 ms, it is CPU-bound at 50 fps, and a faster graphics card changes nothing.

The faster lanes wait. A GPU-bound game's game thread spends part of every frame stalled, waiting for room in the queue; a CPU-bound game's GPU sits idle. Those waits are what profilers show when you look at the threads side by side.

Try it. Slow down one lane at a time and watch the limit move. Switch to one thread at a time and see the frame rate drop while the latency in frames falls to one. Turn on the hitch to see a single slow update ripple through the lanes after it, then add low-latency mode: the queued frames that added latency were also hiding part of the hitch, and without them the longest frame grows from 38 ms to 59 ms.

Simplified

The demo's lanes each take the same time every frame, and the display is left out. Real frames vary, vsync makes the GPU wait for the screen's refresh, and engines differ in exactly where threads wait for each other. The shape is the same: the slowest lane sets the pace, and queued frames add delay.

6 Spreading the work over cores

A modern CPU has 8 or more cores, and the game and render threads use two. The rest are filled by a job system. Systems split their work into small independent jobs, such as "animate these 50 characters" or "test these 1,000 objects against the camera", and a pool of worker threads, about one per core, runs them in parallel.

The catch is the sync point. The game thread must wait for every job's results before it uses them, so the slowest job and any work that cannot be split, such as most gameplay scripts, set the floor. Unity's job system and Burst compiler, Unreal's Tasks System and Godot's WorkerThreadPool are all versions of this.

7 From input to photon

Frame latency, or input latency, is the time from pressing a button to seeing its effect on screen. Add up the stages. The press waits for the next update to read it, then rides through the game thread, the render thread and the GPU, then the display scans the image out from top to bottom.

At 60 fps with every stage taking a whole frame, that is about 67 ms, roughly four frames. Each frame that waits in the GPU queue adds another 16.7 ms. Unreal's documentation gives a worst case of up to 130 ms for a 30 fps game with its default syncing, and about 66 ms, two 30 Hz frames, as the best case with its low-latency mode.

8 What a hitch does

A hitch is one frame that takes far longer than the rest: a file read on the game thread, a burst of garbage collection, a shader compiled on first use. Players feel it as a freeze or a stutter even when the average frame rate looks fine.

Everything downstream feels it too. The render thread and the GPU run out of work and the screen keeps showing the last frame. Then the fixed timestep tries to catch up on the missed time by running several physics steps in one frame, which makes that frame slower as well. If each catch-up step costs more time than it covers, the game falls further behind every frame: Glenn Fiedler named this the spiral of death. Engines cap the catch-up to stop it.

4 What it costs

With pipelining, each lane gets the whole frame budget to itself. At 60 fps the game thread has 16.7 ms, the render thread has 16.7 ms and the GPU has 16.7 ms, all at once. What you pay is latency, and a little memory.

What makes the cost grow

  • Frames in flightEach extra queued frame adds a whole frame of latency, and another copy of every per-frame buffer.
  • Sync pointsEvery place a thread waits for another, or for jobs to finish, is time no work gets done on that thread.
  • Physics rateGodot's documentation notes that CPU use scales roughly with the physics tick rate. Doubling it to 120 Hz doubles the physics cost.
  • Work that cannot be splitSingle-threaded gameplay code sets a floor that more cores cannot lower.

The usual trade

Competitive and rhythm games trade a little frame rate for less latency: fewer frames queued, low-latency modes, sometimes a frame cap just below what the GPU can do. Cinematic games usually take the extra frames of latency for a stable frame rate. Decide which yours is before anyone tunes the queue.

5 How it breaks

Timing and threading bugs are hard to see in a screenshot and easy to feel in the hands. Learn these six and you can usually name the cause from a description.

The game runs faster on faster machines

Cause
Movement or timers advance by a fixed amount per frame instead of being multiplied by delta time.
Ask for
A search for per-frame changes that ignore delta time, and a test that runs the same input at 30 and 144 fps and compares positions.

Fast objects pass through walls

Cause
Physics stepped with a large or variable delta time, or a fast, thin object without continuous collision detection.
Ask for
Physics moved to the fixed step, the step rate and the object's speed per step compared with the thinnest thing it can hit, and continuous collision on fast objects.

Stutter on high-refresh displays

Cause
Objects moved by physics at 50 or 60 Hz, drawn at 120 or 144 Hz without interpolation, or a camera updated on a different step from what it follows.
Ask for
Physics interpolation on moving bodies, and the camera and its target updated on the same step.

Controls feel heavy at a good frame rate

Cause
The game is GPU-bound and the CPU runs several frames ahead, so every frame waits in the queue.
Ask for
Measured input latency, the number of frames queued, and a test of the engine's low-latency options, such as fewer queued frames or NVIDIA Reflex.

Hitches, or a spiral of death

Cause
Loading, allocation or compilation on the game thread; or physics catch-up that costs more than it covers, so frames keep getting slower.
Ask for
A capture of the slow frame with every thread visible, the work moved off the game thread or ahead of time, and the catch-up cap checked.

Flicker, or a crash once a week

Cause
Two threads touch the same data without a handoff: game code changing something the render thread or a job is reading.
Ask for
Which thread owns each piece of shared data, how changes are handed over, and a run with the engine's thread-checking or a thread sanitizer.

To confirm any of these, look at all the threads together, not only the frame rate. Unreal's stat unit, Unity's Profiler timeline and Godot's Profiler each show time per thread or per stage; frame capture tools show the GPU side.

Changing the defaults

Unreal's forums report freezes and corrupted animation data with some combinations of its low-latency settings, and Godot labels its separate render thread experimental. Change these settings on a branch, measure, and test on every platform before shipping them.

7 Say it to your AI

Good briefs about frame timing give per-thread numbers, not just fps, say which thread code runs on, and ask for measurement before and after. Adapt these.

BriefUse when the frame rate is low and nobody agrees why
Engine: Unreal Engine 5.9, PC, DirectX 12. Target: 60 fps.
In our forest level, stat unit shows: Frame 21 ms, Game 9 ms, Draw 7 ms, RHIT 8 ms, GPU 20 ms.

1. Tell us which lane limits the frame rate, and what in these numbers shows it.
2. List the three most likely causes in that lane for a dense forest, and how to confirm each with Unreal Insights or a GPU capture.
3. For each fix, estimate the saving in ms and say which other lane it might move the cost to.
Do not change gameplay code or engine source.
  • Per-thread numbers let the AI reason about the bottleneck instead of guessing.
  • Asking for confirmation steps keeps it from jumping straight to fixes.
  • Costs move between lanes; asking where they go avoids a fix that only shifts the problem.
Bug reportUse when motion stutters or objects pass through things

On a 144 Hz monitor the car visibly stutters. When the frame rate drops below 30 fps in busy scenes, the car sometimes passes through the thin crash barriers.

Find the causes. For each: explain it in terms of the fixed timestep and the frame rate, propose the change (interpolation, step rate, collision detection mode, or code moved between Update and FixedUpdate), and state its CPU cost. Tell us how to verify the stutter fix at 144 Hz and the barrier fix at 25 fps.
  • Stating the step rate and the display rate points straight at interpolation.
  • Tying the tunnelling to low frame rates points at step size and collision mode.
  • Asking for cost stops a blanket "raise the physics rate" answer.

Questions to ask when reviewing timing and threading code

  1. Which thread does this code run on, and which data does it share with other threads?Unsynchronised sharing causes the rarest and worst bugs.
  2. Does movement use delta time, and does physics-related code run on the fixed step?Mixing them up makes behaviour depend on the frame rate.
  3. Does this add a wait in the middle of the frame: a job completed early, a flush, a read back from the GPU?Every wait is time a thread does nothing.
  4. Does it change how many frames are queued, or where threads sync?That changes input latency, often silently.
  5. How was the improvement measured: per-thread times and worst frames, or only average fps?Averages hide hitches and moved costs.

8 Check yourself

  1. The game thread takes 8 ms per frame, the render thread 6 ms and the GPU 14 ms, all pipelined. What is the frame rate, and does optimising the game thread to 5 ms help?

    Show answer

    About 71 fps (1000 ÷ 14), limited by the GPU. Making the game thread faster does not raise the frame rate; it only makes the game thread wait longer each frame.

  2. Physics runs at 60 Hz and the game renders at 144 fps. How many physics steps run per frame, and why might motion look jerky?

    Show answer

    Zero or one, about 0.42 on average. Without interpolation, a moving body is drawn at the same position for two or three frames, then jumps, so motion stutters. Physics interpolation fixes it at the cost of up to one physics step of delay.

  3. Your game holds a steady 60 fps, but players say aiming feels sluggish. The profiler shows the GPU busy all frame and the game thread waiting. What do you ask for?

    Show answer

    A measurement of input latency and frames queued, then a test of fewer queued frames or the engine's low-latency mode, such as NVIDIA Reflex, or a frame cap slightly below what the GPU can sustain. The game is GPU-bound, so frames wait in the queue and each one is older by the time it is shown.
