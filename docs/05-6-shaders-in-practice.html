5.6 Shaders in practice

Real shaders are short programs in a C-like language, multiplied into many compiled variants and bundled with fixed GPU settings into pipeline objects, then run pass by pass through the frame. How a team writes, multiplies and compiles them decides build times, memory and whether the game hitches the first time an effect appears.

1 The picture

2 In plain words

A shader is a small function the GPU runs thousands of times at once, once per vertex, pixel or work item. Programmers write it as text in a shader language, or artists build it in a node editor that writes the text for them. Before the game can use it, it is compiled, usually many times over, into versions for each feature combination, each pass and each graphics API.

A compiled shader is never used alone. The GPU needs it bundled with the fixed settings from 5.5, such as depth test and blend mode, into a pipeline object, and creating that bundle is slow. And each shader runs inside a render pass, one step of the frame that reads some images and writes others. A frame is a chain of a few dozen of those.

Everyday comparison

A restaurant chain writes each recipe once, in one house style, then prints it for every kitchen it runs, in each kitchen's own format. Every option on the menu doubles the cards: with or without nuts, mild or spicy, small or large. Before a dish can be cooked, a station has to be set up for it, with the right pans, oven temperature and garnish tray. Setting up a station in the middle of dinner service makes that table wait. The kitchen's ticket board says which station hands which tray to which, and in what order.

The problem it solves

Recipes are shader source code, kitchens are graphics APIs and GPUs, menu options are shader variants, station set-up is pipeline creation, the wait is a hitch, trays are render targets and the ticket board is the frame graph.

The craft is keeping the card count down, setting up stations before service starts, and keeping the ticket board honest so nothing is cooked that no one eats.

Why a lead cares

Shaders are where art direction meets engineering cost. Every switch an artist adds to a master material can double its compiled versions, which shows up as hours of build time, gigabytes of cache and memory, and hitches for players. Shader compilation stutter has been a widely reported problem in PC releases, enough that Epic, Unity and the Godot project have each built systems to fight it. And as more rendering is built as passes in a frame graph, adding an effect becomes a question of what it reads, what it writes and when, which is something you can review without reading shader code.

3 How it works

Nine steps: the languages and how one source reaches every platform, what a shader reads, node-based authoring, variants, pipeline objects, compile stutter, render targets and passes, frame graphs, and compute shaders.

1 Shader languages and cross-compilation

Two languages dominate. HLSL, Microsoft's High-Level Shader Language, is the language of Direct3D, and Unreal and Unity use it for every platform. GLSL, the OpenGL Shading Language from the Khronos Group, serves OpenGL, phones and WebGL, and can also target Vulkan. Both look like C with built-in vector types such as float3 or vec3. Apple's Metal has its own language, and Godot has its own shading language, close to GLSL.

A game ships on several graphics APIs, and each wants its own format. Shader cross-compilation turns one source into all of them. Microsoft's DXC compiler turns HLSL into DXIL for Direct3D 12 and into SPIR-V, the Khronos format that Vulkan drivers read. SPIRV-Cross turns SPIR-V back into Metal's language or GLSL, and Apple's Metal shader converter turns DXIL into a Metal library. On the player's machine, the driver then compiles the result once more into that GPU's own instructions, as 3.5 CPU, GPU and graphics APIs described.

2 What a shader reads: inputs, constants, textures

The shader in the picture reads three kinds of data. Inputs change from pixel to pixel: the vertex shader writes values at each corner and the rasterizer blends them across the triangle. Textures are images the shader can sample anywhere. And constants are values that stay the same for the whole draw.

Constants live in a constant buffer, called a uniform buffer in Vulkan and OpenGL: a small block of memory the CPU fills before the draw. Engines group constants by how often they change, because updating them costs CPU time for every draw. Camera and sun go in a per-frame buffer, updated once. Material settings go in a per-material buffer. The object's position goes in a per-object buffer that changes with every draw call.

Code The same constants in HLSL, with the packing rule that catches people out

HLSL packs constant buffer members into 16-byte rows, and a value cannot straddle two rows. The CPU code that fills the buffer must lay out its bytes the same way, or every value after the first mismatch is read from the wrong place.

cbuffer PerObject : register(b2)
{
    float4x4 World;       // bytes 0 to 63: four full rows
    float3   TintRGB;     // bytes 64 to 75
    float    Fade;        // bytes 76 to 79: fills the rest of that row
    float2   UVOffset;    // bytes 80 to 87: starts a new row
};

When reviewing shader and engine code together, check that each constant buffer is declared once and shared, or that a test compares the two layouts. A mismatch gives wrong colours or positions, never an error.

3 Shader graphs: node-based authoring

Many of the material shaders in a modern game are never typed by hand. Artists build them in a shader graph, a node editor where boxes such as "sample texture", "multiply" and "lerp" are wired into the inputs of a surface: base colour, roughness, normal and so on. Unreal calls it the Material Editor, Unity calls it Shader Graph and Godot calls it Visual Shader. The engine writes ordinary shader code from the graph and compiles it like any other.

Graphs put look development in artists' hands, which is why every engine has one. They also make it easy to build a 400-node material without seeing its cost. Every engine can show the generated code, and Unreal's Material Editor shows a per-material instruction count in its Stats panel. A technical artist usually owns a small set of master materials, and other artists make instances of them that change parameters but not the graph.

4 Variants: why one shader becomes thousands

A branch decided before compilation costs nothing when the shader runs, so engines turn feature switches into separately compiled versions. Each version is a shader variant, also called a permutation. One on/off switch makes 2 variants, two make 4, five make 32. The count doubles with every independent switch, then multiplies again by the passes the material is drawn in, the kinds of mesh it is used on, the quality levels and the graphics APIs.

The alternatives are to keep a branch inside one shader and decide it at run time, a dynamic branch, or to build one large ubershader that handles many features this way. Fewer compiles, but every pixel pays a little for the flexibility. Unity exposes the choice directly: a keyword declared with shader_feature compiles only the combinations materials in the build use, multi_compile compiles every combination, and dynamic_branch keeps one program with a run-time branch. In Unreal, static switch parameters and the material's mesh usage flags multiply its variants; Epic's documentation notes that each "Used with" flag compiles extra shaders.

Simplified

Not every switch is independent. Engines prune combinations that cannot occur together, deduplicate identical results and strip variants for features a project has turned off. Real counts are therefore lower than the raw product, but they still grow with it.

5 Pipeline state objects

Direct3D 12, Vulkan and Metal do not let a draw pick its shaders and settings one by one. The engine bundles them in advance into a pipeline state object (PSO): the compiled shaders together with the fixed settings they will run with. Creating one is when the driver does its final compile, because the best machine code depends on all the settings at once.

Each variant from the previous step can need several PSOs, one per combination of settings it is drawn with. Godot's documentation puts it plainly: each shader can have dozens of pipelines. A large game has tens of thousands.

6 Compile stutter and PSO caching

If the engine creates a PSO the moment a draw first needs it, the driver compiles it right there, inside the frame. The frame runs long and the game visibly freezes. That is shader compilation stutter: a hitch the first time an effect, a material or an enemy appears, which often disappears on the second playthrough because the driver keeps compiled pipelines on disk, then comes back after a driver update clears that cache.

The fixes all move the work earlier, which is what a PSO cache in the broad sense does. Record which PSOs the game uses during play-testing and ship that list, so they can be created during loading. Or work out the likely PSOs automatically when content loads and compile them in the background, which is Unreal's PSO precaching. Or draw with a slower, general shader until the optimised one is ready, which is Godot's ubershader approach.

7 Render targets and render passes

Most of what a GPU draws never reaches the screen directly. A render target is an image the GPU draws into: a shadow map, a G-buffer layer, an HDR colour buffer, the depth buffer. Each has a size and a format, and later passes read it like a texture. A frame is a sequence of render passes, each running its shaders with some render targets as inputs and others as outputs.

8 Frame graphs

Hand-wiring that chain gets fragile as features are added. A frame graph, also called a render graph, makes the wiring explicit. Each pass declares which render targets it reads and writes; the engine collects the declarations for the frame, then works out the rest. Frostbite's FrameGraph, presented at GDC in 2017, made the idea widespread; Unreal's version is the Render Dependency Graph (RDG), and Unity's URP has a render graph system.

For a lead, the practical effect is that adding a feature becomes a reviewable change: a new pass, the targets it reads, the targets it writes. Engines ship viewers for the graph, Unity's Render Graph Viewer and Unreal's RDG Insights among them, that show every pass, every target and which passes were culled or merged.

9 Compute shaders and dispatch

A compute shader is a GPU program with no triangles attached. Instead of being run once per covered pixel, it is run over a grid of threads that the engine asks for directly, called a dispatch. The threads are organised in a thread group, a block such as 8 × 8 that runs together on one compute unit and can share a small, fast memory. Post-processing, ambient occlusion, lighting in deferred renderers, culling, particles and skinning increasingly run this way.

Compute passes appear in the frame graph like any other pass, reading and writing textures and buffers. Because they skip the rasterizer and the depth and blend units, they suit work that is not about drawing triangles, and work that needs threads to cooperate, such as blurs that share loaded pixels within a group.

4 What it costs

Shaders cost in four places: build machines, memory, the first time something is drawn, and the GPU every frame. The first three are the ones teams underestimate.

Take a project with 300 master materials, each with five independent switches, drawn in four passes, shipping on Direct3D 12 and Vulkan. That is up to 300 × 32 × 4 × 2 = 76,800 pixel shader variants, each with a matching vertex shader. If one variant takes a fifth of a second of compiler time, an assumption that varies widely with shader size and platform, a full rebuild is about 4.3 hours of CPU time, spread over the build farm and cached in the derived data cache. One more switch on all of them doubles it.

76,800variants from 300 materials × 32 combinations × 4 passes × 2 APIs
× 2for each extra on/off switch on every material
81 MBof render targets for the small frame in step 7 at 1080p; about 274 MB at 4K
57,600thread groups of 8 × 8 for one full-screen compute pass at 2560 × 1440

At run time the shader's own instructions are only part of a pass's cost. Reading render targets and textures often costs more than the maths, which is why render target formats and resolution matter as much as shader complexity. A full-screen pass touches every pixel; at 4K that is 8,294,400 pixels, four times 1080p, for every post effect in the chain.

What makes the cost grow

  • Independent switchesEach one doubles the variants of every material that has it, and every PSO built from them.
  • Passes and mesh typesA material drawn in depth, shadow, main and velocity passes, on static and skinned meshes, needs a version for each.
  • Platforms and graphics APIsEach target API is a separate set of compiled shaders; Unity notes it compiles one set per API for the build target.
  • First use in playEvery PSO not created during loading is a potential hitch on a player's machine, worst after a driver update.
  • Render target size and formatMemory and bandwidth scale with pixels × bytes per pixel; 4K quadruples both.
  • Graph shapePasses that run but whose results nothing uses cost full price unless a frame graph culls them.

5 How it breaks

Shader problems split into build-time pain, first-use hitches and wrong pictures. These six cover most reports.

A hitch the first time something appears

Cause
Shader compilation stutter: a PSO created at first use. Typical after a driver update, on a fresh install, or for content the PSO cache never saw.
Ask for
A log or trace of PSOs created during play, then wider precaching or warm-up during loading for those; and a test pass on a machine with an empty driver cache.

Objects pop in late or flash a default material

Cause
The engine's own protection against stutter: it skips a draw, or uses a default material, until the PSO finishes compiling in the background.
Ask for
Which PSOs were late and why precaching missed them, and earlier precaching for content that streams in during play.

Build times and shader caches balloon

Cause
Variant explosion: new switches on widely used master materials, keywords compiled for every combination, or usage flags set on materials that do not need them.
Ask for
A variant count per shader, before and after the change; which switches could be dynamic branches, material instances or stripped; and a budget enforced in the build.

Right in the editor, wrong in the build

Cause
The variant the game needs was stripped from the build, often a keyword switched on by script that no material uses, so the engine falls back to the closest variant it has.
Ask for
How each keyword is declared and who switches it; keep script-driven keywords in every build or list the variant explicitly; then check in a packaged build.

Black, stale or garbage areas after a rendering change

Cause
A pass reads a render target nobody wrote this frame, in the wrong format, or before the writer finished; or the frame graph removed a pass whose reads were not declared.
Ask for
The pass's declared reads and writes checked against what its shaders use, and a look in the render graph viewer or a frame capture at the target before and after the pass.

An untouched strip along a screen edge

Cause
A compute dispatch rounded the group count down, so the last partial row or column of groups never ran; often appears only at some resolutions.
Ask for
Group counts rounded up, a bounds check in the shader, and a test at resolutions that do not divide evenly, such as 1080 lines with 16 × 16 groups.

A frame capture tool shows every pass, its render targets and the shaders and pipeline state of each draw, and is the fastest way to confirm most of these.

Driver caches hide hitches from developers

Developers play the same build all day, so their driver caches already hold every pipeline and the hitches never show. Players see them on first launch. Godot's documentation recommends its pipeline monitors so you can find stutter sources without clearing the driver cache; with any engine, test first-time play on a clean machine or with the cache cleared.

7 Say it to your AI

Shader briefs go well when they state counts and budgets: variants, passes, platforms, resolution, milliseconds. Ask for the variant and pipeline impact of any change along with the shader code.

BriefUse when shader builds are too slow or too large
Engine: Unity 6, URP. Targets: PC (Direct3D 12) and PS5. A clean player build spends about 3 hours compiling shaders, and the build report shows over a million variants, mostly from our 14 custom shaders.

1. For each custom shader, list its keywords, how each is declared (shader_feature, multi_compile, dynamic_branch) and who sets it: materials, scripts or quality settings.
2. Calculate the worst-case variant count per shader and say which keywords multiply it most.
3. Propose changes in order of saving: shader_feature where only materials set the keyword, dynamic_branch where the branch is cheap, stripping for unused features. For each, state the GPU cost risk and how we would see it.
4. Tell us how to confirm that no variant we need disappears from the build.
  • Asking who sets each keyword decides whether shader_feature is safe.
  • Worst-case arithmetic shows where the explosion comes from before any change.
  • Item 4 guards against the "right in the editor, wrong in the build" failure.
BriefUse when adding a full-screen compute effect
Engine: Unreal Engine 5.9, desktop and Steam Deck. Add a screen-space edge-detection effect for a scanner mode, as a compute pass in the Render Dependency Graph after tone mapping.

Requirements:
- Reads the scene depth and the tone-mapped colour; writes a new colour target of the same size.
- Thread groups of 8 × 8, group counts rounded up, and a bounds check for any resolution.
- Budget: 0.3 ms at 1280 × 800 on Steam Deck, 0.5 ms at 4K on our min-spec PC.
- No new material switches; the effect's strength is a constant set per frame.

Show the pass declaration with every read and write, the shader, the dispatch size calculation, and how we check it in RDG Insights and a frame capture.
  • Naming reads and writes makes the pass reviewable in the render graph.
  • Group size, rounding and bounds checks prevent the edge-strip bug.
  • A budget per device turns "fast enough" into something testable.

Questions to ask when reviewing shader work

  1. How many variants does this add, per material and per platform?One switch on a master material doubles everything built from it.
  2. Is each new switch compiled in or decided at run time, and why?Compile-time switches multiply variants; run-time branches cost a little on every pixel.
  3. When is the pipeline for this created: loading, background or first draw?Anything created at first draw is a hitch on some player's machine.
  4. Does each pass declare every render target it reads and writes?Undeclared reads lead to culled passes, missing barriers and black screens.
  5. Which constant buffer does each new value live in, and how often is it updated?The wrong group wastes CPU time or leaves a value stale.
  6. For compute, what is the group size, and what happens at the image edge?Rounding down the group count leaves strips unprocessed.

8 Check yourself

  1. A master material has six independent on/off switches and is drawn in three passes on two graphics APIs. At most, how many variants of its pixel shader does that make?

    Show answer

    26 = 64 combinations, × 3 passes × 2 APIs = 384. One more switch would make 768.

  2. Testers report a half-second freeze the first time a boss uses a fire attack. On the second attempt it is smooth. After a GPU driver update, it is back. What is happening, and what do you ask for?

    Show answer

    Shader compilation stutter: the attack's pipeline state objects are created at first use, and the driver's on-disk cache hides it until an update clears that cache. Ask for those PSOs to be precached or warmed up during loading, and for a check on a machine with an empty cache.

  3. A full-screen compute pass runs at 2560 × 1440 with 8 × 8 thread groups. How many groups does it dispatch? Why must the shader still check bounds in general?

    Show answer

    320 × 180 = 57,600 groups, 3,686,400 threads. At resolutions that do not divide by the group size, such as 1080 lines with 16 × 16 groups, the count is rounded up and the extra threads fall outside the image, so they must do nothing.
