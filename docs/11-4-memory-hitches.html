11.4 Memory, streaming and hitches

A game world is many times larger than the memory it runs in, so it is read from disk, unpacked and made live while the player moves. This chapter shows how teams budget memory per platform, how textures, meshes and levels stream, why loading on the wrong thread freezes the game, what each kind of hitch looks like on a frame-time graph, and what happens when memory runs out.

1 The picture

2 In plain words

Every platform has a fixed amount of memory, and the operating system keeps part of it (1.4). What is left has to hold the frame's render targets, the textures and meshes on screen, the sound, the game's objects and the engine itself. A modern game ships tens of gigabytes of content, so only the part near the player can be in memory at once. The rest waits on disk, compressed.

Older games loaded a whole level behind a loading screen. Open worlds stream instead: while the player moves, the game reads the next area from disk, unpacks it, builds its objects and frees what is behind. Done well, the player never notices. Done badly, it shows up as blurry textures, buildings appearing late, or a hitch, one frame many times longer than the rest, which 11.1 showed can halve the 1% low while barely moving the average.

An everyday comparison

A stage play with a small backstage. The whole production will not fit in the wings at once, so the crew bring the next scene's set in from the lorry while the actors perform, and carry the last one out. If the crew are slow, an actor walks into an empty room. If they wheel a wall across the stage mid-scene, the audience notices.

The problem it solves

Without a budget and a streaming plan, memory fills up until the game crashes on a console or crawls on a PC, and loading happens wherever the code happens to ask for an asset, freezing the game. With them, every system knows its share, the world arrives before the player does, and the slow work happens off the threads that build each frame.

Why a lead cares

Memory budgets, level layout and traversal speed are design decisions: a vehicle that goes twice as fast needs the world to stream twice as fast. Hitches are what players and reviewers notice first, and they rarely show in average frame rates. A lead who sets per-platform memory budgets early, asks for a hitch log from every play-test, and treats each spike as a bug with a cause keeps the game smooth on its weakest target.

3 How it works

The steps follow the data: the memory budget it must fit, how it streams, how it is read and unpacked, how it is loaded without stopping the frame, then a gallery of the hitches that result when that goes wrong, and what happens when memory runs out.

1 The memory budget

A memory budget splits the memory a game may use on each platform between its systems, the way 11.1 split the frame's milliseconds. Consoles, phones and handhelds have unified memory: the CPU and GPU share one pool, so textures compete with gameplay data. A PC splits the game across system RAM and the graphics card's VRAM, and the VRAM the game may use is set by Windows: Microsoft's documentation calls it the video memory budget and says it can fluctuate noticeably as background processes wake up and sleep.

2 Streaming textures, meshes and levels

Streaming happens at three sizes. Texture streaming keeps only the mip levels each texture needs (6.3). Mesh streaming does the same for geometry, loading detailed levels of detail or, in Nanite's case, clusters of triangles only where the screen needs them (4.5). Level streaming loads and unloads whole pieces of the world: buildings, terrain, props and the objects that live in them.

Open worlds automate level streaming with a grid. Unreal's World Partition divides the world into grid cells that are loaded and unloaded by the presence of streaming sources, such as the player; Epic's documentation says player controllers are streaming sources and that the engine only loads the parts of the level the player sees and interacts with. Each grid has a cell size and a loading range, the distance from a streaming source within which cells are loaded.

3 Reading and unpacking

Data is stored compressed, so streaming is two jobs: read the bytes, then decompress them. Both have grown with solid-state drives. Microsoft's DirectX team wrote that previous-generation games streamed at about 50 MB/s, and that saturating the Xbox Series X's 2.4 GB/s drive with 64 KB reads takes more than 35,000 requests a second, too many to handle one at a time. Consoles add hardware decompression: Microsoft says matching the Series X's decompression block in software would need more than four Zen 2 CPU cores.

On Windows the same ideas arrive through DirectStorage, Microsoft's API that lets a game issue batched, parallel I/O requests instead of handling each read one at a time. Version 1.1 added GPU decompression with the GDeflate format, unpacking data with compute shaders on the graphics card. The latest stable release is 1.3, and 1.4, in public preview since March 2026, adds the Zstandard format with CPU and GPU decompression.

4 Loading without stopping the frame

Asynchronous loading reads and prepares assets on other threads while the game keeps running, and only the last steps, such as registering new objects with the world, run on the game thread. Loading synchronously, on the game thread, puts all of it into one frame. Each engine warns about this: Epic's documentation says a synchronous load could potentially stall the main thread for too long, Unity's Addressables documentation says WaitForCompletion can cause frame hitches, and Godot's background loading page says a normal load blocks the thread and makes the game appear unresponsive.

Even fully asynchronous streaming has a game-thread step. When a whole cell of the world becomes live at once, creating and registering hundreds of objects in one frame, the player sees a hitch each time they cross into a new area. This is traversal stutter, and it gets worse the faster the player moves. Engines limit the per-frame cost: Unreal's streaming settings include an Async Loading Time Limit and an Actor Initialization Update Time Limit, both in milliseconds per frame, and Unity's asynchronous upload pipeline caps texture and mesh uploads at a time slice of 1 to 33 ms per frame.

5 A gallery of hitches

Different causes leave different shapes on a frame-time graph, and the shape is the fastest clue to the cause. The gallery below is a minute of play with five kinds of hitch in it. Pick one to highlight its frames, read its cause and fix, then switch to the same minute after the fixes.

Four of the five are timing problems: work that is fine in itself happening in the wrong frame or on the wrong thread. Their fixes move the work earlier, onto other threads or into smaller slices; none of them makes the game do less overall. The fifth, over-commit, is a memory problem, and it is fixed by using less.

6 Shader compilation stutter, again

Shader compilation stutter, from 5.6, is the hitch that comes from creating a pipeline state object the first time something is drawn. Its signature is the easiest to recognise: one spike per new effect, material or enemy, never repeated in the same session. Every engine now tries to move the work earlier with a PSO cache of some kind. Unreal's PSO precaching is on by default and, by default, delays drawing an object until its pipeline is ready, which skips the draw for a moment instead of blocking the frame. Unity's GraphicsStateCollection records the states a development build uses so a release build can warm them up during loading, and Godot precompiles pipelines when meshes load and covers the gaps with ubershaders.

Each also reports misses. Unreal can log pipeline creation that took longer than r.PSO.RuntimeCreationHitchThreshold, 20 ms by default, and Godot's debugger counts pipeline compilations triggered while drawing, which its documentation says show up as stutters the first time a user runs the game. A team should know that number for every build.

7 When memory runs out

Running out looks different on each kind of platform. On a console, memory is fixed and there is no paging to fall back on, so going out of memory means an allocation fails and the game usually crashes. On a PC, going over the VRAM budget is VRAM over-commit. Microsoft's residency documentation says a process that does not stay within its budget will be intermittently frozen to let other applications run, or its creation calls will fail, and that the wrong resource in system memory can severely impact frame rate.

Memory fragmentation is free memory broken into gaps too small to use. Objects are created and freed in a different order, leaving holes, and a large request can fail even when the total free is far larger. Unity's documentation describes exactly this for its managed heap and notes that its collector does not move objects to close the gaps. Fragmentation grows over long sessions, which is why a crash after an hour of play is a classic sign of it, or of a leak.

Short of running out, a streaming system that cannot get the memory or the bandwidth it wants runs behind. Streaming starvation shows as textures that stay blurry, meshes at a low level of detail and objects that appear late. Unity's Mipmap Streaming documentation says that to stay inside its Memory Budget it loads lower-resolution mipmap levels, which can cause textures to pop or load slowly. Starvation trades a hitch for a visible loss of quality, which is often the better trade, as long as somebody chose it.

8 Reading a hitch in a capture

A frame-time graph says when and how long; a capture of the slow frame says why. 11.5 covers the capture tools. In any of them, find the spike, open that frame and look across the threads for the bar that fills it. The other threads usually show waits, because they ran out of work while one thread was stuck.

4 What it costs

Streaming cost follows travel speed. Assume each 128 m of travel brings in 250 MB of compressed data, an illustrative figure; the data rate the game must sustain is then:

Worked example. A driving game crosses a 128 m cell every 2.6 s at 50 m/s and needs about 98 MB/s from disk, under a twentieth of a Series X drive's raw speed, so reading is not the problem. Making each new column of cells live costs 40 ms of object creation on the game thread. Done in one frame, the player sees a 54 ms frame every 2.6 s: traversal stutter, and a 1% low far below the average. Sliced at 2 ms per frame, the same 40 ms takes 20 frames, a third of a second, well inside the 2.6 s before the next column, and no frame goes over budget. The fix cost no memory and no bandwidth, only a change of schedule.

  • Travel speedFaster players cross more cells a second, so every rate in the pipeline must rise with them.
  • Unique contentEach new texture, mesh and material is more to read, unpack, upload and compile.
  • Density per cellMore objects per cell means more game-thread work when a cell becomes live.
  • Platform memoryThe weakest target, often the console with the least memory or the 8 GB graphics card, sets the budget.
  • Session lengthFragmentation and leaks grow with time, so problems appear hours in.
  • First-time eventsEvery effect, enemy and area seen for the first time can compile pipelines or load assets.

The usual trade

Teams set memory budgets per platform in pre-production, check them every night with automated captures, and keep around a gigabyte or so in hand for surprises. They cap traversal speed or simplify distant content where streaming cannot keep up, time-slice activation, precompile pipelines and log every hitch from every play-test. When memory is tight they choose softer textures over crashes, deliberately and per platform.

5 How it breaks

Memory and streaming fail in two ways: the data is not there in time, or it arrives in a way that stops the frame.

Textures stay blurry, then pop sharp

Cause
Streaming starvation: the texture pool is too small for the view, or reads cannot keep up after a camera cut or teleport.
Ask for
Pool size against what the view wants, from stat streaming or the Memory Budget, and the time from cut to sharp on the weakest target.

Buildings appear just ahead of the player

Cause
The loading range is too short for the travel speed, or cells are too heavy to load in the time the range buys.
Ask for
Loading range, cell size and data per cell against the fastest traversal, and load times per cell from a fast run.

Stutter while driving or flying fast

Cause
Traversal stutter: whole cells made live in one frame on the game thread, creating and registering many objects.
Ask for
A capture of a slow frame during traversal, the per-frame activation time limits, and the object count per cell.

Freezes when a menu opens or a boss appears

Cause
A synchronous load on the game thread: the asset is read, unpacked and created inside one frame.
Ask for
The load call in the capture, an asynchronous request made earlier, and a placeholder or transition while it arrives.

Crash after an hour of play

Cause
Out of memory from a leak, from fragmentation, or from a budget that only fitted short sessions.
Ask for
Memory snapshots at the start and after an hour, compared by category, and the largest free block over time.

Smooth on 12 GB cards, slow on 8 GB in one area

Cause
VRAM over-commit: the area's textures and buffers exceed the smaller card's budget, so Windows pages or freezes the game.
Ask for
VRAM use against the budget in that area on an 8 GB card, and texture pool and quality settings sized per memory tier.

7 Say it to your AI

Memory and hitch briefs go well when they name the platform's budget and the fastest traversal, include a hitch log, and ask for each spike's cause before any fix.

Hitch triageUse after a play-test with stutter reports
Unreal Engine 5.8, World Partition open world, PS5, 60 fps. Play-test logs with stat dumphitches (t.HitchFrameTimeThreshold 0.033) and an Unreal Insights capture of the motorbike route are attached.

1. Group every hitch by likely cause: shader or PSO creation, garbage collection, cell activation during traversal, synchronous load, memory pressure. Give the evidence for each group.
2. For traversal hitches, report the cell, the object count and what ran on the game thread in the slow frame.
3. For PSO hitches, check stat PSOPrecache misses and say which materials were not precached.
4. Propose fixes per group with the expected effect on the 1% low. Do not change loading ranges or cell sizes without listing the memory cost.
  • Grouping by cause first stops one fix being applied to five different problems.
  • Naming the evidence per group makes the AI's diagnosis checkable.
  • Tying range changes to memory guards the budget from a quick fix.
BudgetUse when setting or checking memory budgets
Unity 6.6, URP. Targets: Xbox Series S and PS5, plus PC with 8 GB graphics cards. Memory Profiler snapshots from a player build in the three heaviest areas are attached.

1. Propose a memory budget per platform by category: render targets, streamed textures, other textures, meshes, audio, animation, managed heap, native engine, headroom. Mark which numbers are measured and which are estimates.
2. Set the Mipmap Streaming Memory Budget per platform and say what the player will see when it is reached.
3. List the twenty largest assets and anything loaded twice.
4. Compare a snapshot at start with one after an hour of play and report anything that only grows.
  • Per-category budgets give every system an owner and a number.
  • Separating measured from estimated keeps guesses from becoming limits.
  • The hour-later comparison finds leaks and fragmentation before certification does.

Questions to ask when reviewing memory and streaming work

  1. What is the memory budget on the weakest target, and how much headroom is left in the heaviest area?The busiest area on the smallest machine is the one that crashes or pages.
  2. Does anything load synchronously during play?Each synchronous load is a freeze waiting for the right moment.
  3. How much game-thread work does one cell cost to make live, and is it time-sliced?That number becomes traversal stutter at speed.
  4. How many pipelines were created at first use in the last play-test?Each one is a shader stutter someone will see.
  5. What does the hitch log of a long session look like at the end compared with the start?Leaks and fragmentation only show with time.

8 Check yourself

  1. A car travels at 50 m/s through a world streamed in 128 m cells. How long does the game have to bring in each new column of cells, and what does the player see if it takes longer?

    Show answer

    About 2.6 seconds, 128 ÷ 50. If loading takes longer, the player reaches cells that are not ready: blurry textures, low-detail meshes or missing buildings, or, if the engine blocks on slow streaming, a pause until they arrive. A longer loading range buys more time at the cost of memory.

  2. A console build has 270 MB free but fails to allocate 64 MB and crashes. How is that possible?

    Show answer

    Fragmentation: the free memory is split into gaps, none 64 MB long, so no single block can hold the request. Fixes include pools of fixed-size blocks, allocating large long-lived buffers early, and avoiding patterns that interleave long- and short-lived allocations.

  3. Players report a hitch the first time each new enemy type appears, never twice in the same session. What is the likely cause, and what does a capture of that frame show?

    Show answer

    Shader compilation stutter: the enemy's materials need pipeline state objects that were not created in advance. The capture shows the render thread inside pipeline creation for tens of milliseconds while the game thread waits. The fix is to precache or warm up those pipelines during loading.
