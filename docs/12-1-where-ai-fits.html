12.1 Where AI fits today

AI tools can now read and change a codebase, write shaders and tools, summarise logs and captures, and draft art. This chapter maps where along the pipeline that help is real, where a person still has to check, which tasks suit an AI agent, and how to set up the loop so mistakes are caught before they ship.

1 The picture

2 In plain words

An AI model on its own answers questions. An AI coding agent does work: it reads the project's files, changes them, runs the build and the tests, and reports back to the person who asked. It can make many changes and check them before anyone looks, which is what makes it useful and what makes it risky. It is fast and tireless at text, and it knows a great deal about engines and graphics APIs. It does not see the screen the way a player does, it does not hold the target console, and it does not know what the art director meant unless someone wrote it down.

An everyday comparison

A very fast new contractor who has read every manual but has never seen your game. Given a precise job, the right files and a way to test the result, they do excellent work quickly. Given a vague job, they still produce something confident and plausible, built on guesses about everything nobody told them.

The problem it solves

Graphics work is full of well-specified, checkable chores: porting shaders, writing validation tools, wiring settings, adding markers, reading long logs and captures. Handing those to an agent frees experts for the judgement calls, as long as every result passes through checks and a person before it counts.

Why a lead cares

AI changes where the team's time goes more than how much work exists. Writing code gets cheaper; specifying, checking and reviewing it does not. A lead decides which tasks go to agents, what evidence comes back with each result, and who signs off, and keeps the parts that need taste, hardware and legal judgement with people.

3 How it works

The steps go from what an agent can see and do, through which tasks suit it and how its work is checked, to AI-generated assets, the legal questions around them, and the ways AI-written graphics code most often goes wrong.

1 What the model can see

The model context is everything the model can see while it works: the instructions, the files and results it has read, and the conversation so far. It has a size limit, so even a capable agent sees a window onto a large project, not the whole thing. Anything outside the window, the model does not know.

Guesses are not marked as guesses. A model asked about a setting that changed between engine versions will usually answer fluently for some version; NIST's Generative AI Profile calls this risk confabulation, the production of confidently stated but false content. The defence is the same as with any contractor: give it the facts, ask for sources, and check the claims that matter.

2 Tool use and the loop

Tool use means the model asking a program to do something for it, then reading the result: search the code, open a file, build, run the tests, take or summarise a capture. A model with tools can check its own work instead of only predicting it. Repeating that, plan, act, check and go again, is an agentic workflow.

Graphics tools have started to meet agents halfway. Microsoft's PIX 2610.28, released in October 2026, includes a server that lets agents open timing captures and query CPU samples, GPU events, memory allocations and file reads. Apple's Metal debugger documentation describes a command-line tool, gpudebug, with a text interface designed so that AI agents can navigate GPU traces. Capture analysis, which used to mean an expert scrolling through thousands of events, is becoming something an agent can draft and a person can check (11.5).

3 Which tasks suit an agent

Two questions sort most graphics tasks. Is the goal written down precisely? And can a machine check the result? A task that passes both suits an agent well. A task that fails the first needs a better brief before anyone starts. A task that fails the second needs a person, or the target hardware, at the end of it.

The most useful move is often to push a task to the right by adding a check. A reference image, a performance test that fails above a budget, or an asset validation rule turns "looks right" or "fast enough" into something a machine can test, and that makes the task far safer to hand over.

4 The loop: checks, then a person

AI-made work should flow through the same pipeline as anyone else's, with two kinds of gate. Automated checks run on every change, the way continuous integration already does (1.3). A human review gate then puts a named person between the draft and the merge, for everything a machine cannot judge.

The gate only works if the reviewer has evidence: what the agent ran, on which hardware, with captures and screenshots before and after. A review of a large diff without evidence is a reading exercise, and people reading fast miss the same things agents do. 12.3 covers what to look for in the code itself.

5 AI-generated assets

An AI-generated asset is a texture, mesh, image or piece of concept art made wholly or partly by a generative model. Teams use them most for exploration and placeholders. The question for anything that ships is production readiness: does it meet every technical, artistic and legal requirement that a hand-made asset would?

Industry surveys show how unsettled this still is. GDC's 2026 State of the Game Industry report, published in January 2026, found that 36% of game industry professionals use generative AI tools at work, mostly for research and brainstorming (81% of those users), with 47% using them for code assistance and 35% for prototyping. The same survey found 52% think generative AI is having a negative impact on the industry, rising to 64% among visual and technical artists.

6 Provenance and licensing

Training data provenance is where a model's training data came from and on what terms. It matters to a game because it can affect the legal risk of using what the model produces. This section describes the questions; the answers are for your legal team.

Not legal advice

This book cannot tell you whether a particular tool or asset is safe to use. Laws and platform rules differ by country and are changing. Treat provenance and licensing as a risk to raise with your legal team early, before AI-made content is in a build that players will see.

7 How AI-written graphics code goes wrong

AI-written graphics code fails in recognisable ways, most of them the same mistakes people make, delivered faster and with more confidence. Many come from the vocabulary of this book: linear versus sRGB colour, coordinate spaces and handedness, engine versions, per-frame allocation, precision and platform fallbacks.

4 What it costs

The cost of AI work is mostly people-time spent specifying and checking, and risk: the chance that something wrong gets through. Tool subscriptions and compute are real costs, but they are rarely the largest. Measured effects on speed are still uncertain, so treat any promised speed-up as a hypothesis to test on your own team.

The research group METR ran a randomised trial in early 2025 in which experienced open-source developers took 19% longer on real tasks when allowed AI tools, while believing afterwards that they had been about 20% faster. Its February 2026 follow-up says later tools probably do speed developers up, but that its new data is only weak evidence of how much. The lesson for a lead is not the number but the gap between perception and measurement: measure throughput and rework on your own projects.

Worked example, illustrative. An agent writes a 300-line change to the shadow settings in ten minutes. Writing the brief took 15 minutes; review with captures and screenshots takes 40; a devkit run takes 20. The change cost about 85 minutes of people's time, against perhaps a day to write by hand: a real saving. Skip the devkit run and the review, and a bug that only appears on console reaches QA a week later, where finding and fixing it costs far more than the time saved. The saving is real only while the checks stay.

  • Size of each changeReview effort grows faster than the diff; small, staged changes are cheaper to check.
  • Distance from an automatic checkEvery judgement a machine cannot make is a person's time, on every change.
  • PlatformsEach target needs its own build, run and capture before a claim about it is true.
  • NoveltyCode with no similar example in the project, or in public, gets less reliable drafts.
  • Player-facing contentGenerated assets that ship raise art review, provenance and disclosure work.

The usual trade

Teams that get value from agents start with well-specified, checkable chores, invest in checks that make more tasks checkable, keep every change small enough to review, and require evidence with every result. They keep art direction, target-hardware sign-off and licensing decisions with named people.

5 How it breaks

AI-assisted work fails at the joins: where the agent's view stops, where checks are missing, and where a person approves something they did not really check.

Works on the development PC, fails on console

Cause
Every test the agent ran was on the PC it had. Different GPUs, drivers, memory and shader compilers make some failures platform-only.
Ask for
A run on each target platform before merge, with captures, and the list of platforms the agent did not test.

A change too big to review

Cause
A broad brief, or an agent allowed to "improve" whatever it touched. Reviewers skim, and problems pass.
Ask for
A plan first, then small changes in order, each with its own evidence, and files outside the scope left alone.

The fix hides the symptom

Cause
The agent was asked to make a symptom go away and did: a clamp over fireflies, a silenced warning, a larger bias. The cause is still there.
Ask for
The root cause, explained with evidence from a capture or a test, before any fix.

A confident answer for the wrong version

Cause
The engine version was not in the context, so the model answered for one it knew. Settings and APIs move between versions.
Ask for
The exact version in every brief, and links to that version's documentation for every setting or API the answer relies on.

Generated textures with lighting baked in

Cause
A picture made to look good on its own usually includes light and shade; used as albedo, it gets lit a second time by the engine.
Ask for
Flat albedo with separate normal and roughness maps, checked by the import rules for value range and seams.

An asset nobody can trace

Cause
No record of which tool made it, from what inputs, or who approved it. The question arrives late, from legal or a platform holder.
Ask for
A provenance record for every AI-made asset, kept in version control next to it.

6 In the engines

An agent works through text and tools, so what matters is how much of each engine it can reach from the command line, how much of a project is stored as readable text, and which automated checks exist to catch its mistakes.

Unreal Engine 5Unity 6Godot 4
From the command line Automation tests run with -ExecCmds="Automation RunTest …;Quit" on the Editor or game executable. -batchmode with -executeMethod runs an Editor script, for example a build, and quits. --headless with --script runs a script; --export-release exports with a named preset.
Automated tests Automation Test Framework: unit, feature, smoke and content stress tests, plus Editor tests in Python. Unity Test Framework: -runTests with -testPlatform EditMode, PlayMode or a build target, results as NUnit XML. Scripts run with --script can drive a project's own checks.
Visual checks Screenshot Comparison tool: new screenshots are compared with approved ground-truth images. Play mode tests can run on a player built for the target platform. No comparison tool in the documentation pages checked here.
Text an agent can read Code and config files are text; assets (.uasset, .umap), including Blueprints, are binary and cannot be merged as text. Scenes and prefabs can be stored as UnityYAML text, which tools can generate and parse. Scenes (.tscn) are a mostly human-readable text format, easy to manage in version control.

Checked against the documentation for Unreal Engine 5.8 (Automation Test Framework, running automation tests, Screenshot Comparison tool, using Perforce), Unity 6.6 (6000.6: running Unity from the command line, Test Framework command-line reference, text-based scene files) and Godot 4.7 (command-line tutorial, TSCN file format), plus PIX 2610.28 (October 2026) and Apple's Metal debugger documentation, in November 2026. AI tools change monthly; the statements about them in this chapter are general and dated, and name no AI product.

7 Say it to your AI

Two briefs that use the agent where it is strongest: planning a task into checkable steps, and drafting an analysis that a person then verifies.

Plan firstUse before handing an agent a larger task
Unity 6.6, URP, Forward+. Platforms: PC and Steam Deck at 60 fps. Task: add contact-hardening soft shadows for the main light, within 0.6 ms on Steam Deck at 1280 × 800.

Do not write code yet.
1. Split the task into steps small enough to review one at a time, in order.
2. For each step, say how a machine can check it (a test, a reference image, a budget check) and what only a person can check.
3. List what you cannot verify yourself, such as Steam Deck timings or how it looks to the lighting artist, and what evidence you will need from us.
4. List the files you expect to change and anything you will not touch.
  • A plan before code keeps changes small and reviewable.
  • Asking what it cannot verify makes the gaps explicit instead of hidden.
  • The file list sets the scope before the first change.
Capture analysisUse when a timing capture needs a first read
Unreal Engine 5.8, PS5, 60 fps mode. An Unreal Insights trace of a 90-second play-test on the market route is attached, with our per-pass GPU budgets.

1. Summarise frame time over the run: average, 1% low and the ten slowest frames with timestamps.
2. For each slow frame, say whether the game thread, the render thread or the GPU was the longest lane, and which scope or pass filled it.
3. Mark every statement as measured (with the trace location) or inferred.
4. Do not propose fixes yet; list the three questions a graphics programmer should answer next.
  • Measured versus inferred separates evidence from plausible guesses.
  • Locations in the trace let a person check each claim in minutes.
  • Holding back fixes keeps the analysis honest.

Questions to ask when reviewing AI-made work

  1. Which tools did it run, on which hardware, and what did it not test?The report is only as true as the tools behind it.
  2. Which engine version and documentation did it rely on?Version drift produces fluent, wrong answers.
  3. Is there evidence for the cause, not only for the symptom going away?Hidden symptoms come back later and cost more.
  4. Did it change anything outside the scope of the brief?Unrequested changes are where unreviewed risk hides.
  5. For any asset: where did it come from, and who approved its use?Provenance is cheap to record now and expensive to reconstruct later.

8 Check yourself

  1. Three tasks: port a post-process shader from GLSL to HLSL with a reference image; make the night scenes feel lonelier; get a scene to 60 fps on a console devkit the agent cannot reach. How would you split the work between an agent and people?

    Show answer

    The port suits an agent: the goal is precise and the reference image checks it. The night scenes are taste-dependent: an agent can offer variations, the art lead decides. The devkit task is precise but hardware-dependent: an agent can propose and draft changes, and a person measures each on the devkit.

  2. An agent reports "all tests pass, shadow pass now 1.8 ms". What do you ask before approving the merge?

    Show answer

    Where and how 1.8 ms was measured, on which hardware and build; the capture itself; before and after screenshots from fixed cameras for the art lead; which platforms it did not test; and whether anything outside the brief changed.

  3. A generated rock texture looks good in the editor. Name three technical checks and one non-technical check before it ships.

    Show answer

    Technical: no lighting or shadow painted into the albedo, plausible albedo values, seamless tiling, sensible resolution and texel density, correct normal map convention. Non-technical: a provenance record and a licensing review, plus art direction sign-off and any store disclosure.
