1.3 The content pipeline

Every model and texture in a game starts as a large, editable file in an artist's tool and ships as a small file built for one platform. The content pipeline is the chain of tools, people and checks that turns one into the other for every file in the game, without losing anyone's work.

1 The picture

2 In plain words

A game's art is made in specialist programs: one for sculpting, one for modelling, one for painting textures. Each saves its own working files, full of layers, history and settings that only that program understands. A game engine cannot load those files quickly, and a console or phone has neither the memory nor the time to make sense of them while a player waits.

So every piece of art travels down a content pipeline. It is exported from the artist's tool, imported into the engine, checked against the project's rules, and finally converted into compact files for each platform the game ships on. The working files stay with the team, with every version kept. Players only ever receive the converted copies.

Everyday comparison

A newspaper story. The reporter's draft is long and full of notes and tracked changes. Sub-editors check it against the house style and cut it to fit, and production turns that one story into the print page, the website and the phone app, each laid out for its own screen.

Nobody prints the reporter's draft, and nobody throws it away either.

The problem it solves

Artists need rich files they can keep changing for months. Players' machines need small files in exactly the format their hardware reads, and they need them to load fast.

A pipeline lets both exist, keeps them in step, and catches mistakes before they reach a build the whole team depends on.

Why a lead cares

The pipeline decides how fast your team can iterate and how often the build breaks. Models arriving at the wrong size, missing textures, overwritten work and a failed nightly build are all pipeline failures, cheap to prevent and expensive to chase. The pipeline is also where AI-generated assets either get checked or slip into the game unchecked.

3 How it works

Follow the lantern from the first sketch to the shipped game. There are eight steps, and the roles named here are covered in 1.2 Who does what.

1 Artists' tools and source files

A DCC tool (digital content creation tool) is a program artists make content in. For 3D game art the common ones are Blender, Maya, 3ds Max, Houdini, ZBrush, and Adobe's Substance 3D Painter and Substance 3D Designer. Most studios use several, because each is strongest at a different job.

Each tool saves its own native file. These are the source assets: the editable originals the team keeps and keeps changing. They hold far more than the game needs, such as sculpting layers, undo history and paint strokes, and they are large. They are also the only files from which the asset can be changed properly later, so losing one is losing the work.

2 From sculpt to game mesh

Fine detail is easiest to sculpt with millions of polygons, far more than a game can draw for one prop. A game version of the lantern might have around 8,000 triangles, and further away it switches to simpler versions still (level of detail, chapter 4.5).

Retopology builds that light mesh over the sculpt, by hand or with automatic tools, with edges placed where the shape and any animation need them. The artist then unwraps it: cuts the surface along seams and flattens it onto a square, so that every triangle gets its own area of a 2D texture. That gives each corner of the mesh its UV coordinates. Chapter 6.1 Textures and UVs covers unwrapping in depth.

3 Baking: moving detail into textures

Baking moves the detail the light mesh cannot hold into textures it can. The baker casts rays from the low-poly surface towards the high-poly sculpt, records what each ray hits and writes it into an image. A normal map stores which way the sculpted surface faced at each point, so lighting can draw bumps that are not there (chapter 6.4). An ambient occlusion map stores how enclosed each point is, which darkens creases.

A cage, a slightly inflated copy of the low-poly mesh, sets where the rays start. Substance 3D Painter bakes this way, and Blender does it with its Selected to Active option. Without a cage, rays follow the mesh's normals, which Blender's manual warns can cause glitches at edges.

4 Export: the hand-off

To leave the DCC tool, the work is exported to a format engines read. Three formats matter today, and they were built for different jobs.

FBX is Autodesk's exchange format. It carries meshes, materials, skeletons, animation, cameras and lights, and almost every DCC tool writes it. Autodesk's own documentation says the file format is not documented, so programs read and write it through Autodesk's FBX SDK.

glTF is an open standard from the Khronos Group, published as ISO/IEC 12113:2022. It describes meshes, PBR materials, skins and animation in a JSON file with binary data alongside, or packs everything into one .glb file. Its specification fixes the units and axes: metres, with Y pointing up.

USD (Universal Scene Description) came from Pixar and is open source. It is built for assembling large scenes from many files: layers stack changes on top of each other without editing the originals, references pull assets in, and variants pack alternatives into one asset. The Alliance for OpenUSD, founded by Pixar, Adobe, Apple, Autodesk and NVIDIA, published its Core Specification 1.0 in December 2025.

The export settings matter as much as the format: which unit the scene uses, which axis is up, which objects to include, whether to triangulate, how to treat smoothing. Studios write these down as export presets so that every artist exports the same way.

5 Import and the asset database

Import reads the exported file and converts it into the engine's own representation. The import settings are stored with it: scale, whether to use the artist's normals, whether to generate levels of detail, how to compress each texture. Change a setting, or the file, and the engine imports it again.

Engines differ in what they keep. Unreal turns the file into its own .uasset files, which become the working copies the team edits and submits. Unity and Godot keep the original file in the project and store the processed result in a cache folder that each machine builds for itself and that stays out of version control.

Every imported asset also gets an identity. The asset database tracks each asset by a stable ID, with its type, location and what it depends on, so a level refers to the lantern by ID and the link survives a rename. Unity stores that ID as a GUID in a .meta file beside the source file, Godot 4 uses uid:// identifiers, and Unreal's Asset Registry lets the editor list and search assets without loading them.

6 Cooking and packaging

Cooking converts imported assets into the exact form one platform loads. Unreal's documentation describes it as turning editor-only formats into runtime-ready ones: textures compressed into that GPU's formats and sized for its memory, shaders compiled for its graphics API, editor-only data removed and assets that no level uses left out. The result is a cooked asset: fast to load, useless for editing, and different for every platform.

Cooking is slow, so engines cache what it produces. Unreal keeps the results in a derived data cache (DDC); a shared DDC means that once one person or build machine has processed an asset, nobody else repeats the work. Unity Accelerator plays the same role for Unity, storing import results, compiled shaders and compressed textures for the whole team.

Finally the cooked content is packed into a build: a runnable copy of the game for one platform, made of compiled code plus a few large files of cooked assets. Unreal's packaging runs build, cook, stage and package in turn and writes .pak files, alongside .utoc and .ucas containers for its newer loader. Godot exports a .pck file. Unity puts content in the player build, and content loaded separately ships as AssetBundles, usually managed through the Addressables package.

7 Version control and locking

Version control keeps every revision of every file, records who changed what, and lets the team go back to any earlier state. For code it also merges work: two people can change different lines of the same text file and the system combines them. Most art files are binary, and binary files cannot be merged. Unreal's documentation says this plainly about its own .uasset and .umap files.

Teams therefore use file locking, also called exclusive checkout. The first person to open a file locks it, and nobody else can change it until they submit or release it.

  • Perforce handles very large binary files and locks them with its +l file type. Its server, long called Helix Core, is now named P4. Unreal's editor checks files out in Perforce automatically when you start editing them.
  • Git LFS (Large File Storage) adds big-file handling to Git: the repository keeps a small pointer and the file itself lives on a separate server. Files marked lockable stay read-only until you run git lfs lock, and Git LFS checks on every push that you are not changing a file someone else has locked.
  • Unity Version Control has Smart Locks, which do the same for files that cannot be merged.

8 Validation: the automatic gate

Asset validation is code that checks every asset against the project's rules before it reaches a build: names follow the convention, triangle counts are within the budget for that kind of object, textures are no larger than allowed, levels of detail and collision exist, nothing points at a missing file. Unreal ships a Data Validation plugin that runs on save and from the command line. Unity runs AssetPostprocessor scripts before and after each import. Godot can run an import script after a 3D scene imports.

The most dependable place to run it is continuous integration (CI): build machines that pick up every submitted change, import, validate and cook it, and report failures straight back to whoever submitted it. Checks that only run on artists' machines are easy to skip under deadline pressure; the build machine cannot skip them.

AI-generated models and textures enter the pipeline the way work from an outside vendor does: as exported files. Meshy, for example, lists GLB, FBX, OBJ and USDZ among its export formats. They should pass the same gate, plus a few extra checks: where the asset came from and under what terms, whether its triangle count and UV layout suit a game, and whether its scale and up axis match the project.

4 What it costs

A pipeline costs disk space, machine time and, most of all, people's waiting time. Here is the lantern again, as a worked example.

≈ 1 GBsource files for one mid-sized prop: sculpt, texture project, baked and painted maps (order of magnitude)
16 MBcooked for PC and consoles: three 2048 × 2048 maps at 5.3 MB each, plus the mesh
2 MBcooked for a phone: three 1024 × 1024 ASTC 6×6 maps at 0.6 MB each, plus the mesh
× every revisionversion control keeps them all, so storage grows with every save

Scale it up. A game with 2,000 props of this kind carries about 2 TB of current source art. If each file is saved twenty times over the project, the version control server holds around 40 TB. That is why studios plan server storage early, and why team members usually sync only the parts of the project they work on.

Machine time grows the same way. If importing and cooking one asset took 5 seconds, 20,000 assets would take 100,000 seconds, almost 28 hours, on one machine, for one platform. Shared caches turn most of that into downloads: the first machine does the work and everyone else fetches the result.

What makes the cost grow

  • More platformsEach one cooks separately and needs its own build machine time and testing.
  • Bigger texturesA 4096 × 4096 map holds four times the texels of a 2048 × 2048 one, on disk, in the cache and in memory.
  • Changing settingsA changed import or cook setting reprocesses every asset it touches, sometimes the whole project.
  • A team in many placesWithout a shared cache near each office, every machine repeats the same work.

In proportion

People waiting cost more than disks. An artist who waits ten minutes for every export, import and check, twenty times a day, loses over three hours a day. When an artist says iteration is slow, ask for the time from saving in the DCC tool to seeing the change in the game, and treat it as a production cost.

5 How it breaks

Pipeline failures usually show up as art problems. Their cause is almost always a setting, a missing check or a missing lock. These six turn up on most projects.

Wrong size

Cause
The DCC tool and the engine disagree about units, often centimetres against metres, so models arrive 100 times too big or too small.
Ask for
One export preset per tool with the unit stated, and a validation check that flags props whose size is outside a sensible range.

Lying on its side

Cause
One tool treats Z as up and the other treats Y as up, and the export did not convert, so every model arrives rotated by 90 degrees.
Ask for
The axis settings in the export preset and the importer, fixed once at the source rather than by rotating objects in each level.

Bake artefacts

Cause
The cage or ray distance is wrong, so rays miss the sculpt or hit the wrong part of it; or the map was baked with a different tangent basis from the one the engine uses.
Ask for
The baker's cage settings and the engine's normal map settings side by side, and a shared baking preset that matches the engine.

Overwritten work

Cause
Two people edited the same binary file without a lock. Only one version can be kept.
Ask for
Every binary file type marked lockable or exclusive-checkout in version control, set up before work starts, and a rule for who may break a lock.

Missing textures or links

Cause
A file was moved or renamed outside the editor, so the asset database lost track of it, or it was never submitted to version control.
Ask for
Moves and renames done inside the editor only, and a CI check that fails the build on any reference to a missing asset.

Works on my machine

Cause
The change relied on a file that exists on one artist's machine but was never submitted, or on stale cached data. The build machine starts clean and fails.
Ask for
A cook on CI for every submitted change, so the failure reaches the person who caused it the same day, before the rest of the team syncs it.

The build machine is the honest witness. If a clean machine cannot import, validate and cook the project from version control alone, something is missing, however good the game looks on the artist's screen.

6 In the engines

All three engines follow the same pipeline: import, cache, cook, package. They differ in which formats they read natively, what they keep in version control and how teams share processed data.

Unreal Engine 5Unity 6Godot 4
Model formats FBX, glTF, USD and others. The Interchange framework handles glTF and MaterialX; its FBX support is still marked Experimental, so formats it does not handle go through the legacy importer. Reads .fbx, .obj, .dae and .dxf. Opens .blend, .ma, .mb and .max only if that program is installed, by converting to FBX. Recommends FBX. glTF needs the glTFast package. glTF 2.0 is the recommended format. Also .blend (calls an installed Blender), FBX through ufbx since 4.3, Collada and OBJ.
What import keeps Creates .uasset files in the Content folder. These are the working files the team submits. The source stays in Assets with a .meta file holding its GUID and import settings. Results go in the Library folder, whose database files stay out of version control. The source stays with a .import file beside it. Results go in .godot/imported/; commit the .import files, not the .godot folder.
Asset identity The Asset Registry lists and searches assets without loading them. The Asset Database tracks source files and import results (SourceAssetDB and ArtifactDB), keyed by GUID. uid:// identifiers in file headers and .import files; scripts and shaders get .uid files since 4.4.
Shared cache Derived Data Cache. Zen is the default local DDC since 5.4; teams share one through a Zen server or a cloud DDC. Unity Accelerator caches import results, compiled shaders and texture compression for the team. No shared cache. Each machine imports the project into .godot/ itself.
Cook and package Packaging runs build, cook, stage and package, through BuildCookRun in the Unreal Automation Tool. Output goes into .pak files (plus .utoc and .ucas), which are not interchangeable between platforms. Build Profiles (File > Build Profiles) hold per-platform settings, and textures have platform-specific overrides. Separately loaded content ships as AssetBundles, usually through Addressables; 6.6 adds content directories for local content. Export presets live in export_presets.cfg, safe to commit, and need export templates installed. Content goes into a .pck file. Compressed textures use S3TC or BPTC on desktop and ETC2 or ASTC on mobile.
Validation hooks Data Validation plugin, on by default: validates on save, from the Content Browser, or on CI with -run=DataValidation. Rules in C++, Blueprint or Python. AssetPostprocessor scripts run before and after imports (OnPreprocessTexture, OnPostprocessModel and others). An import script (EditorScenePostImport) runs after a 3D scene imports and can inspect or change it.
Version control Built-in Perforce support. The editor checks out, and so locks, .uasset and .umap files because they are binary. Unity Version Control, with Smart Locks for files that cannot be merged. Official Git plugin. Godot generates .gitignore and .gitattributes, and its docs recommend Git LFS for binary assets.

Names checked against the documentation for Unreal Engine 5.8, Unity 6.6 and Godot 4.7 in November 2026. Import and cook features change quickly between versions; if a setting is missing, search for it in your version's documentation.

7 Say it to your AI

Pipeline work suits AI agents well: it is code, rules and scripts more than art. Good briefs name the engine and version control, give the rules as numbers, and say where the check must run.

BriefUse when you want an automatic asset check
Engine: Unreal Engine 5.8. Version control: Perforce. Build machines cook PC, PS5 and Xbox Series X|S every night.

Write data validation rules for static meshes and textures under /Game/Props:
1. Names: SM_ for static meshes, T_ for textures, with the suffixes _BC, _N and _ORM for base colour, normal and packed masks.
2. Triangle budget for LOD0: 5,000 for props under /Small, 15,000 under /Large.
3. Textures no larger than 2048 × 2048 unless the asset is tagged Hero. Textures ending _N must use normal map compression.
4. Every prop needs at least two LODs and simple collision.

Use the Data Validation plugin so the rules run on save and with -run=DataValidation on the build machines. For each rule, show the message an artist will see when it fails, and list the assets in the project that would fail today.
  • Folders, names and numbers turn vague taste into rules a machine can check.
  • Saying where it runs (save and CI) stops a script that only works on one machine.
  • Asking for current failures shows the size of the clean-up before you switch it on.
Bug reportUse when imported models arrive at the wrong size or angle
Since we moved prop modelling from Maya to Blender, new props import into Unity 6 with a scale of 100 and rotated 90 degrees onto their backs. Props made in Maya last month still import correctly. We export FBX with Blender's default settings.

Find the cause in our export and import settings. Compare one old Maya prop with one new Blender prop: scene units, the FBX unit scale, the up and forward axes, and Unity's model import scale settings. Propose a single Blender export preset, a way to fix the props already imported, and an import check that flags any prop whose bounds fall outside 5 cm to 5 m.
  • The pattern (only Blender props) points at Blender's export settings.
  • Naming the four things to compare keeps the search short.
  • Asking for an import check turns a one-off fix into a guard.

Questions to ask when reviewing pipeline work

  1. Which file is the source of truth for this asset, and where is it versioned?If only an imported or cooked copy exists, nobody can change the asset properly later.
  2. What happens when a file this script touches is renamed or moved?References by path break; references by ID survive.
  3. Does this check run on the build machines as well as on artists' machines?Checks that only run locally get skipped under deadline pressure.
  4. Which file types are locked, and who can break someone else's lock?Unlocked binary files are where work gets lost.
  5. For AI-generated assets, where are the tool, prompt, date and terms of use recorded?You may be asked where an asset came from long after the game ships.

8 Check yourself

  1. The PS5 build and the phone build contain different texture files for the lantern, though both came from the same painted maps. Why?

    Show answer

    Cooking makes a separate version for each platform. The PS5 version is compressed in a format its GPU reads, such as BC7, at a resolution its memory allows. The phone version uses a mobile format such as ASTC, usually at a lower resolution. One source asset, several cooked assets.

  2. Two artists changed lantern.uasset this morning, and the second cannot submit. What went wrong, and what prevents it?

    Show answer

    The file is binary, so the two sets of changes cannot be merged; one person's work has to be redone. File locking prevents it: exclusive checkout in Perforce (the +l file type), lockable files in Git LFS, or Smart Locks in Unity Version Control.

  3. An outsourcing partner delivers 40 props as FBX files. What should happen before any of them appear in a level?

    Show answer

    Import them with the project's settings and put them through the validation gate: names, triangle and texture budgets, scale and up axis, LODs and collision, no missing references. Run the same checks on CI, and record where the files came from and on what terms.
