11.5 Profilers and the settings menu

Every number in this part came out of a tool. This chapter shows the three kinds of tool and the questions each answers, what a frame capture looks like inside, how GPU time is measured, a workflow from a slow spot to the draw responsible, and how the graphics settings menu maps onto the techniques and costs of the whole book.

1 The picture

2 In plain words

A game that misses its frame budget does not say why. Something took too long, but the frame is made of thousands of steps on several CPU threads and the GPU, and guessing which one is how teams lose weeks. Measuring tools exist so nobody has to guess. Engineers loosely call all of them profilers, and they come in three kinds, each answering a different question.

A CPU profiler records what every CPU thread did, function by function, over many frames: the flame charts of 11.3. A GPU profiler times the passes and draws on the GPU and, with GPU counters, says which part of the GPU held them back, as in 11.2. A frame debugger records one frame and lets you step through it draw by draw to see what was drawn and with what. The first two answer "where did the time go?"; the third answers "why does it look like that?".

The other half of this chapter is the menu players use to trade quality for speed. The graphics settings menu is the book in miniature: each option switches or scales a technique from an earlier chapter, and each has a cost in GPU time, memory or CPU time that the tools above can measure.

An everyday comparison

A car's dashboard, a mechanic's diagnostic computer and a dashcam. The dashboard says the car is slow; the diagnostic computer reads every sensor over a whole drive and shows which system is struggling; the dashcam replays one moment frame by frame. The driver's mode switch, Eco or Sport, trades fuel for speed in one turn of a knob, the way a quality preset does.

The problem it solves

Without measurement, optimisation is opinion: people speed up what they suspect, and the frame stays slow. With the right tool, the slow pass and the draw inside it have names and numbers, and every fix can be checked. Without a well-built settings menu, a game runs well only on the machine it was tuned on.

Why a lead cares

A lead does not need to drive these tools, but should ask for their output: a capture from the target hardware, the pass that is over budget and by how much, and the draw responsible. That evidence is also what an AI agent needs in its brief (12.2). The settings menu is a product decision as much as a technical one: which options exist, what each preset means on each platform, and what Low must still look like.

3 How it works

The steps go from how a capture is made, through how GPU time is measured and which tool to open for which question, to the tools themselves, a workflow and a worked capture. The last two steps decode the settings menu and the presets that bundle it.

1 What a frame capture records

A frame capture is a recording of every graphics API call in one frame, with the buffers and textures those calls used. The capture tool slips a layer between the game and the graphics driver; while the game runs, the layer passes each call on as normal and also writes it down. Afterwards the tool can replay the frame on a developer's machine, as many times as needed, and stop at any call.

Captures are only readable if the game names its work. A debug marker wraps a group of commands with a name such as "Shadow depths" or "Bloom"; the tool shows those names as the folders of the event list. Engines name their own passes this way; naming the game's own work is up to the team. Without markers, a frame is a flat list of thousands of anonymous draw calls.

2 How GPU time is measured

The CPU cannot time GPU work with its own clock: it only records commands, and the GPU runs them later (2.2). Instead the game puts a GPU timestamp query into the command stream before and after each pass. Microsoft's Direct3D 12 documentation says a timestamp is sampled when the GPU has finished all of the preceding work; the difference between two, divided by the queue's timestamp frequency, is the pass's GPU time. Vulkan's queries work the same way, with a period in nanoseconds per tick, and WebGPU has an optional timestamp-query feature.

Timestamps are cheap, which is why every engine can show live GPU timings per pass. They cannot say why a pass is slow. For that, vendor tools read the GPU's hardware counters: how busy each unit was, how much memory bandwidth was used, how full the shader cores were. That is the difference between the two rows of GPU questions in the next step.

3 Which tool answers which question

Every investigation starts the same way: is the frame over budget, and is the longest lane a CPU thread or the GPU? 11.1 showed that the longest lane sets the frame time. Unreal's stat unit shows the frame, game thread, render thread and GPU times on screen; the Unity Profiler and Godot's Profiler and Monitors give the same split. The answer decides which half of the chart to follow.

5 A capture workflow

Tools only help if the measurement is repeatable. The same four steps work for CPU and GPU problems, in any engine.

6 Reading a capture: a worked example

A 60 fps game runs at 19.8 ms of GPU time in its market square, 3.1 ms over the 16.7 ms budget. The team has a budget allocation per pass from 11.1, so the capture can be read against it pass by pass.

The worked example shows the habits that make captures useful: compare against a budget rather than against intuition, expand the guilty pass before changing anything, and read individual draws, because the cause is usually one kind of content rather than the whole pass.

7 The graphics settings menu, decoded

A settings menu looks like a list of words, but each row is a technique from this book with a known kind of cost. Some options cost per pixel and scale with resolution; some cost memory; some cost CPU time in draw calls. Knowing which is which explains why an option helps one machine and not another.

Menus also hide differences in what an option means. "Shadows: High" might change the map size, the number of cascades and the shadow distance at once, and "Anti-aliasing" in one game may choose between methods while in another it sets the quality of one method. When an option's effect is unclear, the tools above settle it: take a capture with the option at two levels and compare the passes.

8 Presets and platforms

A quality preset sets every row of the menu at once: Low, Medium, High, Ultra. Presets exist because players should not need this book to get a good result, and because nobody can test every combination. Each platform, and each class of PC hardware, starts from one preset; a player can then change single rows, which many games then label Custom.

Each engine builds presets from its own pieces. Unreal groups its settings into scalability groups, each with levels from Low (0) to Epic (3) plus Cinematic, defined in BaseScalability.ini; Epic's Lumen performance guide shows a PS5 device profile that sets sg.GlobalIlluminationQuality and sg.ReflectionQuality to High to target 60 fps. Unity's quality levels form a matrix with platforms, with a default level per platform, and each level can use its own render pipeline asset. Godot has no preset system of its own: a project builds its menu from project settings, viewport and environment properties, and overrides settings per platform with feature tags, such as the 2048 directional shadow size that replaces the default 4096 on mobile.

Simplified

The grid shows one preset per platform. Real games often add a dynamic resolution target, separate presets for battery and plugged-in play on handhelds, and per-device exceptions for phones with known GPU problems, all of which sit on top of the presets.

4 What it costs

Measuring costs time on the machine and time from people. Timestamps are nearly free; captures are not, and the slowest part of any investigation is usually reproducing the problem in the same place twice. The settings menu costs testing time, because every option multiplies the number of ways the game can run.

Worked example. A game has ten graphics options with four levels each: 410 = 1,048,576 combinations, far too many to test. Four presets on five platforms is 20 configurations. If a performance pass on each takes 30 minutes, capturing three fixed camera bookmarks and a one-minute route, one round of preset testing is 10 hours of QA time, which is why teams automate it and run it nightly. The texture row shows why one option can matter more than the rest on small cards: a full mip chain is about 4/3 of its top level, so keeping one level fewer leaves 1/3 of the top level, a quarter of the original.

  • Platforms and GPU vendorsEach needs its own tool and its own captures; a pass that is fine on one GPU can be slow on another.
  • Options and levelsEvery option multiplies the combinations to test, and every level is a configuration that can break.
  • Captures that cannot be repeatedWithout fixed camera bookmarks and builds, two numbers cannot be compared and the work repeats.
  • Missing markersAn unnamed frame takes far longer to read; naming passes is the cheapest speed-up an investigation can get.
  • Capture sizeA capture stores the starting contents of every resource the frame touches, so heavy scenes make large files that are slow to open.

The usual trade

Teams name every pass with markers, keep camera bookmarks for the heaviest places, and run automated performance captures of each preset on each platform every night. They treat the Low preset as a promise to the minimum-spec machine and test it as hard as High, because players on weak hardware are the ones who notice.

5 How it breaks

Measurement fails when it measures the wrong thing, in the wrong place, or changes what it measures. Settings menus fail when an option does less, or something different, from what it says.

Fast in the editor, slow on the console

Cause
Numbers taken in the editor or on a fast development PC. The editor adds its own work, and the target has a different GPU, memory and CPU.
Ask for
A capture from a development build on the target hardware, at a fixed camera bookmark, with the tool and frame named.

The problem vanishes in the capture

Cause
Capturing changes timings, so a bug that depends on timing, such as a race between threads or a resource used before it is ready, may not happen while recording.
Ask for
A capture of several frames, a video of the live bug, and validation layers or GPU-based validation run on the same build.

Pass times add up to more than the frame

Cause
Passes overlap, for example with async compute, or timestamps are taken at the end of earlier work rather than at the start of a pass.
Ask for
The frame's critical path on a timeline view, and which passes run in parallel, before cutting the one that looks biggest.

A wall of unnamed draws

Cause
No debug markers in the build being captured, often a shipping configuration that strips them.
Ask for
Markers around every pass and major system, kept in development builds, and the engine's option for per-draw names when needed.

Low is hardly faster than High

Cause
The biggest cost is in no preset: a pass, a feature or a piece of content that every level runs at full price.
Ask for
Captures of the same place at Low and High, compared pass by pass, and a list of costs no setting changes.

A setting changes nothing until a restart

Cause
Some settings are read only at start-up, or need resources rebuilt; Godot's documentation says its VoxelGI quality setting is only read when the project starts.
Ask for
A list of options that need a restart or a reload, marked in the menu, and a test that each option changes the frame when applied.

7 Say it to your AI

Performance briefs go well when they attach a capture from the target hardware, name the tool and the place it was taken, and ask for the cause with evidence before any change. Settings work goes well when it asks for measured costs per option, not opinions.

Capture triageUse when a GPU pass is over budget
Windows PC build, Direct3D 12, RTX 3060 at 1440p, target 60 fps (16.7 ms). A PIX GPU capture of frame 2417 at camera bookmark 3 and our per-pass budget table are attached.

1. List the passes over budget, sorted by how far over, with their measured time and budget.
2. For the worst pass, expand it and name the draws or dispatches that cost the most. Group them by mesh, material or shader.
3. Explain the likely cause of each group's cost from what the capture shows: triangles, pixels covered, shader, textures, render target formats.
4. Propose up to three changes with the expected saving and the visual risk of each. Do not propose changes to passes that are within budget.
5. Tell us exactly how to confirm each saving with a new capture at the same bookmark.
  • Naming the build, GPU, resolution and bookmark makes the numbers comparable.
  • The budget table turns "slow" into "2.6 ms over".
  • Asking how to confirm each saving keeps the result checkable.
Settings menuUse when building or reviewing presets
Unity 6.6, URP. Platforms: PC, Steam Deck, Xbox Series S. We want Low, Medium, High and Ultra quality levels and a graphics menu with Upscaling, Anti-aliasing, Shadows, Ambient occlusion, Textures and View distance.

1. For each menu option, list the Quality settings, URP Asset and Renderer settings it should change, at each level.
2. Say which options need different URP Assets per quality level and which can change at runtime.
3. Propose the default quality level per platform and why.
4. Write a test that loads each level on each platform, captures the same three camera bookmarks and records GPU time per pass and memory, so we can fill in the real cost of each option.
5. Flag any option that needs a restart or a reload to take effect.
  • Listing the menu rows up front stops the AI inventing options.
  • Asking for a measuring test replaces guessed costs with numbers.
  • Restart flags prevent a menu that silently does nothing.

Questions to ask when reviewing profiling and settings work

  1. Which tool, which build and which hardware produced this number?Numbers from the editor or a development PC say little about a console.
  2. Is it one frame or an average of many, at a fixed camera position?Single frames vary; a fixed bookmark and a median make results comparable.
  3. What was the frame time before and after, in milliseconds?Frames per second hides the size of a change, and averages hide spikes (11.1).
  4. Does each preset level change what the menu says it does?Compare two captures at different levels; options that do nothing are common.
  5. What does the Low preset look like and cost on the minimum-spec machine?Low is the promise the store page makes to players on weak hardware.

8 Check yourself

  1. A pass starts at timestamp 4,200,000 and ends at 4,236,000 on a queue whose timestamp frequency is 12,000,000 ticks a second. How long did it take on the GPU, and when can the CPU read the result?

    Show answer

    3 ms: 36,000 ticks divided by 12,000,000 ticks a second is 0.003 s. The CPU reads it a frame or two later, once the GPU has finished and the results are copied back, so engine overlays show slightly old, averaged numbers.

  2. A character's armour renders black on one PC graphics card only. Which kind of tool do you open first, and what do you look at?

    Show answer

    A frame debugger, such as RenderDoc, PIX or Nsight Graphics, on the affected card. Find the armour's draw in the event list, check the textures and buffers bound to it, its pixel shader and its output, and step through one black pixel's shader to see where the value goes wrong.

  3. Players with 8 GB graphics cards report stutter on High that goes away on Medium. Which menu option is the likely culprit, which cost does it move, and roughly how much does one step down save?

    Show answer

    Textures, which mostly costs video memory (6.3, 11.4). If one step down drops each texture's top mip level, it saves about three quarters of texture memory, because the top level is about three quarters of a full mip chain.
